# 今日晨报 V2.0｜产品设计 V0.6

> **定位**：今日晨报 V2.0 的初步最终版产品设计，供产品所有者整体审阅，也作为后续开发的产品依据。本文聚焦“用户看到什么、系统提供什么、关键行为如何约定”，不承担技术验证报告、实施任务清单或接口设计职责。  
> **设计基准**：北京时间（Asia/Shanghai）｜PC 浏览器｜每天 08:00 启动生成｜以真实信息价值、可追溯性和阅读体验为先。  
> **配套说明**：技术架构、数据源验证、接口与模型、缓存实现、文档冲突、开发验收及 V3.0 候选见《V0.6.1额外信息.md》。

## 一、产品全貌

### 1.1 产品是什么

**今日晨报**是嵌入现有个人助手的独立模块。它每天将**国内新闻、国际新闻、AI 技术资讯**与用户的**昨日活动、长期目标、历史资讯和行动偏好**结合，生成一份可以连续阅读、能够追溯依据的中文晨报。

它每天回答三个问题：

1. **世界发生了什么？** 筛选值得关注的重大公共事件和有实质价值的 AI 进展。
2. **我的昨日有什么进展？** 只归纳有时间证据的个人活动和目标变化。
3. **今天有什么值得做？** 在事实、长期目标和历史建议的基础上，给出必要且不重复的行动建议。

这不是综合新闻门户，也不是自动执行任务的助手。**晨报的价值在于精选、理解、关联与建议，而非展示海量资讯。**

### 1.2 产品模块总览

| 模块 | 用户价值 | 主要产出或入口 |
| --- | --- | --- |
| **资讯获取与筛选** | 每天获取有价值、可溯源的国内/国际/AI 新闻 | 重要资讯候选、来源与覆盖说明 |
| **昨日回顾** | 回顾真实进展，而不是重述当前任务清单 | “我的昨日” |
| **历史知识与检索** | 把新资讯与旧资讯、目标和历史建议联系起来 | 技术演进解释、历史关联与建议去重 |
| **分析与晨报编写** | 把多类材料组织为自然、可信的文章 | 五部分中文晨报 |
| **晨报助手与 Memory** | 让个人兴趣、行动偏好和补充目标长期可控 | 右栏对话、记忆管理 |
| **质量、历史与运行状态** | 看清结果是否可信、能否回看及出错原因 | 质量评价、历史版本、实时日志、使用统计 |

### 1.3 V2.0 的边界

- 只在现有个人助手中新增模块，不改变现有任务、阅读、备忘等功能的业务规则；**现有个人助手数据库只读**。
- 晨报提出建议，但**不自动创建/完成任务、不修改长期计划、不执行外部操作、不发送消息**。
- 晨报助手用于资讯偏好、行动偏好、补充目标和记忆澄清，**不提供通用新闻追问或开放式深度研究对话**。
- 当前仅考虑 **PC 浏览器**，不额外设计移动端独立体验。
- 不为展示技术而增加无意义的 Agent、页面、新闻类别或固定篇幅。

## 二、每天如何使用

### 2.1 自动生成与时间规则

- **每天北京时间 08:00 启动一次常态资讯获取及晨报生成流程**，国内、国际、AI 三类资讯都采用**每日一轮**，不再采用原先每四小时的后台采集安排。
- 08:00 是**启动时间和本期内容截止点**，**不是必须已经生成完毕的时刻**。
- 每期内容窗口固定为**前一天 08:00（含）至当天 08:00（不含）**，同时适用于新闻发布时间和“我的昨日”中有据可查的事件时间。
- 采集可能包括多个来源、接口分页、有限失败重试；这些属于本轮内部工作，**不代表增加每天的常态采集轮次**。
- 若 08:00 后才获取到一条在截止前发布的新闻，只要在本次数据快照固定前取得且证据充分，可以纳入；**截止后新发布的新闻不进入当期晨报**。

### 2.2 用户一天中的体验

1. 系统按时启动，获取三类资讯，核查来源、去重并准备个人上下文。
2. 处理完成并通过必要检查后，分析流程生成中文晨报，核验事实并保存结果。
3. 用户进入模块，默认看到**当天的主报告**；生成尚未结束时看到清晰的当前状态与实时日志。
4. 用户阅读正文，或切换到**质量评价、历史晨报**；需要时在右栏修正偏好和补充目标。
5. 若报告需要纠正，可点击**“重新生成”**，系统在不破坏旧版本的前提下生成新版本。

> 用户不需要守着 08:00 等候。系统应正确展示生成中、已完成、降级完成、失败和未评价等状态，不让旧报告冒充今天的报告。

## 三、晨报正文：读者实际看到什么

### 3.1 五部分固定内容结构

五部分是**文章的组织骨架**，不是要求每节都填满，也不是将原始数据库字段排列在页面上。

| 部分 | 内容设计 | 展示方式 |
| --- | --- | --- |
| **一、开篇速览** | 对本期重要资讯进行整体提炼，呈现今天值得先知道的事 | 一小段自然概述；不重新摘出与正文重复的“今日三条” |
| **二、重要资讯** | 国内社会、国际社会、AI 技术三类；以公共价值和实质进展决定篇幅 | 国内/国际：**标题＋摘要**；AI：**标题＋摘要＋评价** |
| **三、我的昨日** | 有证据的进展、长期目标变化及值得延续的问题 | 自然叙述，不强制分成指标卡、完成数等栏目 |
| **四、今日建议** | 结合资讯、个人目标、历史建议形成行动方向 | **0–3 条**，具体、可执行；没有价值时可没有建议 |
| **五、信息说明** | 覆盖窗口、主要来源、生成时间、数据或核验缺口 | 轻量显示，不与正文争夺注意力 |

### 3.2 不同新闻的表达规则

**国内与国际新闻**以“标题＋摘要”为主。摘要应交代事件、必要背景和关键变化；原始报道链接作为清晰但轻量的来源标记。无需为每条新闻强制添加“对我的影响”“分析评价”等栏目。

**AI 技术资讯**在摘要之外必须有**评价**：说明技术价值、局限、现实意义；当历史对比确实有帮助时，把它自然写进评价，不新增重复的“历史关联”字段，也不要求每条 AI 新闻机械对比旧资料。

同一事件的多个报道应尽可能聚合展示；如出现新版本、新数据、重要争议或更正，允许作为**新的实质进展**纳入，不能简单当作重复内容丢弃。重大公共新闻不能仅因不符合个人兴趣而被过滤。

### 3.3 篇幅与阅读原则

- 默认约 **5 分钟阅读量**；重大资讯较多时可以延长至约 **8–10 分钟**。
- 信息少时可以更短，不能为了满足字数而添写空泛内容。
- 优先保证事实、可读性与上下文，而不是每个类别平均分配条数或字数。
- 来源、覆盖缺口等辅助信息尽量放在“信息说明”，但重要判断必须能追溯依据。

## 四、主要功能模块与重要规则

### 4.1 资讯模块：每日发现、筛选与核查

| 类别 | V2.0 的初始获取方案 | 业务侧重点 |
| --- | --- | --- |
| **国内社会** | **中新网按日归档 + 热摸爽** | 全国性重要事件、公共政策、社会与经济变化；不只追逐热搜 |
| **国际社会** | **中新网国际／时政相关归档 + 热摸爽相关资讯** | 国际外交、冲突、安全、经济和重大公共事件；时政栏中与国际有关的新闻也应纳入候选 |
| **AI 技术** | **AIHOT 精选资讯**为主要入口；热点作为辅助线索 | 模型、论文、框架、产品及开发工具的实质进展 |

上述为**V2.0 初始组合**，不意味着其覆盖率或长期可靠性已经获得上线验收；来源缺失和重大事件遗漏必须被发现和说明。新闻来源及策略若后续调整，不应改变用户看到的三类资讯与统一晨报窗口。

资讯处理遵守以下产品规则：

- **按原始发布时间确定归属**，不是简单读取聚合站点“最近 24 小时”列表；无可靠时间的条目不能直接当成当期新闻。
- **先保存可追溯材料，再参与生成**；保留来源、原文链接、发布时间、获取/核验状态。原文无法取得时明确说明，不伪装成已经阅读全文。
- **保守去重**：相同文章可以合并，多个来源的同一事件可以归组；存在实质新进展或不确定性时保留原始证据和独立候选。
- 热度是**发现线索**，不等于真实性或公共重要性；关注重要政策、财经及不容易上热榜的公共议题。
- 原文、聚合摘要和自动生成的评价必须区分；重要事实回溯可靠来源，不能把聚合摘要直接当作最终事实。
- 新闻正文与元数据的留存须符合来源使用条件，不因是免费接口就默认可以无限期保存第三方全文。

### 4.2 “我的昨日”：可信的个人回顾

结合现有个人助手中可用的每日任务、长期计划、重要信息、随手备忘、阅读记录及有时间依据的 GitHub 等活动，关注**真实进展和目标变化**。

- **只陈述有时间证据的行为**；不能把“今天看起来是已完成”推断为“昨天完成”。
- 优先考虑**标红的重要长期计划**，并联系实际发生的活动与遗留问题。
- 对话补充目标可以辅助分析；如与原有长期计划冲突，**长期计划是权威依据**，晨报助手可请求澄清，但不能自动改原计划。
- 如果历史记录不足，就清楚说明无法还原哪些变化。系统可以从上线后积累自己的只读历史快照/事件证据，**不倒推不存在的历史**。
- 输出应像个人日报，不是将所有任务、阅读和备忘逐一列出。

### 4.3 历史知识：让晨报形成连续性

系统能够检索**历史 AI 技术资料**和**既往晨报**，用于理解技术演进、目标变化，以及之前是否已经提出过相同建议。

- 历史关联以**实际信息增益**为准，不为每一条资讯强行找历史关联。
- 旧资料不会仅因年代久远就被排除；观点可能随时间变化，但客观事实冲突必须核验原始证据。
- 旧晨报可作为查找线索、理解过去建议的依据，**不能单独作为事实真伪证明**。
- 三个 Subagent 都能根据任务需要检索历史资料；复杂问题可按需进行 **Query 改写**（优化检索问法）与 **Rerank**（重排候选结果），简单问题不必运行完整增强链路。
- 不强行把现有计划、任务与所有 Memory 都改造成向量数据；这些信息仍优先使用其权威记录。

### 4.4 三个固定 Subagent：各自负责什么

| 角色 | 工作内容 | 需要坚持的边界 |
| --- | --- | --- |
| **技术研究** | 分析重要 AI 技术变化、价值、局限与历史脉络，必要时进一步检索证据 | 没有值得深究的进展可以明确说明，不制造技术评价 |
| **目标分析** | 对照昨日活动、重要长期计划、已确认 Memory 和历史晨报，识别真正的目标进展 | 不把缺失记录当作已发生事实，不修改个人数据 |
| **建议** | 综合资讯和前两个角色的实际结论，检索历史建议，输出当日有价值的行动建议 | **0–3 条**；不重复已完成、失效或空泛建议 |

**每天固定调用三个 Subagent。** 技术研究与目标分析可并行；建议 Subagent 必须在两者完成或已明确失败后运行。部分角色出错时允许按情况降级，但不能把“角色运行失败”冒充“角色判断没有建议”。

除三个 Subagent 外，系统还会进行必要的资讯分析、个人分析和最终编辑。**固定步骤用于可靠组织流程，Subagent 用于需要推理、综合与自主历史检索的部分。**

### 4.5 晨报助手与 Memory

右栏保留**一个晨报助手对话入口**，主要负责：

- 录入和修正资讯偏好（感兴趣／不感兴趣领域、解释深度、阅读风格）。
- 录入和修正行动建议偏好（希望的行动方式、约束与优先方向）。
- 补充短期目标、澄清与正式长期计划之间的冲突。
- 查看、编辑、禁用、删除已经确认的 Memory。

**Memory 规则：** Agent 可以提出可能的偏好，但只有在主动告知且获得用户确认之后才能写入；不能无声推测并持久化。无需另外建设一套“建议有用／无用”投票系统，用户可以直接在对话中反馈。

### 4.6 事实校验与独立质量评价

这两个环节职责不同，不能混为一谈：

| 环节 | 检查什么 | 对发布的影响 |
| --- | --- | --- |
| **事实与引用校验** | 新闻出处与时间、事实冲突、个人活动证据、历史引用、重复与建议依据 | **严重错误或关键依据缺失时不发布错误报告** |
| **独立内容质量评价** | 成品文章的呈现、逻辑、AI 分析、个人总结建议和阅读体验 | **不设分数合格线**；评价失败不阻塞已通过事实校验的报告 |

质量评价只接收**最终晨报正文**，输出：

1. **综合分（0–100）**；
2. **五项分数**：资讯呈现、内容逻辑与一致性、AI 技术分析、个人总结与建议、阅读体验；
3. 一段自然语言**“评价”**，可自然提及优点、不足和改善方向，不再拆分为多个固定评语框。

**V0.6 采用五维等权综合分**：每项 20%，综合分为五项分数的算术平均，按统一规则取整数；评分规则随历史版本保存。评价不负责证明原始新闻真实，也不会因为低分自动重写晨报。

### 4.7 使用统计与运行透明度

用户能够了解本期是否正常完成，以及系统为本期报告做了什么：

- 当前阶段、执行开始/结束时间、重要步骤耗时、异常原因及重试信息。
- 模型调用次数、输入与输出 Token、可获得的缓存数据、费用估算或实际返回的计费信息。
- 阶段结果复用、历史检索增强、向量复用等关键处理的情况。
- 具体数据无法从服务商获得时明确标为“未知”，而不是当作 0。

日志以**业务事件**为默认展示，技术细节按需展开；不展示私密原文、API Key 或模型内部思考。

## 五、端到端产品流程

```text
每天 08:00 启动（固定本期 08:00—08:00 时间窗口）
            │
            ▼
并行获取国内 / 国际 / AI 资讯（每日一轮）
            │
            ▼
时间筛选、保守去重、来源核查、保存资料
            │
            ▼
完成必要历史索引与 AI 资讯索引检查
            ├── 关键索引失败 → 停止分析、记录故障并有限重试
            ▼
冻结本次新闻与个人上下文的数据快照
            │
            ▼
资讯分析 ────────── 个人分析（并行）
            │                 │
            └────────┬────────┘
                     ▼
技术研究 Subagent ── 目标分析 Subagent（并行）
                     │
                     ▼
          建议 Subagent（后置）
                     │
                     ▼
             主编整合五部分晨报
                     │
                     ▼
           事实与引用校验（发布门槛）
                     │
                     ▼
           独立质量评价（失败可缺失）
                     │
                     ▼
      保存、发布、历史版本与检索记录更新

全程：状态恢复｜有效结果复用｜实时日志｜用量与费用记录
```

**原则**：参与本轮生成的资料必须归属同一明确的数据快照；后续新增或更正的资料不能静默改变已生成版本。为保持报告完整，快照固定前必须先确认必要索引可用。

## 六、报告版本、重新生成与故障体验

### 6.1 每日主报告与附加版本

- 每个北京时间自然日只有**一个正式主报告身份**。
- 自动生成成功后形成主报告；若自动生成失败且当天尚无主报告，**首次手动成功生成**的报告成为当日主报告。
- 当天已有主报告后，重新生成的成功结果作为**附加版本**保存，不覆盖原主报告。
- 每个版本对应自己的正文、时间、来源、数据快照、质量评价和运行记录；历史记录不能因为之后的计划或 Memory 变化被静默改写。
- 用户能够查看和切换历史日期、版本，也能回到当日主报告。

### 6.2 重新生成

页面主要操作只有一个醒目的 **“重新生成”**：

- 默认可安全复用仍然有效的分析结果，受影响的分析重新执行。
- 如用户发现分析错误，可通过高级入口使错误结果失效并执行完整重算；旧错误不能因缓存反复出现。
- 同一日期避免重复并发生成；手动重新生成使用该日期原有的内容截止窗口，允许补齐当期遗漏，但不加入截止后新发布的新闻。
- 重试和重新生成不改变“每天 08:00 一轮常态采集”的原则。

### 6.3 失败与降级

| 场景 | 用户看到的结果 |
| --- | --- |
| 个别新闻来源失败、缺全文 | 有足够可信材料时可**降级完成**，信息说明标注缺口；绝不编造原文 |
| 必要历史／AI 检索索引异常 | **生成阻塞或失败**，说明原因；恢复后再继续 |
| 技术研究或目标分析失败 | 如剩余结果仍可信，可降级，但显式说明缺失 |
| 建议角色失败 | 标注“建议分析失败”，不能伪装成“今日没有建议” |
| 最终主编失败，或严重事实／引用错误 | **不发布错误或不完整的报告** |
| 独立质量评价失败 | 报告仍可显示，评价页提示**未评价／评价失败** |

自动失败采用有限重试，不能无限等待、静默更换模型或用昨天的正文冒充今天。

## 七、页面与交互设计

### 7.1 导航与布局

```text
个人助手 > 今日晨报
┌────────────────────────────────────────────────────────────────────────┐
│  今日晨报    日期 / 内容周期                              [重新生成]  │
│  [晨报正文]     [质量评价]     [历史晨报]                               │
├────────────────────────────────────────────┬───────────────────────────┤
│                                            │                           │
│  宽阅读区                                  │  右侧辅助区               │
│                                            │  晨报助手                 │
│  一、开篇速览                              │  · 偏好 / Memory / 目标   │
│  二、重要资讯（国内/国际/AI）              │                           │
│  三、我的昨日                              │  实时执行日志             │
│  四、今日建议                              │  · 当前阶段 / 详情        │
│  五、信息说明                              │                           │
└────────────────────────────────────────────┴───────────────────────────┘
```

- **三项二级导航**是模块页面，不是文章内部标题：**晨报正文／质量评价／历史晨报**。
- 主阅读区明显宽于右侧辅助区。右栏以晨报助手为主、运行日志为辅；不复刻正文过窄、频繁折行的布局。
- **Memory 管理从晨报助手内进入**，不增加第四个二级页面。
- 分层去重、历史检索和缓存属于后台能力，不为它们单独增加页面。

### 7.2 各页面的核心内容

**晨报正文**：采用舒适的中文字号、行高和段落间距；突出自然阅读，不堆砌大面积卡片、评分、统计仪表盘。来源链接易识别、可打开，信息说明视觉弱化但仍清楚。深色模式控制对比，避免刺眼。

**质量评价**：显示所选报告的日期、版本、综合分、五项评分条与一段自然评价；未评价时不显示虚假的 0 分，也不设置“低于某分不合格”标签。

**历史晨报**：按日期和版本查看旧报告；切换报告后，正文与评价必须指向**同一版本**。旧报告需要显示原日期，不能误认作当日生成结果。

**右栏**：对话主要用于偏好/Memory/目标补充；日志按实际时间和角色归属显示并行事件，技术细节可以展开查看，不强迫用户一直观察运行过程。

### 7.3 用户可识别的状态

- **生成中**：显示当前阶段与实时日志。
- **已完成**：显示可阅读的当期报告和生成时间。
- **降级完成**：报告可用，但明显说明数据或分析缺口。
- **失败**：显示失败阶段、可重新生成入口及旧报告入口。
- **未评价／评价失败**：评价功能状态，不等于晨报正文失败。

## 八、产品质量与验收原则

| 产品目标 | 看什么才算达到预期 |
| --- | --- |
| 新闻有价值 | 国内/国际重大新闻不被兴趣过滤；AI 体现真实技术进展；覆盖不足可见 |
| 事实可信 | 重要事实、时间和个人进展有来源；缺失不编造；严重错误阻止发布 |
| 观点连续 | 历史技术变化、目标推进与建议去重体现实质信息，不是形式引用 |
| 建议有用 | 0–3 条可执行、关联当前目标；不强推已完成或无意义事项 |
| 内容耐读 | 默认约 5 分钟；重要时可延长；避免填字数、重复和字段清单化 |
| 过程可靠 | 固定窗口、一次日常采集、快照隔离、失败可观察、错误可恢复 |
| 版本可追踪 | 主报告唯一，附加版本保留，正文／评价／来源一一对应 |
| 使用透明 | 日志、用量、费用和缺失项可查看，未知值不冒充零 |

这些是**产品验收原则**，不表示相关功能已经正式开发或上线验收通过。

## 九、V2.0 最终设计边界

**V2.0 必须保留：** 每日 08:00 的三类新闻获取、固定时间窗口、自然阅读型五部分晨报、可核实的昨日回顾、三个固定 Subagent、按需历史检索、可控 Memory、0–3 条建议、事实校验、独立质量评价、历史版本、重新生成、日志与故障恢复。

**V2.0 不做：** 独立新闻门户、通用开放式研究聊天、自动执行建议、自动改个人计划、移动端独立页面、为每项优化新增 Agent 或额外导航。

**V3.0 候选**包括语音播报、环境上下文、更加长期的行为趋势与 Memory 学习、开放式新闻追问、Agent 异步优化、Agentic RAG 和 Skills 等。它们不应侵入本轮 V2.0 的必要交付。
