# Personal Hub V1.0 开发计划

版本：v0.2（已含用户决策 D1–D8）
范围：**本文档只管理 V1.0 版本的开发任务与验收标准**；V1.0 之后的规划（V2.0 移动端、备份恢复及待评估需求）统一维护在 `Docs/ROADMAP.md`，未经用户批准不得排入本文档。
阶段总览：0 审查设计 → 1 基础设施 → 2 计划/阅读 → 3 微信集成 → 4 资讯中心 → 5 清理审核 → 6 验收。
顺序理由：1 先把骨架（后端框架、前端框架、启动器、任务/迁移机制）立起来；2 用两个纯 CRUD 模块验证全链路（API→库→前端→打包→启动器）；3 微信复用改造工作量最大、依赖 1 的任务机制，且按 D3 拆成可独立验证的小步；4 资讯独立可后置；5 清理依赖 3、4 的数据都已落库（备份能力按 D1 移出，不在任何阶段实现）；6 收尾。

## 阶段 0：代码审查与设计（本轮）

- 范围：现有项目审查、PRD/架构/测试规划/AGENTS.md 文档；交叉审查并修订（P0×1、P1×7、P2×6 已全部处理）。
- 产出：`Docs/PRD.md`、`Docs/ARCHITECTURE.md`、`Docs/TEST_PLAN.md`、`Docs/DEVELOPMENT_PLAN.md`、根目录 `AGENTS.md`（均为 v0.2）。
- 完成标准：文档通过用户审核；D1–D8 决策全部落入文档（PRD §1.4）。

## 阶段 1：后端基础设施 + 前端框架 + Windows 启动器

- 依赖：阶段 0 审核通过。
- 创建：
  - `app/`：FastAPI 装配、`config.py`（pydantic-settings，默认端口 8620）、`db.py` + Alembic 初始化、`api/health`、统一错误格式、隐私白名单日志、任务框架（`tasks/` 表 + 进程内执行器）、`token_usage` 埋点、`chat_sessions/chat_messages` 表。
  - `web/`：Vite + React + TS + Tailwind + shadcn/ui + TanStack Query 骨架；布局 + 路由 + 7 个页面占位；首页静态壳；Vitest 骨架。
  - `launcher/`：`launch.py` + `.vbs/.bat` + 桌面快捷方式说明。
  - `tests/`：pytest 骨架 + conftest（临时库、依赖覆盖、数据隔离守卫——测试一律使用隔离副本/临时库，见 PRD §2.6）。
  - 精简 `requirements.txt`（当前 `requirements_full.txt` 为 UTF-16 且含大量用不到的依赖：milvus/postgres/jupyter/unstructured 等，按实际 import 裁剪；FastAPI/uvicorn/SQLAlchemy/alembic/feedparser/httpx/chromadb 等保留）。
- 完成标准：`pytest` 通过（含数据隔离守卫用例）；`launch.bat` 双击 → 浏览器打开首页壳； Alembic 迁移可空库初始化；**FastAPI 能托管 `web/dist` 构建产物并访问到首页**；端口默认 8620。
- 测试：健康检查、统一错误格式、任务状态机流转（单元）、数据隔离守卫（测试运行期间真实聊天库路径零写入，单元/集成）。
- 风险：`LangGraph/` 与 `langgraph` 包名冲突在此阶段开始规避（新代码一律不 import 该目录，留待阶段 3 按 D3 迁移）；requirements 裁剪需逐条核对 import。

## 阶段 2：计划管理 + 阅读管理

- 依赖：阶段 1。
- 创建：`models`/`schemas`/`services`/`api` 的 plans、reading 模块；前端两个完整页面（含响应式）；文件上传（大小/类型校验、按书籍归档）。
- 完成标准：PRD §2.3、§2.4 全部功能可用（"移至下一天"= task_date 变更 + moved_from_date 溯源，不复制副本）；刷新/重启不丢数据；手机宽度布局可用；**用户提供云记导出样例后完成笔记预览验证（D7）**。
- 测试：单元（排序、移至次日、状态流转、进度计算、上传校验）；集成（API↔SQLite 每个端点）；前端组件测试（计划勾选/排序、上传交互）；端到端手工脚本 2、3 条（见 TEST_PLAN）。
- 风险：无外部依赖，风险低；注意排序并发（个人使用，乐观处理即可）。

## 阶段 3：微信聊天助手集成（复用改造，按 D3 分步、D2 单通道）

依赖：阶段 1（任务机制）、阶段 2（前端模式参考）。**本阶段拆为以下顺序执行的子步骤，每步独立可验证、单独提交，禁止合并为一次大改动**：

1. **3.1 回归测试先行**：为现有 Agent、总结流水线、RAG 检索、数据库访问建立回归测试基线（Mock LLM/Embedding，固化现有行为：工具返回值格式、报告 JSON Schema、chunk 确定性）。
2. **3.2 目录迁移**：`LangGraph/`、`GetWechatInfo/`、`Tool/` → `app/wechat_agent/`；修正全部 import、配置路径、资源引用与 `__init__.py`。**不改任何业务逻辑**。
3. **3.3 迁移验证**：跑 3.1 基线全绿 + 真实库只读冒烟（单轮问答、单日总结输出与迁移前对拍一致）。
4. **3.4 重建 normalize_snapshot.py**：建于 `app/wechat_agent/` 内（原始快照→归一化，幂等）；与历史归一化库对拍验证（在隔离副本上进行，PRD §2.6）。
5. **3.5 多群适配**：总结按 chat_id 过滤；Agent 提示词补充群选择约束；单群结果与 3.1 基线对拍一致。
6. **3.6 同步服务**：`adapters/wechat_source.py`（健康检查、按 D5 启动已配置 exe、就绪轮询）+ `services/wechat_service.py`（sync_cursors 游标增量→原始库→归一化→`rag_store.incremental_index`）、报告列表/查看。
7. **3.7 Agent 服务化与前端**：Agent 调用封装（SSE 流式、会话历史）、任务状态；前端微信页——**对话窗口为主体**（流式问答、多轮上下文、3 个预置快捷输入 chips 与普通输入同通道进 Agent、总结状态内联展示、报告卡片可点击查看历史）；辅助区含同步按钮/进度、WeChatDataAnalysis 运行状态、库数据时间范围。print 收敛 logger 按 ARCH §6 隐私白名单执行（不改逻辑）。
- 完成标准：PRD §2.1 全部达成；重复同步零重复消息/向量（Mock 计数断言证明）；**所有总结（含快捷按钮）均经 Agent 的 `summarize_chat` 触发（D2，代码评审 + 测试断言无 Service 直调 `run_summary`）**；迁移前后回答质量一致（3.1 基线对拍）。
- 测试：单元（时间范围解析、游标边界——同时刻多消息/中断恢复/迟到对账、归一化幂等、多群过滤）；集成（API↔SQLite、API↔Chroma、适配器 Mock）；迁移前后兼容性（3.1 基线在 3.2 前后均绿）；异常注入（API 超时/启动失败/数据不足 → 清晰错误）。
- 风险：**本阶段风险最高**，已由 D3 拆步显著降低：迁移牵出循环导入→3.3 立刻暴露；normalize 对拍在隔离副本上做；多群改造以单群基线兜底。

## 阶段 4：技术资讯中心

- 依赖：阶段 1、2（前端组件模式）。
- 创建：`adapters/news_*`（HN API、RSS feedparser、GitHub 官方 RSS；按 D6 内置默认来源种子；Trending 不接）、`services/news_service.py`（去重、归一化热度、规则评分、刷新调度）、`models` news 两表、前端资讯页（列表/筛选/排序/收藏/已读/刷新/上次更新时间）。
- 完成标准：PRD §2.2 全部达成；默认来源开箱可用、可在设置中增删；离线时页面给出明确提示而非白屏。
- 测试：单元（去重、各来源热度归一化、评分、过期判断）；集成（适配器 Mock fixture 抓取全链路）；不触网测试全部可跑。
- 风险：RSS 源稳定性（超时/重试/单源失败不影响整体）。

## 阶段 5：周日人工审核清理（D4；按 D1 不含备份）

- 依赖：阶段 3、4（产生可清理数据）。
- 创建：`cleanup/`（候选生成器、审核 API、**三层删除状态机**、**Chroma chunk 局部重建与 rag_state 维护**、审计、非授权删除防护）、前端审核页（PRD §2.5 全部交互）与首页提醒、启动时补生成逻辑、跨周候选去重。
- **完成标准**：PRD §2.5 全部达成，重点验收：默认不预选、跳过不删除、无 confirmed run 执行器拒绝（409）、逐项状态机可断点续跑（kill 后续跑演练）、删除后归一化库+原始快照库+Chroma 三方一致、已删消息语义检索不可命中、未变化 chunk 向量复用（Embedding Mock 计数断言：仅重建 chunk 产生调用）、总结报告不受影响、审计不存内容。
- 测试：单元（候选生成、跨周去重、过期判断、状态机迁移、幂等重跑、chunk 全命中删除/部分命中重建、rag_state 维护后 incremental 不再全量重建）；集成（三层删除一致性：构造跨库数据验证）；异常（执行中断电模拟=执行器中途 kill 后续跑）；非授权删除防护测试。
- 风险：chunk 部分重建触及切分逻辑，宁可保守（未全命中且重建失败则保留旧 chunk 并标记 failed）也不破坏索引一致性；全部验证在隔离副本上进行。

## 阶段 6：端到端测试、异常测试与正式验收

- 依赖：阶段 2–5。
- 范围：TEST_PLAN 全量执行；真实环境演练（真实微信同步与总结、真实清理审核——演练前确认当日已有隔离副本说明，不可逆操作按 PRD §2.6 先获批准）；性能冒烟（首页加载、1 天消息总结时长）；文档收尾（Read.md 重写、CHANGELOG）。
- 完成标准：PRD §5 验收标准 1–6 逐条通过；无 P0/P1 缺陷；用户签字进入日常使用。

## 跨阶段约束

- 每个阶段结束：代码可运行、测试绿、文档同步更新、git 打 tag（stage-N）。
- **数据安全（D1 + PRD §2.6）**：开发与测试一律使用隔离副本/临时库；对唯一真实聊天库的任何不可逆操作必须先告知风险并获用户批准；任何阶段不得改动 WeChatDataAnalysis 原始库。
- **D2 铁律**：任何阶段不得引入 Service 直调 `run_summary` 的总结通道；Agent 工具 docstring = 提示词，未确认不得修改。
- **D3**：目录迁移已批准，按阶段 3 子步骤执行，不再征求意见。
- LLM/Embedding 相关测试一律 Mock，CI/本地默认零付费调用、零真实外网、零真实生产数据。
- **范围纪律**：ROADMAP 中的 V2.0 及待评估需求不属于 V1.0 任务；未经用户明确批准不得排入本计划或提前实现。
