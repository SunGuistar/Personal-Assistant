# 开发计划（Development Plan）

各阶段需要实现的功能规划。本文档只回答"做哪些功能"，不承担进度追踪职责（开发历史由 Git 记录）；需求规则见 `PRD.md`，技术设计见 `Architecture.md`。

V1（个人助手基础版）已全部完成并归档，见 `Docs/archive/DEVELOPMENT_PLAN_V1.md`。本文档管理下一阶段开发规划。

## 核心定位

**个人数据驱动的智能工作助手。**

整合计划、备忘、重要信息、阅读记录及未来接入的 GitHub 等个人数据，利用 AI 进行信息整理、关联分析、总结和建议。

核心目标：

1. **实际提效**：减少信息整理、工作回顾和计划制定的时间。
2. **简历展示**：通过真实功能体现 Agent 工作流、工具调用、上下文管理、长期记忆、检索策略、执行追踪和效果评测能力。

开发原则：

- 以真实需求为导向，避免无意义地堆砌 AI 功能。
- 普通程序能够高效解决的问题，不强行使用 LLM 或 Agent。
- 优先实现有实际价值的功能，再考虑技术复杂度。
- 不强制采用 Multi-Agent。
- AI 分析和建议应尽可能基于可追溯的个人数据。
- 涉及重要数据修改时，应保留人工确认机制（沿用 D2/D4 的"人工确认"传统）。

已确认的开发原则（2026-11-05 批准，下一阶段开发以此为准）：

1. 阶段一优先开发每周回顾 Agent，以跨模块数据分析、建议生成、人工确认和周报保存为核心。
2. 长期记忆以 SQLite 为权威存储，Chroma 仅在需要语义检索时作为辅助索引；第一版不强制向量化。
3. 每日简报采用应用启动或首次进入首页时检查、后台按需生成的方式，不引入常驻守护进程。
4. 每周回顾 Agent 第一版以只读分析和人工确认保存为主，不自动修改计划、备忘等业务数据。
5. 保持本文档的功能规划定位，不记录开发或验收状态。
6. 不提前开发新阶段功能。

## 阶段划分总览

| 阶段 | 内容 | 优先级 |
|---|---|---|
| 阶段一 | 每周回顾 Agent | P0 |
| 阶段二 | 每日工作简报、跨数据源检索与长期记忆 | P0 |
| 阶段三 | GitHub 数据集成、模型调用与成本优化、执行追踪与效果评测 | P1 |
| 阶段四 | 智能信息分类、数据仪表盘（候选） | P2 |
| 开发工具优化（独立事项） | Claude-y Comment Detector | P1 |

划分理由：每周回顾是核心价值闭环，直接复用现有 Agent 与任务状态机能力，且其数据读取需求会沉淀出阶段二所需的检索与记忆基础；每日简报与长期记忆依赖回顾模块验证过的数据通路，放在阶段二；GitHub 集成、成本优化、执行评测是为已有功能（简报/回顾/问答）增强数据与工程能力，依赖前两个阶段的功能形态稳定后再接入；P2 两项仅候选，待实际需求验证后再决定是否开发。

## 阶段一：每周回顾 Agent（P0）

- 手动触发每周回顾。
- 自动读取计划、备忘、重要信息等相关个人数据。
- 总结本周工作进展、未完成任务和重要问题。
- 通过多轮对话追问信息缺口。
- 根据历史目标和当前进度提出下一阶段建议。
- 用户确认后生成并保存周报。
- 将重要决策和项目背景更新至长期记忆。

本阶段打通"数据读取 → 多轮分析 → 人工确认 → 周报保存"的完整闭环，是后续简报与记忆功能的基础。第一版以只读分析和人工确认保存为主，不自动修改计划、备忘等业务数据。

## 阶段二：每日工作简报 + 长期记忆（P0）

- 每日工作简报：
  - 每天开始工作前自动准备简报；采用应用启动或首次进入首页时检查、后台按需生成的方式，不引入常驻守护进程。
  - 整理今日重点、昨日遗留事项和需要关注的重要信息。
  - 必要时结合历史数据给出简短建议。
  - 尽量减少不必要的 LLM 调用；避免重复生成和无效提醒。
- 跨数据源检索与长期记忆：
  - 整合现有业务模块的数据。
  - 支持结构化查询与必要的语义检索。
  - 关联不同模块的信息。
  - 保存长期项目背景、历史决策和用户偏好；**长期记忆以 SQLite 为权威存储，Chroma 仅在需要语义检索时作为辅助索引，第一版不强制向量化**。
  - 支持跨会话使用相关记忆。
  - 避免将全部历史数据无差别传入模型。

## 阶段三：GitHub 集成 + 工程优化（P1）

- GitHub 数据集成：
  - 获取项目提交、PR 等开发活动信息。
  - 结合现有计划与项目目标分析开发进度。
  - 为每日简报和每周回顾提供数据支持。
  - 不简单以提交次数或代码行数判断项目进度。
- 模型调用与成本优化：
  - 支持配置不同的模型 API。
  - 根据任务复杂度选择合适模型。
  - 记录 Token 消耗、延迟和成本。
  - 在保证结果质量的前提下优化调用成本。
- 执行追踪与效果评测：
  - 记录 Agent 的执行过程与工具调用。
  - 建立核心任务的测试样例。
  - 评估总结质量、检索准确性和任务完成情况。
  - 对比优化前后的效果、耗时和成本。
- 分领域 AGENT.md：
  - 为主要业务领域建立独立的 Agent 上下文与规则。
  - 按需加载相关领域的信息。
  - 与项目开发规范文件（AGENTS.md）区分，避免重复和冲突。

共享基础能力（检索、记忆、执行追踪、成本埋点）在本阶段及相关功能开发时合理实现，不重复建设。

## 阶段四：候选功能（P2，未经批准不开发）

- 智能信息分类：
  - 用户通过对话输入信息。
  - AI 判断适合存放的业务模块。
  - 用户确认或纠正分类结果。
  - 保存分类建议、最终选择和纠正记录。
  - 后续根据实际需求决定是否开发。
- 数据仪表盘：
  - 集中展示任务完成情况、项目进度及重要统计信息。
  - 可结合 GitHub 数据展示开发活动。
  - 避免与现有页面功能重复。
  - 暂不开发复杂的独立分析平台。

## 开发工具优化（独立事项，P1）

- Claude-y Comment Detector：纳入开发工具与代码质量优化规划，目标是改善 AI 生成代码注释和技术文档的质量。
- 本阶段仅记录规划，不安装、不集成、不讨论具体使用方式。
- 参考：https://github.com/citelao/dotfiles/blob/main/dotfiles/.chezmoitemplates/skills/claudy-comment-detector/SKILL.md
- 此项为开发工具优化，独立于 Agent 业务功能阶段，不与上述阶段耦合。
