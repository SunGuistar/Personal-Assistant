## 一、仍需要讨论的 6 个产品决策

### 1. Memory 是否应分成两类？

你提出了两种不同的偏好：

- 资讯偏好： 喜欢看什么，例如 AI 模型、Agent 技术、软件工程。
- 行动建议偏好： 希望 Agent 提出什么类型的建议，例如项目开发、学习、职业发展。

我的建议：统一使用一个 Memory 系统，但将两种偏好作为不同的记忆类型。

这样可以同时支持两种个性化行为，也能防止出现“用户喜欢阅读某类新闻，因此 Agent 总建议用户去做相关事情”的错误推断。

阶段目标则不应完全依赖 Memory，而应优先读取现有长期计划中标红的重要目标，对话输入作为补充。若存在冲突，由 Agent 主动询问。

### 2. Agent 应采用编排式多角色，还是 Subagent？

这是目前最值得讨论的架构问题。

| 方案                 | 优势                                     | 局限                           |
| -------------------- | ---------------------------------------- | ------------------------------ |
| 编排式多角色工作流   | 流程稳定、结果可追溯、适合固定的每日晨报 | 临时复杂任务的灵活性有限       |
| 主 Agent + Subagents | 擅长按需委派任务和分工分析               | 可能产生额外协调与结果整合问题 |
| 混合架构             | 同时支持稳定生成和专业分析               | 架构复杂度较高                 |

推荐：编排式工作流为主，必要时允许委派专业 Subagent。

例如资讯分析、昨日回顾可以独立处理，但整个晨报仍由一个明确的生成流程控制。前端只需要一个统一对话框，不必因为有多个 Agent 就设计多个聊天窗口。

### 3. RAG 的具体使用目的是什么？

目前 V0.2 对 RAG 的描述仍过于宽泛。

我建议只围绕两个具体问题评估：

1. 跨来源新闻是否需要语义检索，才能可靠判断不同报道是否属于同一事件？
2. 随着 Memory 与历史记录增加，关键词检索是否会漏掉与用户目标有关的信息？

推荐：V1.0 保留 RAG 式证据检索能力，但不强制引入向量数据库。

如果结构化查询和全文检索已经足够，就没有必要额外引入 Chroma。只有发现明确的语义召回问题时，再引入向量检索。

### 4. Agent 应在什么情况下主动询问用户？

你已经明确：阶段目标优先来自标红长期计划，出现冲突时 Agent 主动询问。

但需要进一步定义什么算冲突，以及是否阻塞晨报生成。

推荐：不阻塞每日晨报。

晨报可以先按照已有高优先级目标生成，同时在右侧对话框显示待澄清问题。用户回答后影响下一次生成；只有直接影响事实正确性的问题，才应阻止相关结论输出。

### 5. 重新生成应支持哪些方式？

你已经取消了普通手动生成，只保留重新生成，并希望尽量使用缓存、局部更新。

我建议分成三个内部行为：

- 直接复用： 输入未变化，显示已有晨报。
- 局部重算： 部分资讯或个人数据更新，仅重算受影响的分析部分，再统一整合。
- 完整重算： 重大数据变化、原报告错误或用户明确要求时执行。

产品界面可以只保留一个“重新生成”按钮，由系统自动判断处理方式。

这里还需决定：局部重算后，是否保留完整历史版本？我建议保留。

### 6. 资讯全文获取失败时怎么办？

你已经决定每小时抓取全文，但仍有一个产品层面的冲突：

如果某条重大新闻只能获取标题和摘要，是否必须将它排除在晨报之外？

推荐不要一刀切。

重大新闻可以依据可靠的标题、来源摘要和其他独立信源进行简要报道，但应标明信息完整度；需要详细分析却没有足够证据的内容，则暂不展开。

这比要求“每条新闻必须成功取得全文”更有利于晨报的可靠性。

## 二、需要 Kimi Code 先验证的 6 个问题

按照你的要求，这一类问题应该持续保留在每轮产品设计 MD 中，直到测试结束并形成结论，不需要你现在凭主观判断选择。

| 编号 | 待验证问题                   | 需要验证什么                                                 |
| ---- | ---------------------------- | ------------------------------------------------------------ |
| T1   | 现有数据库能否还原昨日活动？ | 任务完成时间、状态变化、长期计划、备忘、GitHub 数据是否有可靠记录 |
| T2   | 国内社会新闻源               | 哪些 API/RSS 稳定、支持全文、内容覆盖如何、有无使用限制      |
| T3   | 国际新闻源                   | BBC 等来源在实际运行环境中是否可访问，是否支持全文和稳定更新 |
| T4   | AIHOT 采集机制               | API 是否提供完整资讯、发布时间、热度、来源链接；是否需要额外定时采集 |
| T5   | daily.dev 和 hotai.news      | API 可用性、访问权限、全文获取能力、独特内容价值             |
| T6   | 全文采集可靠性               | 各来源正文获取成功率、去重效果、采集耗时，以及全文缺失对晨报质量的影响 |

其中 T4 和 T6 值得特别关注，因为它们直接关系到你提出的“每小时抓取全部正文”是否合理。

建议这些问题采用统一记录方式：

```
### T1. 现有数据库能否还原昨日活动？
状态：待 Kimi Code 验证

验证目标：
- 数据是否真实存在
- 是否有足够的历史时间信息
- 是否需要补充快照机制

验证结果：待填写
最终决策：待确定
```

## 三、两份文件产生的 7 个新问题

这些问题有些是你修改设计后自然产生的，有些是 V0.2 原本没有明确覆盖的。

| 编号 | 新问题                                           | 推荐解决方案                                                 |
| ---- | ------------------------------------------------ | ------------------------------------------------------------ |
| N1   | 08:00 自动生成的资讯覆盖窗口如何处理迟到数据？   | 固定昨天 08:00 至今天 08:00 为主窗口，迟到的重要新闻在下一次晨报中补录，避免永久漏报 |
| N2   | 08:00 自动生成失败，手动重试是否仍使用固定窗口？ | 使用原定窗口，不随重试时间向后移动；保证同一天晨报的统计口径一致 |
| N3   | 重新生成的缓存应该基于什么判断有效？             | 综合资讯版本、个人数据快照、Memory 版本、报告配置和模型版本判断；缓存应持久化 |
| N4   | 长期计划发生变化时，Memory 是否同步变化？        | 长期计划作为当前目标的主要事实来源，Memory 保存偏好与补充目标，避免复制后两边不一致 |
| N5   | 如何防止同一条新闻被重复介绍？                   | 以事件而非单篇文章作为晨报基本单位；已有事件只有出现实质性进展才再次入选 |
| N6   | 一个对话框具体负责什么？                         | V1.0 主要负责记忆录入、偏好修正、目标冲突澄清；新闻追问和开放式问答放到 V2.0 |
| N7   | 如何判断多角色架构是否确实优于单 Agent？         | 使用同一批资讯和个人数据生成对照晨报，比较事实准确性、相关性、建议质量、稳定性及耗时 |

其中我认为 N3 缓存、N4 目标同步、N7 架构质量评估 应该优先解决。

特别是 N7：既然这一轮明确不再为了省 Token 而选择最简单架构，那么就应该用最终晨报质量来决定是否采用 Subagent，而不是只从架构概念上讨论。

## 四、已经确定、不应该再次讨论的事项

根据 V0.2 修正文档，以下内容可以直接纳入下一版产品设计：

- 每天上午 08:00 自动生成。
- 资讯和昨日总结统一使用昨天 08:00 至今天 08:00 的时间窗口。
- 普通手动生成取消，保留重新生成和重试。
- 自动重试最多 3 次，手动重试不限次数。
- 自动生成使用 DeepSeek，并在调用前严格检查低峰时段；不符合则报错停止，不自动切换。
- 手动重新生成使用 DashScope。
- 模型失败直接报错，不自动切换供应商。
- 中文晨报默认阅读约 5 分钟，信息说明不计入阅读长度。
- 内容分为国内社会、国际社会、AI 三类，Agent 和软件工程作为兴趣方向。
- AIHOT 作为 AI 方向的资讯来源，不用于国内与国际社会新闻。
- 记忆允许推测，但必须经用户确认后才能持久化，并主动提醒。
- 不自动执行 Agent 提出的行动建议。
- UI 使用左右两栏，左侧为主要晨报内容，右侧包含对话框、二级入口和常驻 Agent 信息窗口。
- 偏好设置归入记忆管理。
- 不增加“有用/无用”反馈按钮，通过对话框管理建议偏好。

这些内容如果已经确定，下一版就不应继续占用“待讨论问题”的篇幅。

## 五、我的建议：下一轮优先解决什么？

建议的决策优先级

1. Agent 架构：编排式工作流、Subagent，还是混合模式。
2. Memory 体系：资讯偏好、建议偏好、阶段目标的分类和关联关系。
3. RAG 边界：具体解决哪类检索问题，在什么情况下才需要向量数据库。
4. 资讯采集方式：AIHOT 与其他信源如何协作，全文缺失如何处理。
5. 重新生成机制：如何判断复用、局部重算和完整重算，以及历史版本如何保存。

最后，我建议下一版 V0.3 增加一个独立的 “Kimi Code 待验证事项” 章节，与产品待讨论问题严格分离。

这样产品规划会形成清晰的管理规则：

- 产品设计问题：确定后从待讨论列表移除，结论写入对应模块。
- Kimi Code 验证问题：没有真实验证结论前，始终保留。
- 新发现的问题：标注问题来源、影响范围和推荐解决方案。
- V2.0 功能：只记录方向，不提前设计详细实现。

目前最关键的不是继续增加功能，而是确定如何组织 Agent、如何使用长期记忆，以及如何保证资讯和个人总结的质量。 这三个决策将真正决定今日晨报能否从普通的新闻摘要工具进化为有价值的个人智能助手。
