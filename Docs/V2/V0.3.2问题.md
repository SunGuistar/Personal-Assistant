## 二、新产生的 7 个关键问题

## P1. 故障兜底应该到什么程度？

高优先级

这是 V0.3.1 新增需求中最重要的一项。

目前你已经决定模型超时、拒绝或故障需要处理，但仍没有定义：如果三个 Subagent 中有一个失败，整份晨报是否应该失败？

例如技术研究成功、目标分析成功，但建议 Subagent 超时。

我建议采用分级处理：

- 资讯来源或部分非关键分析失败：继续生成，信息说明中标注缺失。
- 技术研究或目标分析失败：保留已经完成的有效分析，允许缺少相应内容。
- 建议 Subagent 失败：允许不展示今日建议。
- 主 Agent 最终编辑失败：整份晨报生成失败，不发布不完整报告。
- 数据错误或关键事实无法验证：阻止发布受影响的错误内容。

推荐：允许降级生成，而不是任何一个节点失败都导致整份晨报失败。

但需要区分“模型调用失败”和“没有值得输出的内容”，两者不能混为一谈。

### P2. Qdrant 存储架构还有一个缺口

你在 V0.3.1 中确定：

- Qdrant：技术资讯原文、向量检索、历史晨报索引。
- SQLite：正式晨报、Memory、缓存、运行日志与费用。

问题是：国内社会新闻和国际社会新闻的原始数据存在哪里？

目前你的 Qdrant 设计只有两个 Collection：技术资讯、历史晨报。

推荐明确为三类存储

Qdrant

AI 技术资讯全文与语义索引

历史晨报语义索引

SQLite

国内/国际社会新闻原文

正式晨报及版本

Memory、缓存、日志及统计

这样既保留 Qdrant 的全文和语义搜索能力，也不必给暂时不需要语义搜索的社会新闻建立向量索引。

需要注意：历史晨报仍以 SQLite 中的正式版本为准，Qdrant 保存可检索的语义片段。

推荐：这一存储分工可以直接确定。

### P3. 实时日志应该显示到什么程度？

V0.3.1 已经将原来的“Agent 信息小窗口”改为“实时日志”。

这意味着右侧不再只是显示 Token 和耗时，而是要支持查看 Agent 的执行过程。

但如果直接展示每一步底层日志，阅读体验会非常差。

推荐分成两层：

- 默认显示简洁的业务事件，例如“完成资讯筛选”“技术研究开始检索历史资讯”“建议分析完成”。
- 点击事件后展示调用模型、Tool、耗时、Token、缓存命中情况、错误摘要等技术详情。

完整日志写入数据库，供历史查看和调试。

特别需要明确：不建议默认将用户的私人资料、完整 Prompt 或模型内部推理内容直接展示在日志中。

### P4. 重新生成时，哪些操作允许复用缓存？

你已经确定“每个阶段保存结果，有可用缓存就复用”。

这里产生一个新问题：如果某个阶段缓存结果本身存在错误，应该如何重新计算？

例如技术研究 Subagent 的分析结论有误，但输入没有变化。点击重新生成时，系统仍然命中缓存，那么错误就会一直存在。

我的推荐是将缓存复用与用户主动纠错区分开：

| 场景                     | 推荐行为                       |
| ------------------------ | ------------------------------ |
| 自动生成后的正常重新生成 | 优先使用有效缓存               |
| 输入发生变化             | 重算受影响阶段                 |
| 某个阶段发生失败         | 保留其他成功阶段，重试失败部分 |
| 用户明确指出分析错误     | 允许使对应阶段缓存失效         |
| 需要完全重新分析         | 提供完整重算能力               |

UI 不一定需要展示一堆生成模式按钮，可以把高级选项放在“重新生成”的下拉菜单中。

另外，你已经决定每天 08:00 删除上一轮缓存，因此12 小时应当是最长有效期，而不是保证缓存一定保存满 12 小时。

### P5. 历史资讯关联应该出现多频繁？

目前你已经确定：

- 历史资讯不因时间久而降低检索价值。
- 新旧观点冲突时以新观点为主。
- AI 技术资讯的历史关联自然写进“评价”。

但尚未明确：每条 AI 资讯是否都必须检索历史，并写出历史对比？

我的建议是：

技术研究 Subagent 应主动检查历史关联，但不强制每条资讯都展示历史对比。

只有发现以下情况时，才值得写入评价：技术取得实质进展、旧结论受到挑战、同一项目出现新版本，或者历史信息能明显帮助理解当前资讯。

否则直接评价技术本身即可。

这样可以避免晨报为了体现 RAG 能力而强行插入不必要的历史知识。

### P6. Prompt 缓存优化是否会影响 Agent 的判断？

V0.3.1 提出：“Prompt 尽量追加信息，暂时不压缩信息，也不限制 Token 长度。”

这里存在一个需要纠正的技术理解。

保持稳定的 Prompt 前缀有利于服务商的输入缓存命中，但不代表所有历史信息都应该不断追加到 Prompt 中。

否则长期运行后，Agent 可能受到过多旧结论干扰，甚至混淆当前事实与历史背景。

我建议：

- 固定系统指令和角色定义，尽量保持稳定前缀。
- 当前任务、历史检索证据作为动态上下文。
- 不为节省 Token 强制压缩有价值的内容。
- 但仍保留模型上下文窗口限制和相关性筛选。

推荐：以信息质量为优先，不以追求缓存命中率为目标不断堆积历史消息。

### P7. 每日 08:00 生成时，资讯采集和向量索引是否必须全部完成？

此前我们已经解决了“08:00 先采集再生成”的问题。

但现在加入 Qdrant 后，完整流程变为：

```
08:00 最后一轮资讯采集
    ↓
新闻正文获取、清洗、去重、落库
    ↓
技术资讯 Embedding 与 Qdrant 索引更新
    ↓
固定本次晨报的数据快照
    ↓
Agent 工作流开始
```

如果 Qdrant 索引更新失败，是否应该阻塞晨报？

推荐：原始数据落库是必要条件，向量索引更新不应成为整个晨报的绝对阻塞条件。

如果部分新资讯尚未完成向量化，本期仍可根据原始数据库完成新闻总结；历史关联检索可能降级，并在信息说明中标注。

但正式发布前应确保同一份晨报引用的数据快照一致。

## 四、我发现一个值得考虑、但不需要立即增加的功能

晨报内容质量检查。

现在你已经投入了很多精力设计 Agent、Memory、RAG 和历史资讯关联，但它们最终都服务于同一个目标：每天生成一份值得读的晨报。

因此我建议 V1.0 至少支持简单的人工质量检查，不需要开发复杂的评分系统。

例如每次使用时重点观察：是否漏掉重要新闻、AI 评价是否有价值、历史关联是否牵强、昨日总结是否准确、行动建议是否重复。

V2.0 再考虑自动化质量评估与长期推荐优化。

### P9. 质量评价与历史晨报的页面关系

现在顶部有三个二级导航：

```
晨报正文 | 质量评价 | 历史晨报
```

但用户查看某一天的历史晨报时，应该如何访问那一天对应的质量评价？

建议：质量评价始终跟随当前选中的晨报版本。 进入历史晨报后选择某个日期或版本，再切换到质量评价，就展示对应版本的评分。

这样不必为历史评价另设页面。

### P10. 生成过程中的页面显示

每天 08:00 开始采集后，可能需要一段时间才能生成完成。

建议页面明确区分：

- 尚未生成：显示本期生成中，右侧可查看实时日志。
- 已生成：展示正式晨报。
- 生成失败：显示失败原因与重新生成入口。
- 今日尚未生成但有昨日晨报：允许阅读昨日内容，但必须明确标注日期。

尤其是你已经决定 Qdrant 索引失败会阻塞生成，用户需要知道当前停留在哪个阶段。

### P11. 质量评分是否需要设置合格线？

现在已经决定：

- 独立 LLM API 评分。
- 五个维度 + 综合评分 + 自然语言评价。
- 不根据评分自动重新生成。

我建议不设置强制合格线，评分仅用于质量观察和版本对比。

因为单次 LLM 评分存在波动，不能简单认为 80 分一定合格、79 分就不合格。

这条可以直接确定，不必额外设计复杂规则。
