# 今日晨报 V1.0｜产品设计规划

> 文档用途：供产品所有者审阅、讨论和决定产品方向，不是交给开发 Agent 的实施 Prompt。  
> 状态：讨论稿（基于《V0.1 粗略设计》《V0.1.1 补充信息》重新整理）  
> 本轮原则：**先追求产品质量、可靠性与可演进性，不以 Token 成本作为架构选择的首要约束**。

## 一、产品定位

**一句话定位**：个人助手中的每日智能简报——筛选值得关注的外部信息，回顾真实的个人进展，再结合长期目标与兴趣，提出有依据的行动建议。

**用户每天打开后，希望得到三个答案：**

1. **世界发生了什么？** 国内、国际以及 AI / Agent / 软件工程中，哪些事情真正值得关注？
2. **我昨天做了什么？** 哪些事项推进了，哪些仍需关注？
3. **今天我该关注什么？** 新闻与自身目标有什么关系，有哪些值得执行的建议？

**产品边界**：它不是追求资讯覆盖率的新闻门户，也不是替代现有计划管理的待办应用。其优势在于“重要资讯 + 个人上下文 + 有依据的建议”。现有资讯功能不作为依赖，未来可以独立下线。

**V1.0 成功的标准**：用户愿意每天读；内容重要且相关；事实能够追溯；个人总结可信；建议不是套话；每天运行稳定。

## 二、整体体验与信息结构

### 2.1 用户使用流程

- 系统持续采集资讯，先写入今日晨报自己的数据库。
- 每天 **08:00 自动生成**一份中文晨报，作为当天主报告。
- 用户进入“今日晨报”，直接阅读已生成内容，不必等待一次新的生成。
- 用户可手动触发重新生成，或查看历史报告。
- 用户通过“告诉晨报”对话框补充兴趣、目标与不喜欢的内容，并管理被记住的偏好。
- 晨报中支持查看原始来源与解释“为什么推荐给我”。

**报告内容建议顺序：**

1. **开篇速览**：今天最值得了解的 3 件事，一眼抓住重点。
2. **重要资讯**：国内 / 国际 / AI & Agent & 软件工程；重点不是每类平均分配，而是按当天信息价值分配篇幅。
3. **我的昨日**：已完成事项、重要进展、仍未解决的问题；只描述有证据支持的行为。
4. **今日建议**：1–3 条与个人目标或当前事项有关的具体建议，附建议依据。
5. **信息说明**：覆盖时间、来源、生成时间、数据缺失提示；运行耗时及模型用量放在可折叠的技术详情中。

**阅读长度**：建议默认 **约 5 分钟**，允许在重大事件较多时扩展到 8–10 分钟；资讯少时允许更短，不为了凑篇幅制造内容。中文、分节、可扫读，详细内容按需展开。

### 2.2 资讯时间和“昨日”的区别

- **新闻增量范围**：从上次成功生成到本次生成，最长回看 24 小时；首次生成取最近 24 小时。
- **每日 08:00 的新闻覆盖**：默认上一份晨报之后的新消息，不只限制在当天零点之后。
- **昨日总结**：按用户设定时区的“昨天 00:00–今天 00:00”自然日计算，不受新闻增量窗口影响。
- **同一事件新进展**：即便上一份提过，只要出现实质性新进展，可以再次入选，并说明更新点。
- **08:00 自动生成失败**：保留昨日晨报，页面醒目标明今日尚未成功生成，并允许手动重试。

### 2.3 主报告与手动生成

**推荐**：一天以 08:00 的主报告为主；手动生成的版本作为“更新版”保留记录，而不是覆盖历史。若资讯与个人数据没有变化，先提示“没有明显更新”，用户仍可主动强制重生成。

## 三、核心功能设计

### 3.1 外部资讯：从“多来源抓取”走向“值得读的事件”

**内容范围**

| 方向 | 重点 | 候选来源（接入前验证） |
| --- | --- | --- |
| 国内社会 | 重大社会事件、政策与科技动态 | 国内综合新闻 API / RSS、AIHOT 等 |
| 国际社会 | 重要国际事件及其背景 | BBC 等主流新闻来源；建议引入第二独立信源 |
| AI / Agent / 软件工程 | 模型与框架进展、工程实践、开源项目、重要论文 | AIHOT、daily.dev、Hacker News、OpenAI、GitHub 更新、hotai.news |

**产品功能**

- 后台**每小时**检查资讯源，增量更新，失败源不影响其他来源。
- 任何用于晨报的资讯**必须先落入本地独立数据库**；不让生成阶段临时直接搜索一批未留痕的网页。
- 保存新闻的来源、发布时间、链接、标题、摘要、采集时间、已有热度及必要正文；正文仅在来源许可与实际可得时获取。
- 将多平台重复报道归并为一个**事件**，保留多来源和不同视角，而非重复输出多条标题。
- 先按**公共重要性**与**个人相关性**筛选，再撰写摘要；保留一定公共重大事件的曝光，避免完全被兴趣过滤。
- 新闻展示“发生了什么 / 为什么重要 / 为什么与你有关（如有）”，附可访问的原文链接。
- 事实与分析分开：来源能够证明的事实明确标注；不确定信息不包装为确定事实。

**AIHOT 的角色**：优先评估作为现成热点事件、热度与聚合信息的来源，不复制其 UI，也不假定其算法、参与人数口径或 API 权限已完全透明。若使用其结果，完整保留可获得的原始字段与来源链接。具体热度计算和参与者定义待核查后再决定是否直接采用。

**“完整数据落库”的建议解释**：完整保存**从合法渠道实际取得的数据及重要原始字段**，不等于对所有网页强行爬取全文。这样既能保证可追溯，也不会把产品成败押在难以稳定获取的全文上。

### 3.2 我的昨日：真实回顾而不是猜测

**主要来源**：现有计划管理、长期计划、重要信息、随手备忘、阅读管理，以及确实已经接入并有可读取记录的 GitHub 数据。

**输出重点**：昨天完成了什么、哪件事有进展、重要遗留事项、与长期目标的联系；不把简单的任务数量统计当作整个个人总结。

**关键约束**：现有数据库只读。必须先调查它提供的时间字段与历史记录。比如“任务属于昨天”不代表“昨天完成”；无法确认完成时间，就只能说“目前已完成”，不能编造发生日期。

**推荐补充**：今日晨报从上线起独立存储必要的每日数据快照或可验证的聚合结果，为后续回顾提供依据，但不改动原系统数据库。

### 3.3 个人记忆与偏好：让“个性化”真正可控

**V1.0 建议支持三类记忆**：

- **长期稳定**：偏好的领域、排斥的主题、表达风格。
- **阶段目标**：当前工作、学习、项目或求职重点；可设置失效时间。
- **晨报反馈**：例如“这类资讯太浅”“以后多讲实践价值”，影响后续排序和写作。

**录入方式**：独立对话框，用自然语言告诉 Agent；系统提取候选记忆供用户确认后落库。另提供记忆查看、编辑、禁用与删除，避免错误记忆长期污染推荐。

**个性化使用位置**：不只是把用户偏好写进最终提示词，而是在**候选资讯排序、事件解释深度、建议优先级**三个环节均使用。

**记忆来源与隐私**：记忆区分用户明确提供、用户确认的系统归纳；私人数据仅在实现对应功能所必需的范围内传给模型，不默认把旧数据库整库发送出去。

### 3.4 Agent 分析与建议

**主目标**：对事件和个人活动进行交叉判断，而不是把两份摘要机械拼接。

建议的输出形态：

- **优先关注**：重大热点即使与个人兴趣不强相关，仍能进入报告。
- **与我相关**：解释某项新框架、工具或研究成果为什么值得用户了解。
- **可以行动**：当信息确实支持行动时，建议做什么、为什么、优先级如何；不要每天强行生成三条建议。
- **可解释性**：每条关键建议能够指向具体新闻、个人计划、或明确的个人记忆。

**建议不自动执行**：V1.0 不直接修改任务、发送信息或替用户做外部操作。涉及行动仍由用户决定。

### 3.5 生成和运行信息

- **生成时间**：保存总耗时，并能看到主要阶段耗时；目标 60 秒是体验指标，不是保证。
- **模型调用情况**：显示当前阶段、正在使用的模型、调用次数、是否成功。
- **Token 统计**：保留总次数、总 Token、费用；单次输入/输出、缓存命中/未命中、命中率、费用、耗时。API 没返回的字段显示未知，不伪造数字。
- **展示方式**：默认是一条简洁运行状态；鼠标悬浮展示速览，点击弹出有关闭按钮的详情窗。
- **费用的产品定位**：V1.0 作为**透明度与运营观察指标**，而非架构设计的首要约束。必要的防异常重试和失控保护仍应保留。

## 四、重新评估的架构方案（以产品表现为第一原则）

> V0.1.1 的“单 Agent + 确定性工作流、V1.0 不引入 RAG”是上一轮的技术判断。以下为本轮重新评估后的**推荐方案**，并非宣称多 Agent 或 RAG 一定更先进。

### 4.1 Agent 架构：推荐“明确分工的编排式多角色工作流”

**考虑的方案**

- **A. 单 Agent**：一套 Agent 同时筛新闻、回顾个人数据、写报告。简单，但职责多且质量问题难定位。
- **B. 自由协作的多 Agent**：角色可以自主互相委托、反复讨论。灵活，但可预测性和稳定性较弱，不适合每天自动生成的固定产品。
- **C. 编排式多角色工作流（推荐）**：通过一个稳定的流程，分开执行“资讯分析”“个人回顾”“报告编辑与核查”等角色；只在需要语义判断的环节使用 Agent，采集、去重、统计和入库仍由普通程序完成。

**推荐理由**：晨报融合两种不同性质的数据：外部新闻需要跨来源判断重要性与可信度，私人回顾需要严守事实与时间边界，最终编辑要统一语气和篇幅。角色分工有助于独立评估和改进报告质量，也便于未来加入新模块。

**V1.0 的合理边界**：不要求三个角色都必须是独立的自主智能体；可以由同一底层模型承担不同角色。产品先定义角色和工作流，再根据质量评估决定是否将某环节实现成独立 Agent。避免为了“多 Agent”而多 Agent。

**推荐结构**：

```text
定时采集与本地存储（非 Agent）
               ↓
资讯检索 / 事件聚合 —— 个人数据与记忆检索
               ↓                  ↓
         资讯分析角色        个人回顾角色
               └──────┬───────────┘
                      ↓
              晨报编辑与核查角色
                      ↓
               格式化报告与存档
```

### 4.2 RAG：推荐“检索增强能力分层引入”，不一刀切

**为什么需要检索**：资讯、历史晨报、长期记忆和个人事件都需要从本地找到最相关的证据。检索是产品能力，不等同于必须立即部署向量数据库。

**V1.0 推荐**：

- **资讯与事件**：数据库条件检索 + 关键词全文检索 + 时间/热度/兴趣排序；在重复事件合并难以可靠完成时，可以增设语义相似检索。
- **结构化个人数据**：直接查询原业务数据库的相关记录，不应通过向量检索计算确定性指标。
- **个人记忆 / 历史晨报**：先按类型、优先级、时间与关键词检索；若出现自然语言关联不足的情况，再引入 Embedding 语义检索。
- **生成时**：把检索到的证据连同来源 ID 交给分析角色，并在输出中保留引用。

**判断**：V1.0 应当有明确的**RAG 式证据检索流程**；但“统一向量 RAG”不是强制条件。是否上向量检索，由新闻跨来源聚合效果和记忆检索质量决定，而不是 Token 预算决定。

### 4.3 模型策略：保留已明确的产品运行规则

- 正式运行每天 **08:00 自动生成**：DeepSeek-V4.1-Flash-1017（接入时核对服务商正式可用的 API model ID）。
- 开发阶段以及正式运行后的**手动生成**：当前已接入的 DashScope 免费模型。
- 这是用户已明确提出的运行方式，不再沿用旧稿中笼统的“高峰用 DashScope、低峰用 DeepSeek”来覆盖它。
- 模型切换失败时要明确显示故障；是否自动切换供应商仍待讨论，避免无提示改变用户选定的生成方式。

### 4.4 数据架构：推荐“独立存储、只读关联”

- 本模块独立存储原始/规范化资讯、事件、历史报告、个人记忆与调用记录。
- 现有个人助手数据库**只读**，通过受控的数据读取层获得个人活动信息。
- 保留必要的来源元数据和历史报告版本，以支持可追溯、可重现；不必复制现有数据库的全部业务数据。
- 不依赖现有资讯功能。是否继续采用 SQLite，取决于实际采集量和并发写入需求；个人单机版优先保持简单。

## 五、UI 与交互规划

### 5.1 页面分区

```text
今日晨报
┌───────────────────────────────────────────────┐
│ 日期 / 已生成时间         [手动生成] [偏好设置] │
├───────────────────────────────────────────────┤
│ 今日重点  →  重要资讯  →  我的昨日  →  今日建议 │
│                                               │
│ 文章式阅读布局：标题、要点、依据与来源链接     │
│                                               │
├───────────────────────────────────────────────┤
│ Agent 状态：已完成 · 用时 · 模型   [查看详情]  │
└───────────────────────────────────────────────┘
旁侧或二级入口：历史晨报 / 个人记忆 / 调用统计
```

### 5.2 关键交互

- **默认进入**：显示最近一份成功晨报及其日期，不自动触发新的模型生成。
- **生成中**：可看到阶段变化及耗时，避免空白等待；不重复启动同一任务。
- **来源查看**：新闻可打开原始链接；重要建议可查看关联依据。
- **历史记录**：能够查看当天主报告和后续更新版，历史内容不被后续记忆修改覆盖。
- **个人记忆**：对话录入、待确认卡片、记忆列表管理。
- **运行详情**：只在点击时显示完整信息；默认不展示隐私原文及 API Key。

**视觉方向**：接近“高质量的个人日报阅读器”，而非密集资讯卡片平台。技术统计不应喧宾夺主。

## 六、待讨论问题与推荐方案

| 优先级 | 问题 | 推荐方案 | 需要最终确认什么 |
| --- | --- | --- | --- |
| 高 | 多 Agent 是否真的改善质量？ | 采用可分工的编排工作流；通过样例晨报比较单角色与多角色的准确性、关联性和稳定性 | 是否将多角色作为 V1.0 必需能力 |
| 高 | RAG 要做到哪一层？ | 所有内容先做可靠本地检索；向量检索只在事件聚合或记忆召回需要时引入 | V1.0 是否要求语义检索 |
| 高 | 已有数据库能否可靠还原“昨日”？ | 先核查历史时间字段；缺少时明确标注，不推断；从上线起存必要快照 | “昨日回顾”允许哪些数据缺口 |
| 高 | 自动 08:00 生成的时区和失败策略？ | 使用本地设置时区；失败时保留旧稿并显示失败，允许手动重试 | 是否自动限次重试 |
| 高 | 国内新闻源怎么选？ | 首选稳定 RSS / API，至少一主一备；按可靠性、覆盖和授权条件评估 | 国内新闻的主要来源 |
| 高 | AIHOT 热度与参与者数据怎么理解？ | 优先使用其结果但保留来源口径，不把未知字段解释成人数 | 核查后是否直接展示其热度指标 |
| 中 | 是否每小时抓取全文？ | 每小时增量获取可得元数据，重要文章按需获取合法正文 | 哪些来源允许或需要正文 |
| 中 | 5 分钟还是 10 分钟？ | 默认 5 分钟，必要时 8–10 分钟 | 是否允许按内容密度动态调整 |
| 中 | 社会热点与个人兴趣如何平衡？ | 重大公共事件保底、技术资讯按兴趣深化，不做固定平均配额 | 是否设置用户可调的内容偏重 |
| 中 | 用户喜好如何生成？ | 自然语言录入后确认；使用晨报反馈补充，避免无提示永久记忆 | 是否允许从历史行为推测候选记忆 |
| 中 | 手动生成与自动生成关系？ | 自动为主报告，手动生成作为更新版，保留两者 | 是否允许覆盖主报告 |
| 中 | 模型失败时怎么办？ | 不静默切模型；显示原因并允许用户显式选择备用模型 | 是否要自动回退 |
| 中 | 单次和累计 Token 信息放哪？ | 简洁状态栏 + 详情抽屉 + 独立统计页面 | 是否需要常驻小窗口 |
| 中 | daily.dev、hotai.news 是否必接？ | 作为候选适配器，先验证可用性、授权、重复内容和独特价值 | 首版正式接入的来源名单 |
| 低 | 是否给建议添加“有用/无用”反馈？ | V1.0 可用简易反馈，长期自动优化放 V2.0 | 首版是否增加反馈按钮 |

**推荐决策顺序**：先定“昨日数据真实性 → 资讯来源与事件质量 → 多角色评估 → 检索能力 → UI 与篇幅”。不建议先讨论图标、天气和复杂统计图。

## 七、V1.0 与 V2.0 的范围划分

### V1.0 必须具备

- 国内、国际、技术三类资讯的定时收集、独立落库、去重/聚合、可靠来源追溯。
- 每天 08:00 的正式自动晨报与手动更新版；中文版式化阅读和历史记录。
- 从现有数据库只读提取可验证的昨日信息。
- 个人偏好与目标记忆：对话录入、确认、存储、管理、用于内容筛选。
- 检索增强的证据链、分工清晰的分析与编辑流程、事实核查与有依据的建议。
- 简洁运行状态、生成耗时、模型调用与 Token / 费用统计。
- 模块与旧资讯功能解耦；不破坏现有数据库和功能。

### V2.0 优先候选（按产品价值排序）

1. **记忆自动更新与反馈学习**：从长期使用和明确反馈中更新兴趣，支持纠错、时效和冲突消解。
2. **历史行为趋势分析**：结合完整事件日志，识别连续拖延、长期目标推进及阶段变化。
3. **高级语义检索与跨期关联**：在长期历史足够丰富时，跨新闻、晨报和个人活动建立有价值的关联。
4. **语音完整播报**：支持播报控制、阅读同步与失败恢复。
5. **天气、地点、气温、日期等环境上下文**：含天气图标，避免与晨报核心内容争夺首版资源。
6. **个性化内容深度自适应**：根据用户实际阅读与反馈调整技术解释的深浅。
7. **开放式新闻追问和深度研究**：允许基于已保存证据继续提问，必要时触发可追溯的补充研究。

### 暂不作为独立需求

- 自建完整热点指数体系、参与人数推算平台。
- 自由协作且无限循环的多 Agent 系统。
- 为架构复杂度而引入统一向量数据库、知识图谱或微服务。
- 自动执行个人任务、替用户发消息、修改原有业务数据。
- 重建现有资讯聚合 UI 或移动端全套适配。

## 八、建议先观察的产品指标

| 指标 | 衡量的问题 |
| --- | --- |
| 日常晨报生成成功率 | 用户每天能否稳定拿到内容？ |
| 重要新闻来源可追溯率 | 晨报事实能否核查？ |
| 重大新闻重复率与漏报案例 | 事件聚合与筛选是否可靠？ |
| 用户标记“值得读”的比例 | 推荐是否真正有用？ |
| “我的昨日”事实错误数 | 个人回顾是否可信？ |
| 建议被用户采纳或保存的比例 | Agent 是否创造行动价值？ |
| 每次生成耗时 | 体验是否可接受？ |
| 调用次数、Token、缓存、费用 | 运行是否透明、可持续？ |

**总结**：本产品的核心竞争力不是收集最多新闻，也不是使用最多 Agent，而是**用可信的证据，把重要外界变化与用户自己的生活和目标连接起来**。在此基础上，推荐采用可分工、可核查的编排式 Agent 工作流与分层检索能力，先把晨报质量做好，再由实际问题决定是否增加独立 Agent 和向量 RAG。
