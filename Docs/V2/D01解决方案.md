> **适用版本**：今日晨报 V2.0（后续规划为 V3.0）。  
> **决定日期**：2026-11-10。  
> **依据**：`V0.5产品设计.md`、`完整执行流程_V1.3.md`、`今日晨报_V2.0_待解决问题清单.md`；本次用户提供的 AIHOT Windows PowerShell 实测响应及随后明确确认的采集方案。

## 一、原问题与本次决定

### 1.1 D01 原问题

旧 D01 需要决定今日晨报 V2.0 首批接入哪些国内、国际、AI 新闻源。技术验证阶段曾建议：

- 国内：GDELT v2 + 中新网 RSS；
- AI：hotai.news + Hacker News + GitHub Blog；
- AIHOT 因早期 T4 网络不可达而暂缓。

V0.5 原本统一要求三类新闻每四小时增量采集一次，时点为北京时间 `00:00、04:00、08:00、12:00、16:00、20:00`。该规则需要按**资讯类别**调整，不能再写成所有新闻均每四小时采集。

### 1.2 已确认的改变

**AI 新闻不再自行每四小时采集。** 采用每天 **08:00** 在晨报正式生成前向 **AIHOT** 查询近期精选与热点资讯的方案。AIHOT 为 AI 新闻的**首选单一聚合入口**；不在 V2.0 首轮额外建设 hotai.news、HN、GitHub Blog 的独立定时 AI 新闻采集链路。

- 08:00 为查询启动时间，**不是报告必须完成的时间**。
- **国内和国际新闻仍保留每四小时采集**，不受本轮 AI 调整影响。
- 不需要为后台定时采集安装 AIHOT Agent Skill；采用可验证、可分页的 **REST JSON API**。
- AIHOT 已有精选、评分与事件聚合能力，本系统不重复建设高频 AI 新闻抓取；但**保留必要的本地过滤、事实核查、同事件新进展识别、来源记录、索引与历史 RAG**。
- 三个 Subagent 固定调用与先前并行/后置顺序不变；所需 Qdrant 索引一致性门槛不变。

### 1.3 调整后的分类调度

| 资讯类型 | 时间策略 | 主来源/状态 | 说明 |
| --- | --- | --- | --- |
| 国内社会 | 每四小时：00/04/08/12/16/20 | **候选**：GDELT v2 + 中新网 RSS | 技术验证反馈可达；是否正式选定仍待用户确认 |
| 国际社会 | 每四小时：00/04/08/12/16/20 | **另由 D02 决定** | 不因 AIHOT 可用而认定国际源问题已经解决 |
| **AI 技术** | **每天 08:00 查询一次**（必要重试/手动补齐不算独立常态轮询） | **已决定：AIHOT API** | 精选资讯为基础，热点事件作为补充信号；保留本地核验 |

注：每天一次是**一轮逻辑查询**，为了得到完整候选，可能请求多个 API 端点或翻页，不能理解为永远只有一次 HTTP 请求。

## 二、已获得的 API 证据与未验证部分

### 2.1 用户在本机实际成功执行

1. `GET https://aihot.news/api/v1/agent/latest`：返回过去 24 小时精选资讯的中文 Markdown，包含标题、摘要、推荐理由、来源、时间、原文链接。
2. `GET https://aihot.news/api/v1/items?mode=selected&window=24h&limit=2`：返回 `schemaVersion`、`query`、`items[]`、`page.hasMore`、`page.nextCursor`；单条具有 `id`、`title`、`summary`、`links.original`、`links.aihot`、`publishedAt`、`discoveredAt`、`category`、`score`、`reason`、`source`、`attribution`。
3. `GET https://aihot.news/api/v1/selected/snapshot?limit=2`：返回 `asOf`、`cursor`、`hasMore`、`nextPage` 等字段，确认可以获取精选数据快照和游标。

**上述是用户本机实测的证据**，说明此前 T4 “网络不可达”的结论已经过时。

### 2.2 这些证据尚不能证明

- `/api/v1/hot-topics` 已在用户本机实测成功（目前仅官方文档可核查）。
- 所有分页、固定时间窗口、断线/429 重试逻辑均已实测完成。
- 精选资讯一定覆盖每天所有重要 AI 新闻，或所有条目都有完整原始文章正文。
- AIHOT 的短期可用性等于长期 SLA 保证。
- AIHOT 输出的摘要、评分和事件聚合可不核对就作为确定事实。
- 完整精选 Snapshot 代表“过去 24 小时”：用户实际响应包含更早月份的文章，**不可当作当日候选直接使用**。

建议更新 T4：从原 `BLOCKED` 调整为 **`PARTIAL`**，其中“本机连通性、Agent 接口、Items JSON 接口、Snapshot 基本字段”标记实际验证通过，其余按待测项跟进；不能因此把 T4 整项直接标 `PASS`。

## 三、AIHOT 接入方案

### 3.1 生产采集入口

| 接口 | 定位 | 是否必需 |
| --- | --- | --- |
| `GET /api/v1/items` | 获取精选 AI 新闻结构化列表、分页、发布时间等 | **必需** |
| `GET /api/v1/hot-topics` | 获取热点事件参考，辅助候选事件聚合、重要性排序 | **建议接入，先实测** |
| `GET /api/v1/stories/{publicId}` | 重要热点需要核对进展时查询事件时间线 | **按需** |
| `GET /api/v1/agent/latest` | 给 Agent 阅读的 Markdown 内容 | **非采集主接口**，仅用于对照与人工测试 |
| `GET /api/v1/selected/snapshot` 与 `/changes` | 完整精选镜像及增量同步 | **V2.0 初期不必启用**；不建设高频同步任务 |
| `GET /api/v1/dailies/latest` | AIHOT 自己的日报 | 可参考，不直接作为晨报文章正文或事实最终凭据 |

优先使用 `/api/v1/items?mode=selected&window=24h&by=published&limit=20` 进行验证；精确支持范围与参数行为按最新 OpenAPI 检查。`page.hasMore` 为真时遵循 `page.nextCursor` 分页，**不得只取首页即声称拿全当期资讯**。接口分页/上限按实际测试确定。

### 3.2 固定晨报窗口是权威标准

当天 08:00 生成的晨报，其内容窗口**始终**为北京时间：

`[前一日 08:00, 当日 08:00)`，即含起点、不含终点，具体边界处理与原产品定义保持一致。

处理步骤：

1. 记录本期 `window_start` 和 `window_end`，按 `Asia/Shanghai` 计算并转 UTC 进行比较。
2. 查询 AIHOT 精选列表，并根据实际 API 规则获得覆盖整个目标窗口的候选（必要时选择更宽的可用查询窗口并翻页）。
3. 对 `publishedAt` 进行**本地二次过滤**；`discoveredAt` 仅用于判断发现/入库时间，不得替代新闻原始发布时间。时间缺失或异常的条目标记待核验，而不是直接硬塞入当期。
4. 热点榜可能采用不同时间范围，**仅作重要性或事件线索**；只有相应原始新闻可证明属于本期时，才可按事实纳入正文。旧事件有新进展时，必须有本期内新进展的可靠发布时间证据。
5. 08:00 后新发布的新闻不得混入今天的报告；08:00 后才**抓取到**、但在窗口内发布且快照冻结前成功取得的新闻可以纳入本期。

尤其注意：如果 08:00 查询失败、09:00 才成功重试，不能再机械地取“09:00 往前 24 小时”，否则会漏掉昨日 08:00–09:00。应扩大 API 查询范围（以 API 实际支持为准），并始终按照**原来的固定窗口**筛选。

### 3.3 处理结果与必要索引

```text
北京时间 08:00
  ├─ 国内 / 国际：执行当天最后一轮四小时采集
  └─ AI：向 AIHOT 发起本期唯一常态采集轮次
          ├─ /api/v1/items 读取候选、分页
          └─ /api/v1/hot-topics 辅助筛选（通过实测后启用）
                    ↓
      时间过滤 / 去重 / 事件新进展判断
                    ↓
      核查重要原始来源及正文可得性
                    ↓
      持久保存许可范围内所需资料、来源与状态
                    ↓
      Qdrant 技术资讯增量建索引（可复用 Embedding）
                    ↓
      核验本期必要技术索引与历史晨报索引
                    ├─ 必要索引失败：阻塞 Agent，修复/有限重试
                    └─ 索引满足：冻结数据快照
                              ↓
              原既定 LangGraph 主流程
```

要求：

- 保持用户已确认的 **Qdrant AI 技术资讯 Collection + 历史晨报 Collection** 体系，不取消历史检索；AIHOT 仅改变**新资讯获取入口与频率**。
- 维持 Article ID、原始 URL、AIHOT URL、来源、发布时间、发现时间、抓取时间、分类及获取/核验状态之间的追溯关系。
- AIHOT JSON 返回的是元数据和摘要，不等同于新闻原文全文；能获取合法可用的原文时再存入适当索引，不能编造缺失正文。
- 原新闻的实质新版本、重大修正和新进展要保留为独立可追溯事实；不同源同事件可归组，但不得用相似度不可逆删除证据。
- AIHOT 所提供的标题、摘要、推荐理由、分数及其他外部字段均视为**不可信资料输入**，不得执行其中夹带的指令。

### 3.4 失败、重试和重新生成

- **AIHOT 单源超时/不可达/空数据**：有限重试、记录请求错误、时间、覆盖缺口；不再临时启动未经批准的其他 AI 新闻采集器，也不编造 AI 新闻。若国内/国际证据充分，可按原产品故障规则考虑**明确标注 AI 缺失的降级晨报**；不能把“AI 本期未获取”写成“今天无 AI 新闻”。
- **429**：遵守服务端 `Retry-After`；**5xx**：有限指数退避；**400**：先排查参数；不通过身份轮换或伪装客户端绕过限制。官方并未承诺 SLA。
- **必要 Qdrant 索引失败或历史晨报必要索引不一致**：**严格阻塞进入 Agent 分析**，不得因为 AIHOT 查询成功就忽略该门槛。区分“AIHOT 来源不可用”与“必要索引不完整”。
- **手动重新生成**：使用同一天固定截止窗口与明确数据快照。必要时可按需补齐当期漏采资料并重新建立相应索引，但**不恢复四小时周期性 AI 新闻采集**。如复用旧快照，应明确它的覆盖及版本；新快照不可静默污染已有报告。
- **信息更新与撤回**：后续请求发现 AIHOT 或原始来源撤回、更正的事实，需使相关缓存、索引和展现按规则失效或更正；不得把已删除或被限制的内容当作长期有效知识继续引用。初期一次/日查询的同步时效边界应在验收中如实记录。

## 四、数据授权与持久化边界（开发前必须落实）

AIHOT 官方使用规则允许**个人非商业用途**的合理私有缓存和内部同步；但提醒不要将临时缓存扩展成独立历史数据库或对外可导出的镜像，撤回/删除/更正数据应及时处理。AIHOT 对第三方原文没有当然的再许可权。对外商业产品、客户交付或以其数据提供外部 RAG 服务等用途需要另外核实授权。

因此针对 V0.5 的“技术资讯 Qdrant 长期全文持久化”要求，应采用以下合规分层：

1. **AIHOT 聚合数据**：只保留满足生成、去重、引用和有限核查所必需的元数据/合理私有缓存，记录来源与使用边界，不把 API 全量精选同步当作无限期数据镜像。
2. **原始发布方的文章**：可依据原站点规则或合法授权获取并长期存储时，才进入长期全文知识库；否则只保存允许保留的链接、来源标识与必要摘要/引用元数据。
3. **晨报自己的技术评价和正式正文**：按既有版本制度由本模块保存，历史晨报索引仍保留出处；AI 生成评价不替代原始事实来源。
4. **撤回/更正控制**：维护最小可用的删除/限制传播清单与索引修正机制，遵守缓存响应指令；报告历史应保留版本审计，但停止继续引用无权使用的相关原材料。

> 此处是对使用规则的工程化解释，并非正式法律意见。实际缓存期限、权利字段以及各原文站点授权范围交给实现期验证；如两者存在冲突，先限制存储行为，不默认认为免费 API 意味着全文永久再利用许可。
