# 个人助手产品需求文档（PRD）

版本：v0.2（已含用户决策 D1–D8）
状态：待审核
定位：个人助手 —— 面向个人使用的轻量级、本地优先的个人信息与事务管理平台。
版本范围：本文档定义 **V1.0** 的需求、非目标与验收；V1.0 之后的需求统一维护在 `Docs/ROADMAP.md`。

## 1. 产品概述

### 1.1 定位

个人助手是运行在 Windows 本地的个人管家系统，以网页为交互界面，统一管理微信聊天分析、技术资讯、计划与阅读四类信息。

### 1.2 核心原则

| 原则 | 含义 |
|---|---|
| 个人使用优先 | 单用户，不做多用户、权限体系、商业化功能 |
| 低资源消耗 | 减少 LLM Token、Embedding 调用、存储与后台占用 |
| 本地优先 | 第一版全部运行在 Windows 本地，核心数据存本地 |
| 成熟方案优先 | 复用现有项目代码（微信 Agent）与成熟开源组件 |
| 可靠性优先 | 测试、数据安全、异常处理、可维护性高于功能数量 |
| 易用性优先 | 简约美观的网页 + 桌面一键启动 |
| 长期可扩展 | 架构支持未来移动端，前后端彻底分离 |

### 1.3 非目标（第一版明确不做）

- 多用户、账号体系、权限管理
- 微服务、消息队列等复杂基础设施
- Electron 桌面壳（用浏览器即可）
- AI 自动规划、复杂提醒、多人协作
- OCR、AI 笔记总结、云记实时同步/双向编辑
- 局域网/公网暴露、远程访问（仅架构预留）
- 为每篇新闻调用 LLM 生成摘要
- **自动备份与恢复系统**（V2.0 已确定需求，见 `Docs/ROADMAP.md` 与 §4；第一版以 §2.6 数据操作安全规范替代保障）

### 1.4 已确认的关键决策（后续开发以此为准）

| 编号 | 决策 |
|---|---|
| D1 | 第一版不实现备份/恢复功能；不做最小备份服务；破坏性操作以隔离副本规范替代（§2.6）；备份恢复规划为 V2.0（`Docs/ROADMAP.md`） |
| D2 | 所有总结请求统一经过现有 Agent 工作流，由 Agent 调用 `summarize_chat` 工具触发；禁止 Service 直调 `run_summary` 的旁路 |
| D3 | `LangGraph/`、`GetWechatInfo/`、`Tool/` 迁移至 `app/wechat_agent/` 已批准，阶段 3 分步实施，不再征求意见 |
| D4 | 原始快照库与归一化库均纳入 7 天待清理，与 Chroma 关联管理；所有删除必须经周日人工审核逐项确认，绝不自动删除 |
| D5 | 允许自动启动用户配置的 WeChatDataAnalysis 桌面程序；EXE 路径在设置中配置，后端仅启动经配置与校验的程序 |
| D6 | 资讯第一版使用少量高质量默认来源（官方 API/RSS/成熟开源方案），后续允许用户增删 |
| D7 | 阅读管理采用 PDF/PNG 文件关联方案；真实样例文件在阶段 2 验收前提供 |
| D8 | 普通问答默认不额外导出 Markdown；总结报告与用户主动保存的问答长期保留；兼容现有 Output 文件，未经确认不清理 |

## 2. 模块需求

### 2.1 微信聊天助手

#### 复用现状（已确认实现，见代码审查）

- WeChatDataAnalysis 本地 API 客户端（`app/wechat_agent/data_api/wechat_data_api.py`）
- 原始消息快照库（`app/wechat_agent/data_api/message_store.py`，幂等 upsert）
- 消息归一化（`app/wechat_agent/structured/structured_message.py`）+ 归一化脚本（`data_api/normalize_snapshot.py`，阶段 3.4 重建）
- LangGraph 问答 Agent（8 个只读工具）
- 确定性总结流水线 map/reduce/final（`app/wechat_agent/chat_tools/summarizer.py`）
- Chroma 语义检索 + DashScope Embedding + 增量索引（`app/wechat_agent/normal_tools/rag_store.py`）
- HTML/PNG 日报渲染

#### 需求功能

**主交互为对话式**：页面主体是一个对话框，用户输入自然语言（如"总结昨天的聊天""这周谁最活跃"）后进入 Agent 流程，由 Agent 自主决策调用工具（取数、统计、检索、总结）完成回答，不依赖用户先填表单。

1. 对话窗口：
   - 流式输出回答（SSE）；多轮追问上下文保持（会话级历史，存服务端，见 ARCH §5.1）。
   - 对话框提供 3 个点击即发送的预置快捷输入（chips）：
     1. "总结今天的馨馨子钻粉群的聊天记录"
     2. "今天的馨馨子钻粉群是否有人表达过对主播的担忧？"
     3. "列出今天说话最多的十个人"
     预置文案中的群名跟随当前库中的群（默认取最近同步的群），不写死在代码里，群变更时自动替换；快捷输入发送后与普通输入走完全相同的 Agent 流程。
   - 群聊、日期、时间范围等参数通过对话指定（群名由 Agent 用 list_chats 解析，日期支持"今天/昨天"等相对说法，由现有系统提示词机制处理）。
   - **总结请求统一经 Agent**（D2）：由 Agent 决策调用现有 `summarize_chat` 工具触发确定性流水线；对话中内联显示执行状态（如"正在生成报告…"），完成后给出报告链接/卡片，可在页面内查看历史报告。
   - 数据缺失时（如该日期未同步），Agent 明确告知并提示先同步，不编造。
2. 对话上方保留轻量辅助区（非必填流程）：一键同步按钮（含 WeChatDataAnalysis 运行状态检查）、同步执行进度、当前库实际数据时间范围展示。
3. 一键同步（D5）：检查 WeChatDataAnalysis 是否运行 → 未运行则启动设置中配置的桌面程序并等待 API 就绪 → 增量拉取新消息 → 清洗归一化 → 写入 SQLite → 增量向量化（已有向量不重建）。
4. 同步不重复导入消息、不重复向量化（依赖主键幂等、sync_cursors 游标与 rag_state 增量机制，游标设计见 ARCH §3.1）。
5. 外部程序启动失败、API 超时、数据不足时：同步按钮处给出清晰错误；对话中的请求则由 Agent 返回可理解的失败说明。

#### 约束

- 语义检索、RAG、Embedding、Chroma 逻辑直接复用，不重写。
- **总结统一经 Agent（D2 铁律）**：快捷按钮与普通输入同通道；Service 层只做 Agent 调用封装（SSE）、任务状态、报告管理与接口适配；保留现有总结行为与提示词约束，任何修改必须过回归测试。
- 只读原则不变：Agent 工具层保持 SQLite `mode=ro`；不触碰 WeChatDataAnalysis 管理的原始数据库。
- 总结等长任务异步执行，提供任务状态查询；失败有明确错误信息。
- 问答记录按 D8 处理：默认不落 Output Markdown；会话历史存应用库。

#### 已知缺口

（阶段 3 已全部解决：`normalize_snapshot.py` 于 3.4 重建并与历史库对拍一致；多群于 3.5 支持，按 chat_id 过滤；`index_exists()` 兼容性 bug 于 3.0 修复。）

### 2.2 技术资讯（外部导航，2026-11 产品调整）

> 历史决策：第一版曾实现自建资讯聚合（HN/RSS 抓取、去重、评分、收藏/已读、本地存储，提交 `437db29`），产品评估后改为直接链接成熟的第三方资讯网站——不再自行维护抓取、评分、存储与清理。历史新闻表 `news_sources`/`news_items` 按保守策略保留在库中（停止写入、不删除），不参与任何清理流程。

#### 范围

人工智能与大模型、AI Agent、软件工程、Python/TypeScript 技术、AI 编程工具、热门开源项目、重要产品/框架更新——以上内容由外部资讯网站提供，个人助手只做统一入口。

#### 默认导航网站（D6 替代）

| 网站 | 地址 | 主要用途 |
|---|---|---|
| daily.dev | https://daily.dev/ | 软件工程、开发工具、AI 开发 |
| LLM Digest | https://www.llm-digest.com/ | LLM、Agent 工程及工具链 |
| HotAI.news | https://hotai.news/ | 中文 AI 新闻及热点 |
| Edition | https://edition.cafe/ | Hacker News、GitHub Trending、RSS 聚合 |

导航配置为前端静态清单（`web/src/lib/newsNav.ts`），不建数据库存储；站点可用性以用户实际网络为准（开发网络下 LLM Digest 未连通，已如实报告，未擅自替换）。

#### 前端功能

- 资讯页（`/news`）：卡片式展示各网站（名称、简介、favicon、打开按钮），点击新标签页打开（`target="_blank" + rel="noopener noreferrer"`），禁止 iframe 嵌入。
- 首页"技术资讯导航"：展示主要入口，点击进入外部网站；不调用任何新闻 API，不影响其他模块。
- 响应式：桌面网格布局，手机宽度可用。

#### 明确不做

新闻抓取/解析/去重、热度评分与排序、自动/手动刷新、收藏/已读状态、RSS 源管理、新闻过期清理（取消原 7 天清理需求，阶段 5 不涉及新闻数据）。

### 2.3 计划管理

#### 长期计划

新建/修改/删除；字段：标题、描述、状态（进行中/已完成/已搁置）、目标日期；查看关联每日任务。不显示完成进度。

#### 每日计划

按日期查看；任务的增删改；标记完成/未完成；调整顺序（手动排序，仅针对当日任务）；关联长期计划；未完成任务手动移至下一天；查看历史日期。

**"未完成延续显示"语义（已确定）**：某日视图 = 当日任务 + 更早日期未完成的任务（逾期任务自动延续显示，前端单独分区展示、不参与当日排序）；已完成的任务只在其归属日期显示，之后日期不再出现；任务完成状态不变更归属日期（`task_date` 不变，无副本）。

**"移至下一天"语义（已确定）**：移动 = 任务归属日期变更为目标日期，原日期视图不再显示该任务；任务记录 `moved_from_date` 保留来源可追溯；不复制副本（避免重复任务）。

#### 持久化

- SQLite（新应用库），SQLAlchemy + Alembic 迁移。
- 永久保存，不参与 7 天清理。
- 页面修改立即持久化，刷新/重启不丢失。

### 2.4 阅读管理

#### 书籍管理

增删改；字段：书名、作者、备注、阅读状态（待读/正在读/已读）；按状态筛选；正在读列表。

**删除规则（已确定）**：存在一条或多条关联笔记的书籍**禁止删除**——后端 Service 层在删除事务内检查 `book_notes`，存在则返回 HTTP 409（错误码 `book_has_notes`）；用户必须先主动删除该书的全部笔记，才能删除书籍。不采用级联删除，不采用自动解除关联；后端约束独立于前端校验，绕过前端直接调用 API 同样被拒绝；删除被拒绝时书籍记录与笔记文件均保持不变。

#### 读书笔记（云记导出文件关联，D7）

1. 用户在云记导出 PDF/PNG 等文件。
2. 前端上传至个人助手。
3. 后端存放到受管理目录 `data/reading_notes/<book_id>/`。
4. SQLite 保存书籍 ↔ 笔记文件关联。
5. 前端点击即可查看（浏览器直接预览 PDF/图片）。
6. 支持格式以实际云记导出验证为准（**阶段 2 验收前用户提供 1–2 个真实导出样例**）。

#### 暂不做

OCR、AI 总结、云记实时同步、双向编辑。

### 2.5 数据保留与人工审核清理（核心需求，D4）

#### 保留策略

| 数据类型 | 规则 |
|---|---|
| 微信聊天缓存——归一化库消息 | >7 天进入待清理 |
| 微信聊天缓存——原始快照库消息（D4） | >7 天进入待清理（与归一化库同一候选、同一确认） |
| 对应 Chroma 向量 | 随消息关联清理（chunk 处理策略见 ARCH §3.4） |
| 微信 AI 总结报告 | 长期保留 |
| 长期计划 / 每日计划 | 永久保留 |
| 书籍及阅读状态 | 永久保留 |
| 读书笔记 | 永久保留 |

7 天是"进入待清理"条件，不是自动删除期限。**任何数据不经人工勾选确认不得删除；系统任何位置不得提供自动删除入口。**

#### 每周日审核流程

1. 每周生成一次清理候选清单（周日应用运行时生成；周日未运行则下次启动时补生成，同一审核周不重复生成）。
2. 用户打开应用看到待清理提醒（首页横幅 + 独立审核页）。
3. 审核界面展示：数据类型、名称/描述、日期范围、数量、预估释放空间、勾选状态。
4. 用户操作：查看全部、按类型筛选、单选/取消、全选/取消全选、确认删除、暂时跳过。
5. 默认全部不预选；删除前二次确认，明确显示实际删除数量与范围。
6. 跳过 ≠ 同意删除；未审核数据始终保留；跨周候选处理规则见 ARCH §3.4（同一数据不会同时出现在多个未完结审核中）。

#### 删除一致性（D4）

- 删除微信消息 = 归一化库删除 → Chroma chunk 处理（全命中删除 / 部分命中局部重建，策略见 ARCH §3.4）→ 原始快照库删除；不动 WeChatDataAnalysis 原始库；不误删总结报告。
- SQLite 与 Chroma 无跨库原子事务 → 采用**逐项状态机**（pending → normalized_deleted → chroma_done → snapshot_deleted → done / failed），每步落库可重试，失败可从断点继续。
- 清理审计记录：时间、类型、数量、结果、失败原因；**审计日志不记录被删聊天内容本身**。

#### 备份与恢复（D1：第一版不实现）

- 第一版**不开发**备份 API、备份页面、自动备份与恢复流程；备份与恢复为 **V2.0 已确定需求**（§4、`Docs/ROADMAP.md`）。
- 保留未来备份架构设计说明（ARCH §6），但不作为第一版开发任务。
- 不实现备份不代表可以随意操作真实数据：第一版以 §2.6 数据操作安全规范作为替代保障。

### 2.6 数据操作安全规范（D1 配套，强制）

- 开发、调试、数据库迁移、破坏性测试**必须使用隔离的数据副本或临时测试数据库**，禁止直接修改唯一一份现有聊天数据（原始快照库、归一化库、Chroma 目录）。
- 测试用数据副本由脚本/Fixture 生成或复制，测试结束可丢弃；禁止测试代码出现真实库路径的写操作。
- 如确需对真实数据库执行不可逆操作，必须**先明确告知风险并取得用户批准**。
- 现有 `Output/` 下的历史报告与问答文件（D8）：兼容保留，未经用户确认不得清理或删除。

## 3. 前端与体验

### 3.1 技术栈

React + TypeScript + Vite + Tailwind CSS + shadcn/ui + TanStack Query（均为成熟主流方案，无更优替代，按默认采用）。

### 3.2 页面

首页工作台、微信聊天助手、技术资讯、计划管理、阅读管理、数据清理审核、基础设置。

首页展示：今日计划及完成度、最新资讯、聊天总结快捷入口、正在读的书、系统状态与待办提醒（含待清理提醒）。

视觉：简约、美观、易用；避免复杂动画与信息堆叠。响应式布局，兼容桌面与手机浏览器（未来移动端的基础）。

### 3.3 Windows 一键启动

双击桌面快捷方式 → 检查/启动 FastAPI 本地服务 → 等待就绪 → 打开默认浏览器 → 首页。用户无需手动执行任何命令。正式运行使用构建后的 React 静态资源，由 FastAPI 托管（默认端口 8620，可配置，见 ARCH §3.5）。

## 4. 未来移动端与 V2.0（架构约束）

> 权威规划见 `Docs/ROADMAP.md`；本节仅说明 V1.0 必须遵守的设计约束与演进方向，不包含 V1.0 任务。移动端为 **V2.0 已确定需求**（手机访问、必要的身份认证与安全连接）；具体形态（PWA / 手机浏览器访问电脑端服务 / 独立移动客户端）待 V2.0 启动时评估。

- 前后端彻底分离，所有业务经后端 API；前端不直连数据库、不执行系统命令。
- 后端默认监听 127.0.0.1（第一版不对外开放）。
- 演进方向（V2.0 设计约束级）：局域网访问 → 认证（Bearer Token）→ HTTPS（反向代理/自签）→ 移动端数据同步（SQLite 单写者约束下的同步服务）。
- **备份与恢复系统为 V2.0 已确定需求**（D1）：覆盖 SQLite（hub.db + 聊天两库）、Chroma、笔记附件与应用配置；与移动端同步服务一并设计，详见 `ROADMAP.md`。
- 禁止采用阻碍移动端复用的设计（如把业务逻辑写进桌面脚本、接口依赖 Windows 特有对象）。

## 5. 验收标准（概要）

各阶段详细验收见 `DEVELOPMENT_PLAN.md`，关键端到端验收：

1. 双击快捷方式 → 浏览器打开首页，无需命令行操作。
2. 新建/修改每日计划 → 刷新页面 → 数据仍在。
3. 修改书籍状态 → 重启应用 → 状态保持。
4. 打开技术资讯导航 → 各网站入口新标签页正常打开。
5. 同步微信聊天 → 在对话框触发总结（含点击快捷按钮）→ 查看报告；重复同步不产生重复消息与重复向量。
