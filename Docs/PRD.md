# 个人助手产品需求文档（PRD）

定位：个人数据驱动的智能工作助手——整合计划、备忘、重要信息、阅读记录及未来接入的 GitHub 等个人数据，利用 AI 进行信息整理、关联分析、总结和建议；面向个人使用的轻量级、本地优先平台（Windows PC，浏览器访问，单用户）。
本文档是**产品需求与业务规则的权威来源**；技术设计见 `Architecture.md`，开发进度见 `DEVELOPMENT_PLAN.md`。

## 1. 产品概述

### 1.1 核心原则

| 原则 | 含义 |
|---|---|
| 个人使用优先 | 单用户，不做多用户、权限体系、商业化功能 |
| 低资源消耗 | 减少 LLM Token、Embedding 调用、存储与后台占用 |
| 本地优先 | 全部运行在 Windows 本地，核心数据存本地，默认仅监听 127.0.0.1 |
| 成熟方案优先 | 复用现有微信 Agent 代码与成熟开源组件 |
| 可靠性优先 | 数据安全、异常处理、可维护性高于功能数量 |

### 1.2 非目标

- 多用户、账号体系、权限管理；微服务、消息队列等复杂基础设施
- 移动端/平板适配（当前版本仅面向 PC 浏览器；移动端为 V2.0 需求）
- 局域网/公网暴露、远程访问（仅架构预留）
- AI 自动规划、复杂提醒、多人协作；OCR、AI 笔记总结
- 为每篇新闻调用 LLM **生成**摘要（仅翻译来源已有的标题/摘要）
- **自动备份与恢复系统**（V2.0 需求；当前以 §5 数据操作安全规范替代）

### 1.3 已确认的关键决策（后续开发以此为准）

| 编号 | 决策 |
|---|---|
| D1 | 不实现备份/恢复功能；破坏性操作以隔离副本规范替代（§5）；备份恢复为 V2.0 需求 |
| D2 | 所有总结请求统一经 Agent 工作流，由 Agent 调用 `summarize_chat` 工具触发；禁止 Service 直调 `run_summary` 的旁路 |
| D3 | 微信模块（原 LangGraph/GetWechatInfo/Tool）迁入 `app/wechat_agent/`（已完成） |
| D4 | 原始快照库与归一化库均纳入 7 天待清理，与 Chroma 关联管理；所有删除必须经人工审核逐项确认，**绝不自动删除** |
| D5 | 允许自动启动设置中配置的 WeChatDataAnalysis 桌面程序；后端仅启动经配置与校验的 exe |
| D6 | 资讯使用少量高质量默认来源（官方 API/RSS），后续允许用户增删 |
| D7 | 阅读管理采用 PDF/PNG 文件关联方案；真实样例文件验收前由用户提供 |
| D8 | 普通问答默认不额外导出 Markdown；总结报告与用户主动保存的问答长期保留；兼容现有 Output 文件，未经确认不清理 |
| D9 | GitHub 数据接入采用官方 REST API，不引入 GitHub MCP（未来 Agent 需要自主查询时再评估）；贡献统计为 Personal Hub 本地口径，非 GitHub 官方 Contributions |

## 2. 模块需求

### 2.1 微信聊天助手

**主交互为对话式**：用户输入自然语言（或点击预置快捷输入）后进入 Agent 流程，由 Agent 自主决策调用工具（取数、统计、检索、总结）完成回答。

- 对话窗口：SSE 流式输出；多轮上下文保持（会话历史存服务端）；提供 3 个预置快捷输入，其群名跟随当前库中的群（不写死，群变更自动替换），点击后与普通输入走完全相同的 Agent 流程；群/日期/范围由对话指定（相对日期由提示词机制处理）。
- 总结请求统一经 Agent（D2）：由 Agent 决策调用 `summarize_chat` 工具触发确定性流水线；对话中内联显示执行状态，完成后给出报告卡片；数据缺失时明确告知并提示先同步，**不编造**。
- 一键同步（D5）：检查 WeChatDataAnalysis 是否运行 → 未运行则启动已配置程序并等待 API 就绪 → 增量拉取 → 清洗归一化 → 写入 SQLite → 增量向量化（已有向量不重建）。同步不重复导入消息、不重复向量化；外部程序启动失败/API 超时/数据不足时给出清晰错误。
- 约束：语义检索、RAG、Embedding、Chroma 逻辑直接复用不重写；Agent 工具层 SQLite `mode=ro` 只读；不触碰 WeChatDataAnalysis 管理的原始数据库；长任务异步执行；问答记录按 D8 处理。

### 2.2 技术资讯（近期热门 TOP 10 + 外部导航）

- 范围：AI/大模型、Agent、软件工程、Python/TypeScript、AI 编程工具、热门开源、重要产品更新。页面命名"近期热门资讯 TOP 10"——指从指定来源综合筛选的热门推荐，不代表全网实时热度。
- 来源：默认 7 个已验证来源（HN 官方 Algolia API、GitHub Blog、Python Insider、TypeScript Blog、OpenAI News、Hugging Face Blog RSS、阮一峰的网络日志 Atom），种子见 `news_service.DEFAULT_SOURCES`。仅公开 API/RSS；单源失败不影响整体；**不伪造数据**。
- 榜单与评分：确定性规则、可解释。有效分 = 归一化热度 × 来源权重 × 时效衰减(48h 半衰期) × (1 + 0.5 × 主题相关度)；排名键（有效分↓, 发布时间↓, id↑，多次请求稳定）；优先 24h、回退 72h；单来源上限 4；相同文章不重复上榜。**LLM 不参与评分**。
- 展示：首页直接展示完整 TOP 10（排名、中文标题、中文摘要、来源、发布时间、查看原文），与资讯页共用同一份 API、翻译缓存与组件；摘要默认展示并限 2 行、点击展开；摘要仅使用来源原始提供内容（无摘要显示"来源未提供摘要"），**不生成摘要**；外部导航新标签页安全打开，禁止 iframe。
- 中文翻译：仅对最终进入 TOP 10 且缺少有效翻译的资讯，经现有 LLM **批量翻译一次**并落库缓存；已是中文的直接回填不调 LLM；无摘要的只译标题、**不得凭标题编造**；翻译失败回退原文且不再自动重试；异步执行（刷新任务成功后 + 启动补发），不阻塞首页；每次调用记 `token_usage`。
- 刷新与缓存：后台任务刷新（同 kind 409 防重），缓存有效期默认 30 分钟（`PH_NEWS_REFRESH_MINUTES`）；首页只读缓存不触发抓取；刷新失败保留旧缓存并提示；缓存只增不删、不做自动清理。
- 明确不做：收藏/已读、大规模列表、复杂筛选搜索、资讯源管理 UI、新闻历史浏览、LLM 摘要/推荐。

### 2.3 计划管理

**排序统一规则（每日/长期/书籍一致）：重要状态优先置顶；长期计划支持手动排序（重要/普通内部均可调整），每日任务与书籍无手动排序入口（按创建先后/默认顺序）。**

#### 长期计划

- 字段：标题、描述、**具体目标 goal**（可选多行文本，不参与进度计算）、目标日期（可选，未设置时不显示日期区域、无任何占位文案）、重要标记。
- 完成机制：不设进度/状态下拉，由"标记完成"按钮（二次确认）置为已完成并记录完成时间，立即离开当前列表进入**历史计划**；历史保留名称/描述/目标/创建时间/完成时间/重要状态，按完成时间倒序；完成时间未知显示"完成时间未知"（不伪造）；历史可删除。是否完成只由用户主动标记决定。
- 重要置顶：重要自动置顶，重要/普通内部均可手动调整，取消重要自动回落普通区域。
- **与每日任务完全独立**：无关联字段、无进度计算、删除互不影响。

#### 每日计划

- 按日期查看；增删改；完成复选框可反复切换（完成记录完成时间；取消完成清除完成时间并回到未完成区，历史列表同样允许取消）。
- **任务类型**：固定四种——日常（默认）/功能添加/功能优化/奇思妙想（内部枚举 + 前端中文名）；新增可选类型、编辑可改；每条任务显示类型标签；可选内容/备注字段（多行文本）。
- **统一排序**：当日任务与更早日期未完成任务纳入同一待办列表（可相互穿插）；排序优先级 **未完成优先 > 重要状态 > 任务类型（按上列顺序）> sort_order**；已完成任务整体置底（重要已完成同样置底，内部按完成时间倒序、未知最后）；**无手动排序入口**——sort_order 仅由创建/移入顺序决定（追加到视图末尾），同组内即按创建先后展示；新增/改类型/切重要/切完成均立即重排且持久化；排序不改任务日期/重要状态/类型。
- **未完成延续显示（已确定）**：某日视图 = 当日任务 + 更早日期未完成任务（逾期任务带原始日期徽标延续显示）；更早日期但**在本视图日期完成**的任务同样留在本视图置底展示（完成动作发生在本日，避免"勾完即消失"），且在其归属日期视图也可见；完成状态不变更归属日期（无副本）。
- **不做跨日期移动**：不提供"移至其他日期"入口（已移除）；任务到期未完成即作为逾期任务自然延续到后续日期视图。历史已移入任务保留 `moved_from_date` 溯源展示。
- **历史**：已完成任务按完成时间倒序可查、可按归属日期筛选（与 daily_tasks 同表）；历史内同样允许取消完成（取消后从历史消失、回到未完成列表）。
- **与随手备忘双向转换**（移动非复制，单事务原子）：未完成任务的"转为随手备忘"；随手备忘的"转为每日任务"（可选日期/类型/重要，标题与内容完整迁移）。已完成历史任务不提供转换。

### 2.4 阅读管理

- 书籍：增删改；字段：书名、作者、备注、阅读状态（待读/正在读/已读）、重要标记（红色强调、自动置顶，各状态筛选内分别生效）；按状态筛选。
- **书籍删除规则（已确定）**：存在一条或多条关联笔记的书籍**禁止删除**——后端删除事务内检查 `book_notes`，存在则返回 409 `book_has_notes`；必须先删光笔记才能删书；不级联、不自动解除关联；绕过前端直调 API 同样被拒绝；拒绝时数据与文件均不变。
- 读书笔记（D7）：云记导出 PDF/PNG，或直接上传/在线编写 Markdown → 存 `data/reading_notes/<book_id>/` → 库中存关联 → 浏览器直接预览；支持格式：PDF / PNG / JPG / MD（md 必须为有效 UTF-8 文本）；在线编写经 `POST /books/{id}/notes/md`（JSON：文件名可留空自动补 `.md` + Markdown 正文）。

### 2.5 数据保留与人工审核清理（D4）

| 数据类型 | 规则 |
|---|---|
| 微信聊天缓存（归一化库消息、原始快照库消息） | >7 天进入待清理（同一候选、同一确认） |
| 对应 Chroma 向量 | 随消息关联清理 |
| 微信 AI 总结报告 | 长期保留 |
| 长期计划 / 每日任务 / 书籍 / 读书笔记 / 重要信息 | 永久保留，不参与清理 |
| 随手备忘（memos 表） | 永久保留（SQLite），不参与清理 |

- 7 天是"进入待清理"条件，不是自动删除期限。**任何数据不经人工勾选确认不得删除；系统任何位置不得提供自动删除入口。**

**永久保护（最高优先级）**：`2026-10-27` 的微信聊天数据（原始快照、归一化消息、Chroma chunk 及关联索引状态）用于 Agent/RAG/检索测试，**禁止删除**——保护规则覆盖候选生成、确认、执行与重试全过程，全选、API 直调、失败恢复均不可绕过；包含保护消息的混合 chunk 一律整体保留。保护日期配置在 `Settings.protected_dates`（`PH_PROTECTED_DATES` 可扩展），重启后生效。
- 每周日生成一次清理候选（按群+日期分组；周日未运行则下次启动补发；同一 week_id 不重复创建；不覆盖此前未处理周期）。"稍后"仅隐藏提醒（首页横幅），"跳过本次"才结束周期。审核页展示群/日期/三层数量/保留原因；默认全部不预选；删除前二次确认并显示实际删除数量与范围；跳过 ≠ 同意删除，未审核数据始终保留。候选生成与预览严格只读（不删数据、不改 Chroma、不动游标、不 Embedding）。
- 删除一致性：微信消息删除 = 归一化库 → Chroma chunk → 原始快照库；不动 WeChatDataAnalysis 原始库；不误删总结报告。Chroma 第一版采用**保守策略**：只有 chunk 全部消息都属于待删日期且不含保护消息才删除；混合/含保护/归属无法确认的 chunk 一律保留并记录与展示原因（保留的混合 chunk 仍可能检索到已删消息文本，预览与执行结果明示；不做部分重建、不重新 Embedding）。删除计划持久化（消息区间、计数、chunk ID 与处置），执行前重新校验目标与保护规则；逐项状态机落库可重试、断点续跑，重启后靠明细状态恢复（启动时陈旧任务标记 failed，不依赖进程内锁）；清理与微信同步互斥（双向 409）。**审计日志只记元数据，不记被删聊天内容**。
- 备份与恢复：不实现（D1），替代保障见 §5。

### 2.6 工作台布局（PC 专用）

固定三栏：左侧导航（仅页面导航）+ 中央业务工作区（独立纵向滚动，页面切换不影响侧栏）+ 右侧常驻信息栏（可折叠，折叠状态存浏览器本地，折叠不卸载组件、未保存编辑不丢）。

- **重要信息（右栏上部）**：多条长期保存记录（名言/规范/单词/提醒等）；新增、编辑、删除（二次确认）、上移/下移排序、内容折叠展开；存 SQLite；长期保留。
- **随手备忘（右栏下部）**：多条结构化记录（SQLite memos 表），新增/编辑/删除（二次确认）/上移下移排序、标题与内容完整显示自动换行、无展开收起、基础 Markdown 安全渲染；与重要信息同一卡片组件规范但不合并表。定位：搁置想法/未定时任务的缓冲池，最终去向只有删除或转为每日任务（双向转换见 §2.3）。不参与清理。
- 旧版本地文件备忘（`~/.personal-hub/memo.md`）已废弃：启动时幂等迁移其内容（如有）为一条备忘记录，原文件保留不删除、不再作为数据源。
- 两类数据模型不合并；Markdown 渲染必须安全（无 XSS）。

### 2.7 GitHub 数据与年度贡献热力图（阶段一）

- **接入方式**：GitHub 官方 REST API（已确定不引入 GitHub MCP）；Token 配置于 `~/.personal-hub/.env` 的 `GITHUB_TOKEN`，仅后端持有，不向前端暴露、不进日志。
- **同步范围**：当前用户 owner 的仓库（含私有与 fork）及其 Commit / Pull Request / Issue（issues 端点混含的 PR 条目不计入 Issue）；同步走后台任务状态机，同 kind 409 防重；增量游标（sync_cursors，scope=github:{full_name}）；主键幂等 upsert，重复同步不重复计数；限流按 Retry-After 等待重试。GitHub 上已删除的仓库本地保守保留（删除走专门清理流程）。
- **时间口径**：存储为 UTC ISO8601 文本；归属日与展示时间统一转 Asia/Shanghai。
- **贡献统计（Personal Hub 口径，非 GitHub 官方 Contributions）**：某天贡献数 = 当天（+08:00）作者时间归属的 commit 数 + 当天创建的 PR 数 + 当天创建的 Issue 数。GitHub 官方口径（默认分支、提交归属等规则）不对齐；页面与接口均明示该口径，不得宣传为官方贡献数。颜色等级固定阈值：1-2 / 3-5 / 6-8 / ≥9 次。
- **缺失数据区分**：未同步年份明确提示"数据尚未同步"，不把缺失显示为零贡献；部分覆盖年份展示覆盖起止范围。
- **交互**：年度热力图（GitHub 布局：列=周、行=周一~周日、月份标签、Less/More 图例）、悬停 Tooltip（"Month D, YYYY: N contributions"/"No contributions"）、点击日期展示当日活动详情（类型/仓库/标题/时间/原始链接）、年份切换（禁止未来年份）。
- 第一版不同步 GitHub Events（避免与 commit/PR/issue 重复计数）；不自动创建或修改任何业务数据。

## 3. 前端与体验

React + TypeScript + Vite + Tailwind + shadcn/ui + TanStack Query。页面：首页工作台、微信聊天助手、技术资讯、计划管理、阅读管理、数据清理审核、设置。首页展示今日计划及完成度、最新资讯、聊天总结快捷入口、正在读的书、系统状态与待办提醒（含待清理提醒）。

Windows 一键启动：双击桌面快捷方式 → 检查/启动本地服务 → 打开浏览器 → 首页；正式运行使用构建后的 React 静态资源，由 FastAPI 托管（默认端口 8620，可配置）。

## 4. V2.0 方向（仅约束，不提前实现）

权威规划见 `DEVELOPMENT_PLAN.md` "未批准的后续规划"。约束：前后端彻底分离、后端默认 127.0.0.1；演进方向为 局域网访问 → 认证 → HTTPS → 移动端数据同步；禁止采用阻碍移动端复用的设计（业务不进桌面脚本、接口不依赖 Windows 特有对象）。

## 5. 数据操作安全规范（D1 配套，强制）

- 开发、调试、数据库迁移、破坏性测试**必须使用隔离的数据副本或临时测试数据库**，禁止直接修改唯一一份现有聊天数据（原始快照库、归一化库、Chroma 目录）。
- 如确需对真实数据库执行不可逆操作，必须先明确告知风险并取得用户批准。
