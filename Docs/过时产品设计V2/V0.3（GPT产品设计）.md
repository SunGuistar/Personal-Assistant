# 今日晨报 V1.0｜产品设计规划 V0.3

> **文档性质**：供产品所有者审阅、讨论与决定产品方向；不是开发 Prompt，也不是技术实施方案。  
> **更新依据**：《V0.2（GPT产品设计）》《V0.2.1问题及修正》《V0.2.3问题》《V0.2.4GPT回复》《完整执行流程V1.2（加入RAG）》及随后确定的“08:00 先采集再生成”规则。  
> **设计原则**：优先保证信息价值、事实可信、个性化和持续积累；Token 成本作为观察指标，暂不作为架构选择的首要约束。  
> **状态**：V0.3 产品讨论稿。标明“待讨论”或“待 Kimi Code 验证”的内容尚未最终确定。

## 一、产品定位

**一句话定位**：个人助手中的每日智能简报——从热点与兴趣匹配的资讯中发现重要变化，回顾个人进展，利用历史积累和个人目标提出有依据的建议。

每天回答三个问题：

1. **世界发生了什么？** 国内社会、国际社会、AI 领域有哪些重要且值得关注的消息？
2. **我昨天做了什么？** 最近一个晨报周期内完成了什么、推进了什么、还留下什么问题？
3. **今天值得我关注或行动的是什么？** 新信息与已有知识、当前目标有什么联系？

**产品边界**：不追求全面覆盖的新闻门户；不取代计划管理；不自动执行建议。现有资讯模块不作为依赖，未来可以独立下线。首先服务个人日常使用，再兼顾 Agent 工程能力展示。

**成功标准**：每天能稳定得到一份值得阅读的报告；信息重要且相关；引用可追溯；历史关联有依据；个人总结真实；建议不重复、不空泛。

## 二、整体体验与信息结构

### 2.1 日常使用流程

- 后台按计划持续收集资讯，增量获取正文、去重、落库；AI 技术资讯同步维护向量索引。
- **每天 08:00 先执行一轮最终资讯采集**，完成落库后固定本轮使用的数据快照，再启动晨报生成。用户无需手动触发首次生成。
- 当天正式晨报只有**一份主报告**；进入页面默认看到最新成功的主报告，若当天生成失败则明确显示失败状态并保留旧报告。
- 页面提供一个 **“重新生成”** 入口；同时承担失败后的手动重试、数据更新后的重新生成，不另设“首次手动生成”功能。
- 历史晨报可按日期阅读；同日重新生成的结果以附加版本保存，不覆盖原始主报告。
- 用户通过右栏对话框告知偏好、补充目标或回应澄清；记忆修改应可确认、查看与管理。

### 2.2 晨报内容结构

1. **开篇速览**：当天最重要的约 3 个要点，快速抓住重点。
2. **重要资讯**：国内社会、国际社会、AI 三大方向；根据当天信息价值安排篇幅，不要求平均数量。Agent、软件工程等作为 AI 方向内可重点匹配的个人兴趣。
3. **我的昨日**：周期内已完成事项、重要进展、遗留问题和长期目标状态；不能将当前状态冒充历史活动。
4. **今日建议**：由建议 Subagent 综合资讯、技术研究、目标分析形成 0–3 条有依据的行动建议，允许当天没有新增建议。
5. **信息说明**：来源、覆盖范围、数据缺失、生成日期与耗时等；**不计入阅读长度**。

**阅读长度**：正文默认约 5 分钟，重大信息较多时可延伸至 8–10 分钟；没有足够有价值的信息则缩短，不为达到字数凑内容。中文、分节、适于扫读。

### 2.3 时间窗口与生成规则

- 资讯与个人回顾统一以 **前一天 08:00—当天 08:00** 为晨报周期（按产品配置时区，当前建议北京时间）。
- **08:00 为内容时间截止点，不等于模型开始运行的时刻。** 08:00 启动最后一轮采集，采集结束后才进入分析；记录实际采集完成和生成时间。
- 建议以来源的发布时间及原始记录的事件时间划分周期；最终快照只包含本轮截止时已成功获取、符合本周期定义的数据。**不做专门的迟到补抓或自动改写主报告**。这是一条覆盖范围规则，不保证资讯源不存在延迟更新。
- 同一热点已有报道但出现**实质性新进展**时可以再次入选，并解释与此前报道相比有什么变化。
- 08:00 自动生成失败：自动重试**最多 3 次**；仍失败则提示错误，保留旧报告，允许不限次数手动“重新生成”。自动重试只在模型时段限制与其他约束允许时进行。
- **自动生成与手动重新生成的模型规则不同**：自动使用指定 DeepSeek 模型，且调用前必须满足允许的低峰时段；否则报错停止，不自动切换。手动重新生成使用已接入的 DashScope 免费模型。模型本身失败也直接报错，不静默切换。
- 自动失败后的手动重新生成仍沿用该日固定的晨报周期，不因触发时间改变起止时间；是否重新采集以既定“重新生成”策略处理。

### 2.4 重新生成与缓存

- 页面只有一个“重新生成”按钮；系统自动选择：**直接复用**（输入未变）、**局部重算**（仅部分数据或分析变化）、**完整重算**（重大变化、缓存失效或无法安全复用）。
- 缓存设定 **12 小时有效期**；应持久化，供重启后复用。判断输入有无变化要综合资讯版本、个人数据快照、Memory、报告配置以及模型版本，而不是仅比较日期。
- 局部重算后仍重新整合并核查完整报告；**保存每次成功重新生成的历史版本**。当天主报告的身份和历史记录入口保持唯一、明确。
- 这里的缓存指**本地生成结果及阶段结果复用**，与服务商的 Token 缓存分开统计。

## 三、核心功能设计

### 3.1 外部资讯：热点与兴趣匹配

| 方向 | 内容重点 | 候选来源与状态 |
| --- | --- | --- |
| 国内社会 | 重大事件、政策与公共议题 | **不使用 AIHOT**；国内综合新闻 API / RSS 等由 Kimi Code 先验证 |
| 国际社会 | 重要国际事件及背景 | BBC 等来源先验证实际访问、更新和全文能力 |
| AI | 模型、技术、研究、开源项目；重点倾向 Agent 与软件工程等兴趣 | AIHOT 优先评估；daily.dev、hotai.news、Hacker News、OpenAI、GitHub 等按实际价值和可用性接入 |

**核心设计**：

- 后台**每小时**进行资讯增量采集，08:00 再执行一轮最终采集；已取得的文章不重复抓取全文，需支持更新检测。
- 以**获取完整正文为目标**，正文连同标题、摘要、来源、时间、URL、热度等必要原始字段保存在本模块独立数据库。实际获取失败时不能伪造全文。
- 同源与跨源重复报道按**事件**聚合，保留多个来源及视角；避免相同事件重复占据晨报篇幅。
- 依据公共重要性、时效性、已有热度、来源可信度和个人兴趣筛选。重大公共事件不能完全被兴趣过滤。
- **AIHOT 只作为 AI 方向的候选来源**；可使用其已有热度与聚合结果，但不得将语义不明的指标解释成真实参与人数；来源限制、字段口径及必要性待实际核查。
- 所有进入晨报和 Subagent 的外部资讯须先落入本地数据库；生成阶段不允许绕开此规则进行无留痕联网研究。
- **全文获取失败的例外**：重要新闻可在来源足够可靠、信息有限且明示缺失时做谨慎简述；不足以支持深度判断的内容不展开。V1.0 完成后重点观察全文抓取成功/失败对报告质量的影响。
- 技术资讯入库后维护**技术资讯向量索引**，支持跨时间发现相关技术、论文和框架发展；正文事实仍由原始数据库与来源提供。

### 3.2 我的昨日：可核实的个人进展

- 原有个人助手数据库**只读**；从任务、长期计划、重要信息、备忘、阅读记录及确实可用的 GitHub 数据读取信息。
- 主要呈现完成事项、重要进展、未解决问题与目标关系，不把“做了多少任务”当作全部总结。
- 周期按前一天 08:00 至当天 08:00；**能否准确还原历史行为，必须由 Kimi Code 审计现有时间字段与记录机制**。
- 没有历史证据时说明数据限制，不编造“昨天完成”。建议从新模块上线起保存必要的只读快照，逐步增强历史回顾能力。
- 标红长期计划作为阶段目标优先来源；对话补充目标为辅。两者冲突时**不自动同步或覆盖**，以长期计划为准，并在报告中主动提示冲突。对话中发现冲突可要求用户澄清，但不阻塞正常晨报流程。

### 3.3 Memory：资讯偏好、行动建议偏好与补充信息

**使用统一 Memory 管理体系，区分用途而非拆成两个不相通的数据库：**

- **资讯偏好**：感兴趣或排斥的领域、深度和风格，影响选题、排序、技术解释。
- **行动建议偏好**：偏好的建议方向、实践方式、限制条件，影响建议 Subagent 的行动判断。
- **补充目标与其他记忆**：用户主动告知的短期关注点等；对长期计划的正式状态不具覆盖权。

用户通过**一个对话框**录入或修正。允许 Agent 推测候选偏好，但**必须主动提醒并由用户确认后才落库**。支持查看、编辑、禁用、删除；偏好设置入口统一放到记忆管理。不增加“有用/无用”反馈按钮，而是通过对话表达偏好。

### 3.4 Agent 分析与个性化建议

**已确定架构**：编排式工作流 + 普通 LLM 节点 + **每天固定调用的三个 Subagent** + RAG 混合检索。固定调用不意味着一定输出研究结论或建议。

- **Tool**：资讯/个人数据/Memory 查询，时间窗口和统计、去重、缓存判断、存储、引用校验、Token 记录；RAG Tool 提供向量及相关原文检索。
- **普通 LLM 节点**：资讯重要性与兴趣匹配、筛选摘要；昨日活动与计划进展初步分析。两条分析链可以并行。
- **技术研究 Subagent（固定）**：针对 AI 技术资讯，必要时自主调用 RAG Tool 检索历史技术资讯及历史晨报，回溯原文，判断新旧技术差异及实际价值；允许返回“无值得深研的进展”。
- **目标分析 Subagent（固定）**：结合标红长期计划、昨日活动与相关历史晨报，分析进展、关联和冲突；不改变原始目标数据。
- **建议 Subagent（固定且后置）**：等待技术研究、目标分析结果，再结合资讯、建议偏好与历史建议判断新行动是否值得提出；允许无新增建议。
- **主 Agent：晨报主编**：统一整合，决定重点与篇幅，生成结构化中文晨报。**不再负责决定三个核心 Subagent 是否启动**。
- **报告校验**：核对事实引用、个人统计、历史关联、建议依据、重复信息与结构；历史晨报只能帮助发现关联，涉及事实应回溯原始记录。

**RAG 范围**：

1. **技术资讯向量库**：跨时间技术关联和发展比较。
2. **历史晨报向量库**：跨日期连续分析、历史建议去重、新进展识别。
3. 两类索引分开维护，通过统一检索 Tool 访问；关系型数据库保存全文和权威资料，向量库保存语义索引及来源关联。
4. **数据准备阶段不预先执行历史语义检索**。Subagent 在任务过程中选择检索内容和深度；需要主动检查是否存在重要历史关联，但不强制多轮查询。
5. 个人当前任务、长期计划及结构化 Memory 主要使用精确查询，暂不纳入独立向量化范围。
6. 新资讯落库后更新技术资讯索引；晨报成功保存后，将内容按事件、个人总结、建议等语义单元更新历史晨报索引。

**行动边界**：只提出建议，不自动更改任务、发消息或执行外部操作。

### 3.5 生成状态、Token 与质量透明度

- 记录总生成耗时与主要阶段耗时；**60 秒内**是体验目标，不是稳定性保证。
- 记录调用次数、模型、输入/输出 Token、缓存命中与未命中 Token、命中率、单次与累计费用、错误状态。服务商没有返回的字段显示“未知”，不虚构。
- 右栏**常驻简洁 Agent 信息小窗口**：当前阶段、模型、耗时、调用和费用摘要；鼠标悬浮快速查看或点击打开可关闭的详细窗口。
- 显示数据源缺失、采集失败、资讯证据不足等质量提示，不把不完整数据包装成完整报告。
- 成本主要作为运营观察指标，仍防止异常无限重试。

## 四、系统与架构设计原则

### 4.1 产品级架构

采用“**后台资讯采集与建索引 → 08:00 最终采集及快照 → 数据读取 → 并行 LLM 初步分析 → 两个并行 Subagent → 建议 Subagent → 主 Agent 编辑 → 校验 → 保存与更新历史晨报索引**”的顺序。

完整的工具与节点关系以《完整执行流程V1.2（加入RAG）》为参考；**本版增加“08:00 最终采集、固定快照后才开始分析”**的已确定规则。无需在产品规划中展开函数、接口或具体数据库字段。

### 4.2 数据隔离

- 今日晨报使用独立数据存储，现有个人助手数据库只读，不更改原有功能和表结构。
- 保存新闻原文及来源、事件、Memory、历史晨报与版本、模型执行与费用记录。
- 推荐原始数据存储与语义索引职责分离：例如 SQLite 管理权威内容，Chroma 管理技术资讯和历史晨报索引；**具体向量产品属实施选型，不是当前产品决策**。
- 旧资讯功能与本模块解耦；不要求独立部署为微服务。

### 4.3 模型运行规则

- 正式每日 08:00 自动流程使用 **DeepSeek-V4.1-Flash-1017**（实际 API 名称、适用峰谷时间由开发验证）。
- 开发期间以及产品上线后的手动“重新生成”使用已接入的 DashScope 免费模型。
- 自动调用前严格检查允许的低峰时段；不符合时报错停止。**不自动跨供应商切换**。
- 自动失败重试上限 3 次；手动“重新生成”不限次数，但避免重复并发任务。

## 五、UI 与交互规划

**PC 优先，作为个人助手的一个模块，采用左右两栏。**

```text
个人助手 > 今日晨报
┌───────────────────────────────────────┬───────────────────────┐
│ 左侧：今日晨报（主要阅读区域）         │ 右侧：辅助区域         │
│ 日期 / 生成时间    [重新生成]          │ 历史晨报 / 记忆管理   │
│ 开篇速览                              │                       │
│ 国内 / 国际 / AI 重要资讯             │ “告诉晨报”对话框      │
│ 我的昨日                              │ （右栏主要面积）       │
│ 今日建议                              │                       │
│ 来源 / 信息说明                       │ Agent 信息常驻小窗口  │
└───────────────────────────────────────┴───────────────────────┘
```

- **左栏**：报告阅读为主，展示当天主报告、生成时间、重新生成入口、资讯来源及必要展开详情。
- **右栏二级入口**：历史晨报、Memory 管理、必要的运行统计；偏好设置归入 Memory 管理。
- **右栏对话框**：说明当前功能仅涵盖记忆录入、偏好修正、目标补充与冲突澄清；不暗示它已支持任意新闻追问。
- **右栏 Agent 信息**：常驻简要状态，悬浮或点击看调用详情，详情有关闭按钮。
- **历史记录**：每天主报告唯一；同日重新生成作为独立版本可查看，历史内容不因新记忆被重写。
- **失败体验**：可看到失败原因和“重新生成”入口，不以旧报告伪装成今日报告。
- **视觉方向**：可读的个人日报，而不是密集资讯门户。

## 六、仍待讨论的产品问题（仅保留未决项）

> 以下问题尚未被修正文档明确最终决定。每项提供推荐方案；一旦确认，将结论移入正式章节，从本列表删除。

**P1. 08:00 最终采集的截止与失败策略**  
08:00 启动最后一轮采集后，如果个别来源超时，应该等待多久才进入报告生成？  
**推荐**：为每个来源设置采集超时和总等待上限；成功数据先落库，未成功来源标注缺失，然后固定快照启动分析。实际阈值由采集试验决定。

**P2. 固定周期与重新生成时的新资讯如何兼容**  
手动重新生成可能发生在下午，但该日主报告窗口固定截止 08:00。是否允许使用 08:00 之后的新资讯？  
**推荐**：同日重新生成默认仍使用固定 08:00 截止的主报告周期，目的是纠错、补齐漏采和重新分析；08:00 之后发布的新闻不加入当天主报告范围。若未来需要即时资讯更新，另列 V2.0。

**P3. 部分数据变化时，局部重算的边界**  
哪些情况可以只重算个别阶段，哪些必须全部重算？  
**推荐**：资讯变化重做受影响的资讯分析、技术研究及建议，目标/Memory 变化重做相关个人或建议分析；最终报告整合和校验总是重新执行。无法可靠识别依赖时退化为完整重算。

**P4. 历史晨报应索引哪些信息**  
仅索引最终正文，还是保存对应的分析结论和引用依据？  
**推荐**：完整晨报及结构化章节都可检索；同时保留关键建议、关联来源及版本 ID，避免历史晨报只剩一段 AI 总结、无法回溯事实。

**P5. 向量检索如何平衡语义相关性与时间有效性**  
与当前话题高度相似的旧新闻可能已经过时。  
**推荐**：检索时结合语义相关性、事件时间、资料来源和版本状态；技术比较保留历史背景，当前事实必须使用更新证据。

**P6. 采集全文的严格程度**  
已经决定每小时尝试抓取正文，但无法取得全文的重大新闻怎样纳入报告，仍需形成稳定产品规则。  
**推荐**：保留缺失标识和少量可靠信息的简述权利；深度技术结论必须有足够原始证据，V1.0 开发完成后观察正文缺失对质量的影响再修订阈值。

## 七、V1.0 / V2.0 范围

### 7.1 V1.0 必须具备

- 定时采集三类资讯，08:00 最终采集、快照后生成；数据先入独立数据库。
- 资讯正文尽量完整获取，去重/事件聚合、重大事件与兴趣匹配及来源追溯。
- 固定周期的中文晨报、唯一日主报告、重新生成及历史版本。
- 对现有个人助手数据只读访问，输出有依据的昨日回顾。
- 统一 Memory 体系、两类偏好、用户确认入库、目标冲突提示。
- 编排式工作流、两个普通 LLM 分析节点、每日固定三个 Subagent、主 Agent 整合与事实校验。
- 技术资讯及历史晨报两类向量索引、Subagent 自主使用 RAG Tool、事实回溯。
- 生成状态、常驻 Agent 信息窗口、耗时、Token、缓存、费用统计；DeepSeek/DashScope 分场景运行规则。
- 左右双栏 PC 页面，历史晨报、记忆管理与有明确功能提示的单一对话框。

### 7.2 V2.0 候选

1. 语音播报完整晨报及播报控制。
2. 天气、地点、温度、日期等环境上下文和图标。
3. 长期 Memory 自动更新与反馈学习（须可审查与纠错）。
4. 个人行为趋势及跨月目标追踪（依赖可信历史事件）。
5. 正式开放新闻追问、即时资讯更新和深度研究对话。
6. 根据使用情况自适应调整资讯比例及解释深度。
7. 若有明确价值再扩展 Memory 或个人活动的向量化，不为统一架构强制扩展。

### 7.3 暂不规划

- 自建完整热点平台或独立计算“参与人数”。
- 无限制自由协作的 Agent 网络或无留痕的实时互联网研究。
- 自动修改现有任务、发送消息或其他未经用户确认的外部行动。
- 独立重建现有资讯门户或全套移动端页面。

## 八、V1.0 产品评价指标

| 指标 | 说明 |
| --- | --- |
| 每日晨报成功率 | 每天是否得到可阅读的正式主报告 |
| 资讯覆盖与来源可追溯性 | 是否收录重要事件，事实能否回到原始来源 |
| 重复与过时信息比例 | 新闻和建议是否重复、历史信息是否过时 |
| 昨日回顾准确性 | 是否把当前状态误认作昨天发生的事 |
| 历史关联价值 | 技术研究是否真正找到有意义的新旧关联 |
| 建议质量 | 是否具体、有依据、避免重复，允许无建议 |
| 阅读体验 | 长度、结构、相关性是否适合每天阅读 |
| 生成耗时与稳定性 | 08:00 采集、生成、异常恢复是否可靠 |
| 模型调用透明度 | 调用次数、Token、缓存、费用是否可追踪 |

> 评价指标是未来观察的方向；在没有配套数据来源时，不虚构“采纳率”“值得读率”等已测量结果。
