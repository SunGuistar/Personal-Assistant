## 一、产品定位与目标

### 1.1 产品定位

**今日晨报**是个人助手中的每日智能简报模块：持续收集值得关注的国内、国际及 AI 资讯，结合个人近期活动、长期目标和历史知识，生成一份**有信息价值、可追溯、读起来舒适**的中文晨报。

每天重点回答三个问题：

1. **世界发生了什么？** 国内、国际和 AI 领域有哪些值得关注的重要变化？
2. **我的昨日有什么进展？** 前一个晨报周期内，哪些事情有可核实的进展、哪些问题值得继续关注？
3. **今天值得采取什么行动？** 新信息与已有知识、个人目标相结合，是否能产生有依据的建议？

### 1.2 核心目标

- **资讯有价值**：重大公共事件不过度受个人兴趣影响；AI 技术资讯重视真实技术进展，而不是只罗列标题。
- **事实可核实**：新闻能够追溯原始来源，个人回顾只使用有时间证据的记录，历史晨报不是独立的事实凭据。
- **历史可积累**：通过历史技术资讯与历史晨报检索，理解技术演进、个人目标进展和建议的连续性。
- **建议不空泛**：行动建议具体、关联当前目标，避免重复或提出已完成事项；必要时可不提供建议。
- **日常愿意读**：正文像高质量个人日报，而不是数据库字段展示、Agent 调试信息或密集卡片堆砌。
- **过程可观察**：支持故障排查、运行日志、Token/费用统计和独立内容质量评价。

### 1.3 产品边界与约束

- 本模块作为**个人助手中的独立功能模块**运行，不要求拆分为独立微服务；旧资讯模块不构成依赖，是否下线由后续使用效果决定。
- **现有个人助手数据库只读**：不改原有任务、长期计划、阅读管理等业务结构与数据。
- 晨报可以提出建议，**不能自动修改任务、执行外部操作或发送消息**。
- V1.0 的对话框主要用于记忆与偏好管理、目标补充、冲突澄清；**不承诺通用新闻追问或开放式研究对话**。
- 不建设综合新闻门户，不自行声称能够覆盖所有热点，也不编造平台热度指标含义。
- 优先服务个人实际使用，同时保留可展示的 Agent 工作流、RAG、缓存、故障恢复和运行可观测性。

## 二、整体体验与晨报内容设计

### 2.1 用户日常体验

1. 系统在北京时间 **00:00、04:00、08:00、12:00、16:00、20:00** 增量采集三类资讯，尝试获取原文、清洗去重并持久化，必要时更新技术资讯索引。
2. **每天 08:00** 执行本期最后一轮采集；完成必要向量索引及一致性检查后，固定数据快照，再进入晨报生成。08:00 **不是承诺报告已经生成完成的时刻**。
3. 用户打开模块，默认阅读当天已经生成的主报告；如仍在生成，显示进行状态和实时日志；如当日失败，明确展示失败原因与可用历史报告。
4. 顶部提供唯一的主要操作 **“重新生成”**。系统可根据有效缓存及输入变化决定重用或重算；用户纠错或确需重算时，应具有可发现的高级处理入口。
5. 用户通过顶部二级导航查看 **“晨报正文 / 质量评价 / 历史晨报”**。质量评价与选中的晨报版本绑定。
6. 用户可在右栏与晨报助手对话，录入资讯偏好、行动建议偏好、补充目标，并管理已确认的 Memory。

### 2.2 晨报内容结构：自然阅读而非字段清单

正文包括以下五部分，**五部分用于组织文章，并不意味着每部分都要机械套用固定模板**。

| 部分 | 内容规则 | 呈现原则 |
| --- | --- | --- |
| **一、开篇速览** | 对本期**重要资讯进行整体提炼**，不是重新挑出三条与正文重复的新闻 | 一小段自然概述；重点足够突出时可分句或少量要点；不引入未在正文说明的新事实 |
| **二、重要资讯** | 分国内社会、国际社会、AI 技术三个方向，按新闻价值安排数量与篇幅 | 国内/国际：**标题 + 摘要**；AI：**标题 + 摘要 + 评价** |
| **三、我的昨日** | 回顾有据可查的进展、长期目标相关变化、必要的遗留问题 | 以一至数段自然叙述为主，不强制分成完成数、进展、问题、计划等子栏目 |
| **四、今日建议** | 结合当前资讯、个人活动、目标与历史建议提出 **0–3 条**有依据的行动建议 | 简洁、可执行；无有价值建议时可以不输出；失败与“无建议”必须区分 |
| **五、信息说明** | 资讯与个人数据的覆盖时间、主要来源、证据或数据缺失、生成时间等 | 作为轻量说明，弱化视觉权重，不挤占正文阅读空间 |

**重要资讯的详细表达规则**：

- **国内 / 国际社会新闻**：标题与自然语言摘要即可；摘要包含事实与必要背景，来源作为轻量的可访问链接提供。不强制增加“影响分析”“个人相关性”之类独立字段。
- **AI 技术资讯**：标题、摘要、**评价**。摘要尽量客观；评价讨论技术价值、局限和实际意义。**有意义的历史资讯关联自然写进评价**，不另列“历史关联”字段，也不强制每条资讯都作历史对比。
- **个人兴趣相关性**是后台选题和排序因素，**不在资讯正文中独立显示**；重大公共新闻不能被兴趣权重完全过滤。
- 同一事件存在多个来源时，先在后台聚合，不将相近报道重复写成多个新闻；确有**实质性新进展**时，可以重新入选并交代变化。

### 2.3 阅读长度、时间窗口与信息完整性

- **默认阅读约 5 分钟**；重大内容较多时可延长到约 8–10 分钟；没有足够信息时应缩短，不为凑字数扩写。信息说明不计入目标阅读长度。
- 资讯和“我的昨日”统一采用 **前一天 08:00 至当天 08:00** 的固定周期（北京时间）。
- **08:00 是来源发布时间/个人事件时间的内容截止点**。08:00 开始的最后采集可以在 08:00 后才获取到此前发布的文章；只要符合本期事件时间口径且在快照冻结前成功取得，仍可纳入本期。**08:00 后新发布的新闻不纳入当天报告**。
- 最后采集存在超时、某源缺失或正文无法获取时，允许在证据足够的前提下继续生成，但要在信息说明中反映缺失；不能把没有看到的正文编造成“全文结论”。
- 不做专门的迟到新闻自动补抓或自动改写主报告。当天手动重新生成可对既定时间窗口内的漏采信息进行补齐，但每次生成必须使用明确的快照版本。

### 2.4 主报告、历史版本与重新生成

- **每个自然日只有一个“正式主报告”身份**；同日手动重新生成后的成功结果作为**附加版本**保存，不覆盖已有主报告正文。
- 历史报告及附加版本可查看；每次版本包含对应日期、生成时间、资料快照、引用、质量评价及执行记录关联。
- 历史报告不因之后 Memory 或个人计划发生变化而被静默重写。
- 若当日自动报告尚未成功生成，页面不能把昨日报告伪装成今日报告；首份手动成功结果如何确立“主报告身份”的细则见第九章待确认口径。

## 三、核心功能设计

### 3.1 外部资讯采集、去重与筛选

| 资讯方向 | 收集重点 | 候选来源与原则 |
| --- | --- | --- |
| **国内社会** | 重大社会事件、重要政策和公共议题 | 国内综合新闻 API/RSS、NewsAPI 等**先验证**；**不使用 AIHOT 作为国内综合新闻源** |
| **国际社会** | 重大国际事件及必要背景 | BBC 等国际新闻来源，需先验证访问稳定性、内容可用性与合法使用条件 |
| **AI 技术** | 模型与平台更新、重要论文、框架与开源项目等 | 优先核查 AIHOT；同时评估 Hacker News、OpenAI、GitHub、daily.dev、hotai.news 等；Agent 和软件工程是兴趣标签，不是新增固定新闻大类 |

- 每 4 小时增量采集，不重复下载已取得且未更新的文章；检测原文更新，保留标题、正文（若可得）、摘要、来源、URL、发布时间、必要热度字段及采集状态。
- **尽可能获取全文**。失败时记录缺失状态；重要且可信的新闻可依据有限资料谨慎摘要，AI 技术深度判断不得无依据展开。
- 同文去重与**跨来源事件聚合**并行考虑，保留各来源、原始链接及不同视角，防止热门事件反复占据篇幅。
- 热点筛选兼顾公共重要性、时效、来源可信度、可解释的热度和已确认的兴趣；不将语义不明的“热度”解释为真实参与人数。
- 所有参与生成的外部资讯**必须先进入本模块持久化数据源**；Subagent 不绕过采集与留痕流程直接做无记录的互联网研究。
- 国内、国际原始新闻保存到本模块独立 SQLite；**AI 技术资讯标题、全文、来源及检索元数据由 Qdrant 持久保存**，并建立 Dense/BM25 检索能力。两者的原文可靠性与备份责任按实际权威存储确定。

### 3.2 “我的昨日”：可核实的个人活动

- 对现有个人助手 SQLite **只读**读取每日任务、长期计划、重要信息、备忘、阅读记录与实际可用的 GitHub 活动等；**只使用可以证明事件时间的记录**。
- 内容重点是重要进展、长期目标推进、值得关注的未完成事项及真实变化，不将“当前任务状态”直接等同于“昨天做过的事情”。
- 优先使用**标红的重要长期计划**作为阶段目标；对话中的补充目标只作为辅助手段。若两者矛盾，以原有长期计划为准，不自动同步修改；必要时在晨报中说明或在对话中澄清。
- 如原数据库缺少历史行为记录，应直说可见范围和不确定性；是否需要从模块上线起增补只读快照，由 Kimi Code 先审计后决定，不编造历史活动。

### 3.3 Memory：统一存储、按用途使用

统一 Memory 体系分为：

1. **资讯偏好**：感兴趣 / 不感兴趣的领域、期望解释深度、阅读风格，服务资讯筛选与呈现。
2. **行动建议偏好**：倾向采用的行动方式、建议方向、约束与限制，服务建议 Subagent。
3. **补充目标及相关记忆**：通过对话补充的短期关注、明确偏好等；优先级低于原有长期计划的正式状态。

产品要求：

- 通过**一个晨报助手对话框**录入、修正或澄清；Memory 可查看、编辑、禁用和删除，偏好设置统一纳入 Memory 管理。
- Agent 可以提出推测出来的候选偏好，但**必须主动告知并征得用户确认后才能写入 Memory**，不能静默推断后持久化。
- 不新增“建议有用/无用”投票按钮；用户可通过对话表达建议偏好。
- 不把 Memory 和当前任务、计划强行向量化，也不复制正式长期计划到 Memory；需要时读取其权威业务记录。

### 3.4 历史检索和个性化建议

- 技术资讯、历史晨报分别建立 Qdrant Collection；统一 RAG Tool 支持语义检索、关键词/BM25 与相关元数据过滤，并返回可追溯的文章或晨报版本关联。
- **历史检索由三个 Subagent 在实际任务中自主决定**，不在“数据准备”阶段预先做固定向量检索。可以发现相关历史知识后继续检索，但不强制每次执行多轮查询。
- 历史资料**不因发布时间较早而自动降低价值**。对于随时间变化的观点，优先考虑较新的认识并交代重大变化；涉及客观事实冲突时必须核对原始来源，不能仅以“更新”判断真假。
- 旧晨报有助于寻找历史建议和技术脉络，但其中 AI 生成的判断**不能直接作为最终事实凭据**；必要时回溯原始文章或个人记录。
- 建议 Subagent 必须根据真正完成的技术研究、目标分析和历史建议记录做判断。允许返回 **0 条建议**；不重复推荐已完成、失效或没有明确价值的行动。

### 3.5 事实检查与独立质量评价

**事实及引用检查**是发布前必要步骤：对来源、日期、个人活动证据、统计、历史关联、建议依据、重复内容和缺失说明进行核查，必要时调用 LLM 辅助；有严重事实问题或引用缺失时阻止错误内容发布。

**内容质量评价**是一个独立的 LLM API 环节：

- **仅将最终晨报正文提供给评价模型**；不附加原始新闻全文、个人记录或 Subagent 中间分析。
- 输出**综合分、五项分项分数及一段自然语言“评价”**；评价可自然包含亮点、不足及改进方向，不分拆“问题清单”和“改进建议”。
- 五项：资讯呈现、内容逻辑与一致性、AI 技术分析、个人总结与建议、阅读体验。
- 不设评分合格线，不因分数低自动重新生成或修改报告；**评价失败不阻塞已经通过事实校验的晨报发布**，应记录“未评价/评价失败”。
- 每份晨报版本与自己的评价结果绑定，支持历史查看与版本比较。
- **能力边界**：仅看最终正文的评价不能可靠判断新闻真伪、是否漏掉重大事件或个人记录真实性；这些问题仍由事实校验及外部覆盖检查负责。

## 四、Agent 工作流与系统架构

### 4.1 技术选型与角色

| 组件 | 产品级职责 |
| --- | --- |
| **LangGraph** | 串联主流程、并行阶段、状态、失败分支与中断恢复 |
| **LangChain** | 构建三个固定 Subagent、LLM / Tool Calling、连接 RAG 工具 |
| **Qdrant Server** | AI 资讯全文与 Dense/BM25 检索、历史晨报语义索引与过滤 |
| **本模块 SQLite** | 国内/国际资讯正文、正式晨报及版本、Memory、阶段缓存、执行日志、Token/费用与评价记录 |
| **现有个人助手 SQLite** | 提供只读的个人任务、目标和有据可查的个人活动 |
| **FastAPI + PC 前端** | 承载现有模块集成、报告阅读、对话、实时运行日志和页面状态 |

采用**固定工作流 + 有工具调用能力的三个 Subagent**，不引入 Deep Agents 作为主架构，也不构建无约束的多 Agent 自由协作网络。

### 4.2 端到端执行流程（产品概览）

```text
【独立常态采集：北京时间每 4 小时一次】
00:00 / 04:00 / 08:00 / 12:00 / 16:00 / 20:00
    ├─ 国内/国际：采集、去重、保存到晨报 SQLite
    └─ AI 技术：采集、去重、保存到 Qdrant，增量维护检索索引

【08:00 生成主报告：08:00 采集即当期最后采集】
0. 创建运行记录 → 清理上一轮阶段缓存
1. 完成最后采集 → 检查本期必要 AI 索引和历史晨报索引
   ├─ 必要索引成功 → 继续
   └─ 必要索引失败 → 阻塞，有限重试，保留错误与日志
2. 固定数据快照 → 读取资讯 / 只读个人数据 / 已确认 Memory
3. 普通 LLM 节点（并行）
   ├─ 资讯分析：选题、排序、摘要、后台兴趣匹配
   └─ 个人分析：昨日活动与重要长期计划进展
4. Subagent（每天固定调用）
   ├─ 技术研究 Subagent ────┐
   │    └─ 自主调用 RAG     │ 两者并行
   └─ 目标分析 Subagent ────┘
              ↓ 两者到达明确终态
      建议 Subagent（后置，结合历史建议，允许无建议）
5. 主 Agent / 晨报主编：整合五部分中文晨报
6. 事实与引用校验：严重问题阻止发布
7. 独立 LLM 质量评价：综合评分 + 五维评分 + 自然评价
   └─ 评价失败可标记缺失，不阻塞通过事实校验的报告
8. 保存与发布晨报、版本、来源、日志与评价
   └─ 更新 Qdrant 历史晨报 Collection 及索引状态

【全程】阶段结果缓存 / LangGraph 恢复 / 实时日志 / Token 与费用记录
```

> **权威执行顺序**：本版采用《完整执行流程 V1.3》的各环节设计，但第 0 步前的常态采集频率改为**每 4 小时一次**。主 Agent 不决定三个核心 Subagent 是否调用；三者每天固定执行，允许“无实质结论”作为有效结果。

### 4.3 三个 Subagent 的边界

| Subagent | 主要输入与能力 | 返回内容及边界 |
| --- | --- | --- |
| **技术研究** | 重要 AI 资讯；自主调用 RAG 检索历史文章和晨报，必要时回溯来源 | 技术价值、局限、与既有观点的实质变化及依据；没有值得研究的进展时可明确说明 |
| **目标分析** | 个人活动、标红长期计划、确认的 Memory、相关历史晨报 | 进展、目标关联和冲突；不得修改原有个人助手数据 |
| **建议** | 资讯、个人初步分析、前两位 Subagent 的有效结论、行动偏好及历史建议 | 0–3 条可执行、有依据且不重复的行动建议；必须在前两位 Subagent 完成或明确失败后启动 |

部分 Subagent 失败允许按第五章规则降级，但**不能把“执行失败”伪装成“没有结论”**。

### 4.4 数据边界与历史索引

- Qdrant 的**技术资讯 Collection**保存 AI 资讯标题、全文、来源、时间和必要元数据，提供 Dense、BM25、混合检索能力；因此它**不是纯临时索引**，需要可靠持久化与备份。
- Qdrant 的**历史晨报 Collection**保存按新闻事件、个人总结、建议等语义单元拆分的可检索内容，记录日期、版本 ID 和出处线索；**完整正式晨报的权威版本仍保存于本模块 SQLite**。
- 国内/国际社会新闻在独立 SQLite 保存和精确查询，**V1.0 不强制为其建立向量索引**。
- 快照冻结后，后续工作流始终围绕本次快照及所标识的数据版本开展；不同轮次更新不可无提示混用。成功报告建索引后，应记录索引状态，下一轮生成前校验必要历史索引是否可用。

## 五、生成调度、缓存与故障处理

### 5.1 调度与时间窗口

- **采集频率**：北京时间每天 `00:00、04:00、08:00、12:00、16:00、20:00`，每 4 小时一次。
- **晨报窗口**：上一个自然日 08:00 至当前自然日 08:00；使用事件发生/资讯发布时间判断属于哪个周期。
- **正式启动**：当天 08:00 的采集任务承担当期最后采集职责；必要索引确认成功后再固定快照并开始 Agent 工作流；不另外重复采集一次。
- **采集部分失败**：单一来源超时或全文缺失可按可信资料继续；记录缺失原因。各来源与整体超时阈值需实测确定。
- **向量索引严格阻塞**：当期新增/修改的技术资讯必须完成必要索引；历史晨报必要索引须保持一致且可检索，否则禁止进入 Agent 分析。正常情况下只做增量更新，不每天重建全部历史索引。
- **手动重新生成**：依旧使用该日固定截止窗口；允许补齐该窗口内漏采内容，不能引入当天 08:00 之后才发布的新闻。

### 5.2 本地阶段缓存与 LangGraph Checkpoint

- 对普通 LLM 分析节点和每个 Subagent 的**成功结果**持久缓存，以便失败恢复或同日重新生成；输入匹配时复用。
- 每天 **08:00 开始新一轮自动生成时，清理前一轮阶段缓存**；每条阶段缓存**最长有效期 12 小时**，以先发生的清理或到期为准。
- 匹配依据不仅是日期，还包括相关资讯与个人数据快照、Memory、模型、指令/配置版本等会影响结果的输入依赖。
- 若部分输入变化，只重新执行受影响阶段及其下游依赖；**最终主编整合和事实校验仍需重新执行**。无法安全判断依赖时完整重算。
- 如果用户发现已有缓存分析错误，应能使对应阶段结果失效并允许完整重算，避免输入未变时反复复现错误。
- **LangGraph Checkpoint**用于流程状态恢复，**本地阶段缓存**用于跨执行复用成功结果，**服务商 Prompt 前缀缓存**用于重复输入计费/加速，三者用途不同，分别观察与处理。
- 清理阶段缓存**不影响**长期资讯、Qdrant、Memory、历史晨报、正式日志与费用记录。

### 5.3 重新生成及版本规则

- 前端保留一个醒目的“重新生成”入口：默认依据输入和阶段缓存选择复用/局部重算；需主动纠错时可进入高级操作执行指定失效或完整重算。
- 每次成功重新生成都成为新的**历史附加版本**，保存其独立的快照与质量评价；已有当日主报告不被覆盖。
- 自动生成失败时最多**自动重试 3 次**；手动重试总次数不设上限，但避免同一日期重复并发生成。
- 已完成的有效阶段允许被故障重试使用；失败节点不能伪造成功结果。

### 5.4 故障分级与发布门槛

| 情况 | 预期处理 | 是否阻塞整份晨报 |
| --- | --- | --- |
| 个别新闻源失效、少量全文缺失 | 使用可信的已采集资料、标明覆盖缺口，避免证据不足的深度分析 | **不一定** |
| 必要 Qdrant 技术资讯或历史晨报索引失败 | 修复并有限重试；索引恢复前不进入 Agent 分析 | **是** |
| 非关键普通分析阶段失败 | 保留其他有效分析，注明缺失，可降级 | **视内容可信度** |
| 技术研究或目标分析 Subagent 失败 | 记录失败；其结论视为缺失，后续建议不得假称收到完整分析 | **可降级** |
| 建议 Subagent 失败 | 记录“建议分析失败”；不可展示为“无新增建议” | **不必** |
| 主 Agent / 主编无法形成完整报告 | 标记生成失败 | **是** |
| 严重事实错误或关键引用无法核查 | 阻止发布受影响的错误报告，等待修复 | **是** |
| 独立质量评价 API 失败 | 记录“未评价/评价失败”，保留已校验的晨报 | **否** |
| 模型超时、限流、拒绝或服务异常 | 记录具体错误，按有限重试及分级策略处理，不静默换模型 | **按所在阶段** |

- 对外展示**“生成中 / 已完成 / 失败 / 降级完成 / 未评价”**等可区分的状态；降级不能伪装成资料全部齐全。
- 正式主报告因关键故障无法产出时仍保留历史报告浏览入口，明确标注其原始日期。

## 六、模型调用与运行监控

### 6.1 模型使用规则

- **每日正式自动生成**：目标模型为 `DeepSeek-V4.1-Flash-1017`，实际 API 标识和允许的低峰时段由 Kimi Code 核实；**每次调用前检查当前是否处于允许时段**，超出则报错停止，不自动切换其他供应商或模型。
- **开发与人工“重新生成”**：使用已经接入的 DashScope 免费模型；实际可用配额、接口和模型名称需实测确认。
- **质量评价**：独立的 LLM API 调用；可以复用现有供应商接入能力，最终模型以实施验证为准；不得把独立评价误写成与生成模型完全相同的调用。
- 模型超时、限流、拒绝及其他错误按第五章分级策略处理，记录调用失败和重试，不做隐式模型兜底。

### 6.2 Prompt 组织与缓存优化

- 固定**系统指令、角色说明和输出规则**尽量排在 Prompt 前部，当前资讯、个人记录和 RAG 结果放在后部，以提高服务商前缀缓存命中的机会。
- **不以降低 Token 费用为目的强行压缩有价值资料**；本期资讯和个人信息按任务需要提供。
- 历史资讯与历史晨报经 RAG 相关性筛选，不把完整历史库不断追加进 Prompt；不因资料发布时间久远而直接排除。
- 必须遵守模型实际**上下文窗口上限**并为输出预留空间；这里的限制是模型能力边界，**不是人为设置的低 Token 成本预算**。
- 相关性筛选仅决定本次 LLM 输入，**不删除或覆盖原始持久资料**。

### 6.3 Token、费用和时间统计

- 记录每次模型调用的节点/Agent、模型名称、开始/结束时间、成功/失败、输入/输出 Token、服务商缓存命中/未命中数据（如提供）、调用次数及费用。
- 支持本轮总计、主要阶段耗时及累计统计；记录实际耗时，不设“必须 60 秒生成完成”之类未经验证的性能承诺。
- 当供应商不返回某项缓存数据或费用字段时显示“未知/不可得”，**不自行推断为 0 或声称命中率准确**。
- 区分**阶段结果缓存命中**与**服务商 Prompt Token 缓存命中**，不将两者混为一种指标。

### 6.4 实时日志与可观测性

- **右栏展示实时执行日志**，代替旧版“常驻 Agent 信息摘要小窗口”；默认以业务事件呈现：采集、索引、选题、研究、目标分析、建议、编辑、校验、评价、保存等阶段。
- 允许点击或展开某条日志查看模型、Tool、阶段耗时、Token、缓存、错误摘要等技术细节；**完整日志落库持久保存**，可按执行记录和晨报版本查阅。
- 并行 Agent 的事件需有明确时间与归属，避免用户误以为日志按实际执行顺序串行发生。
- 默认不在 UI 直接展示私人原始数据、完整 Prompt、凭空生成的“内部思考过程”等敏感/不可靠调试内容。
- 日志的可读性服从阅读型 UI 原则：可以发现、可以查，但不抢占晨报主内容空间。

## 七、产品质量与评价指标

### 7.1 质量控制由两层组成

| 层次 | 评价对象 | 是否影响报告发布 |
| --- | --- | --- |
| **事实与引用校验** | 新闻来源、人物/时间、个人活动证据、历史关联、引用支持、重复和明显矛盾 | **严重错误阻止发布** |
| **独立 LLM 内容质量评价** | 已生成晨报的资讯呈现、内部逻辑、技术分析表达、个人总结与建议、阅读体验 | **不以分数阻塞**；评价失败也允许已校验的内容发布 |

### 7.2 内容质量评分规则

- 独立 API **只读取最终晨报正文**；提供综合评分（0–100）、五维分数和一段自然语言**“评价”**。
- 五维名称统一为：**资讯呈现、内容逻辑与一致性、AI 技术分析、个人总结与建议、阅读体验**。
- 评价段落自然描述优点、不足与可改进之处，不额外要求输出“主要问题”“改进建议”两个字段。
- 不设强制合格线、不按评分自动改写或重生成；每个历史版本可以查看自己的分数与评价。
- 评分只是成品的表达与分析质量信号，**不代表对原始事实真伪的独立核验**；同一报告多次评分可能有波动，须通过实际测试观察。
- 综合分与五项分数的具体权重/计算口径不得伪装成已验证指标；实施时需保持同一规则、可解释且便于跨版本比较。

### 7.3 日常效果观察指标

| 指标 | 重点观察 |
| --- | --- |
| **晨报生成成功与降级情况** | 每天是否按规则生成；关键索引阻塞、错误与自动恢复是否透明 |
| **新闻价值与覆盖** | 是否包含重要事件；是否因来源缺失遗漏关键内容 |
| **来源与事实可追溯性** | 重要事实能否回到原始链接/记录；是否有无依据的技术结论 |
| **重复和时效性** | 同一事件是否重复出现；是否合理处理新进展和旧观点变化 |
| **昨日回顾准确性** | 是否错误地把当前状态冒充昨日完成事项 |
| **历史关联价值** | 技术研究的历史对比是否有实际信息量，而非形式化引用 |
| **建议质量** | 是否具体、相关、可执行、去重，且允许确实无新增建议 |
| **阅读体验** | 篇幅、自然程度、标题层级与正文密度是否适合每日阅读 |
| **运行与成本透明度** | 总耗时、阶段耗时、模型调用、Token、缓存与费用是否可追踪 |
| **LLM 评分可用性** | 五维分数与自然评价是否一致、有参考价值，是否存在明显波动 |

> 这些是**计划观察的产品指标**。在没有真实测试数据前，不写入臆测的成功率、费用、评分分布或用户满意度数字。

## 八、UI 与交互设计

### 8.1 视觉方向：以阅读为中心

**UI 目标**：每天打开后迅速理解重点、能够自然连续阅读、较长正文不疲劳，同时需要时能查到 Agent 状态与质量评价。视觉风格以**内容阅读型个人日报**为基调，而非数据控制台。

- 当前以**PC 浏览器**为唯一适配目标；不额外规划移动端专用页面。
- 参考已确认的整体示意图：顶部标题与日期、右上“重新生成”，下方三项二级导航，正文区与右侧晨报助手/实时日志形成双栏。
- **示意图只作为信息层级与布局方向参考**，实际实现需修复示意图中正文过窄、换行频繁的问题：主阅读区占据明显更大空间，右栏保持适中宽度。
- 正文使用舒适的中文字体、字号、行高、段落与模块间距；控制单行长度，避免横向过宽；配色低刺激、对比充足，深色主题下尤其避免纯黑大面积与过亮纯白文字造成疲劳。
- 不靠大量边框、标签和图标区分内容，优先通过**字体层级、间距和轻量分隔**组织信息。

### 8.2 整体页面与二级导航

```text
个人助手 > 今日晨报
┌──────────────────────────────────────────────────────────────────────┐
│ 今日晨报  日期 / 晨报周期                         [重新生成]          │
│ [晨报正文]   [质量评价]   [历史晨报]                                 │
├─────────────────────────────────────────────┬────────────────────────┤
│ 主内容：更宽的阅读区域                       │ 右栏：辅助区域          │
│                                             │                        │
│ 开篇速览                                    │ 晨报助手               │
│ 重要资讯：国内 / 国际 / AI                   │ 记忆与偏好、目标补充   │
│ 我的昨日                                    │                        │
│ 今日建议                                    │ 实时执行日志           │
│ 信息说明                                    │ 可展开技术详情         │
└─────────────────────────────────────────────┴────────────────────────┘
```

- **“晨报正文 / 质量评价 / 历史晨报”是同一模块的二级导航**，不是正文内部的三级标题。
- “晨报正文”优先服务文章阅读；“质量评价”独立展示该版本的综合分、五维评分条和一段评价；“历史晨报”按日期和版本选择旧报告。
- **质量评价始终跟随当前选中的晨报版本**；从历史报告选中某版本后切至评价，应展示该版本评价，而不是自动跳回当天。
- **Memory 管理**从晨报助手内进入，不在三个二级导航中另添重复入口。右栏对话框占主要空间；实时日志为辅助，内容多时可滚动或展开查看。

### 8.3 正文排版与视觉层级

- 开篇速览可适当强调，但仍是一段**对重要资讯的整体总结**，不设计单独的“今日三大新闻”重复式大型卡片。
- 国内/国际资讯条目只突出**标题 + 摘要 + 轻量来源链接**；AI 条目提供**标题 + 摘要 + 评价**，评价通过间距或微弱视觉变化与摘要区分，而不是强制放进厚重卡片。
- “我的昨日”按自然语言回顾呈现，避免一屏四个统计模块。今日建议可以适度强调行动句，但不变成任务编辑器。
- 信息说明与辅助元数据视觉弱化；来源链接仍应易识别、易打开，避免只给不可操作的来源名称。
- 长篇信息支持正常浏览、选中文字和复制；标题层级明确，合理留白；不使用强制单行截断隐藏重要内容。
- UI 的字体、字号、最大正文行宽、侧栏宽度等作为**设计实施阶段的视觉规范**再精细确定，本稿不虚构截图所未体现的固定像素要求。

### 8.4 质量评价页面

- 页面中明确当前晨报日期、对应版本及评分状态。
- 主要内容：**综合评分（0–100）+ 五个分项评分条 + 一段自然语言“评价”**；不额外放“问题清单”“改进建议”卡片。
- 不把评分放到晨报正文顶部，也不在右栏持续占据空间；无评价或 API 失败时展示明确状态，不能默认 0 分。
- 不展示“低于某分不合格”的硬标签，因为 V1.0 不设置发布分数门槛。

### 8.5 运行状态、错误提示与交互

- **生成中**：正文区域清楚显示本期正在进行的阶段；右侧日志可查看实时进展，但不要求用户一直守在页面。
- **生成成功**：显示当日报告与实际生成时间，允许切换二级页面；评价可能已经成功，也可能处于未评价状态。
- **降级完成**：正文可用，但信息说明明确记录未取得的数据或未完成的分析，不伪装成完整成功。
- **生成失败**：说明失败发生在哪个阶段（尤其是必要索引、模型调用或主编校验），保留重新生成入口与旧报告入口；旧报告日期必须醒目。
- **重新生成**：主要按钮保持简单；缓存纠错与完整重算为高级选项，不在主页面堆叠大量按钮。生成中应限制重复并发触发。
- **历史选择**：切换日期与版本后，正文和质量评价保持一致指向；返回今日晨报时应清楚反映当前选择。

### 9.3 仍待确认的细节口径（不属于已决定规则）

这些问题没有在 V0.3.1–V0.3.3 中得到直接而完整的最终决定，因此不擅自写成既定事实：

1. **自动主报告生成失败后，手动生成的首份成功结果如何标记“当日主报告”**：当前已明确“每天只有一个主报告身份、手动成功需保留版本”，但“无主报告时是否自动将首份手动成功版设为主报告”还没有单独确认。推荐将其设为当日主报告，并保留实际生成方式和运行记录；**待产品确认**。
2. **质量评价综合分的具体计算规则**：已确认五维评分与综合评分，但五项权重或综合分生成方式未最终指定。推荐采用稳定可解释的统一规则并通过真实评价样本验证；**由质量评价测试后确定**。

> 对这些未决点保留显式标识；不得在实施阶段无提示地替换已经明确的业务规则。产品决策与现实约束冲突时，先记录测试证据，再讨论调整。

### 9.4 V2.0 规划（候选功能）

1. **晨报语音播报**：全文播报及播报控制。
2. **环境上下文**：天气、地点、温度、日期等信息的轻量融入。
3. **长期 Memory 自动更新与反馈学习**：必须可审查、可纠错，避免静默写入错误偏好。
4. **个人行为趋势与跨月目标追踪**：以可靠的历史事件数据为前提。
5. **开放式新闻追问、即时资讯更新和深度研究对话**：与 V1.0 仅面向 Memory/目标的对话范围区分。
6. **基于使用情况优化资讯比例与解释深度**：不以机械关键词命中替代信息价值判断。
7. **按实际价值扩展 Memory 或个人活动的向量化**：不为技术统一而强行向量化所有数据。
