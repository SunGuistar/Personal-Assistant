# 今日晨报｜完整执行流程 V1.3

> **定位**：在《完整执行流程 V1.2（加入 RAG）》基础上整合已确认的 V0.3.x 产品决策。本文描述端到端执行逻辑、依赖、异常与输出，不作为代码级接口设计。
>
> **整体架构**：LangGraph 编排工作流 + 普通 LLM 分析节点 + LangChain 构建的三个固定 Subagent + Qdrant 混合检索（按需 Query 改写与 Rerank）+ SQLite 业务存储 + 独立阶段缓存与 Embedding 复用 + 独立质量评价 API。
>
> **时间基准**：北京时间（Asia/Shanghai）。本期资讯与“我的昨日”统一覆盖**前一天 08:00 至当天 08:00**。08:00 是内容截止点和最后一轮采集启动点，**不是**保证报告已生成的时间。

## 一、端到端完整执行流程

```text

    每 4 小时（00:00 / 04:00 / 08:00 / 12:00 / 16:00 / 20:00）增量采集国内 / 国际 / AI 资讯
        ├─ 获取元数据并尽可能抓取全文；保留来源、时间、URL

【全流程横切能力】
    ├─ LangGraph：编排、并行、执行状态、中断/恢复
    ├─ LangChain：Subagent、LLM 调用、Tool Calling / RAG 集成
    ├─ 阶段缓存：成功节点落盘；有效期至多 12h；输入匹配才复用
    ├─ Embedding 复用：内容哈希 + 模型/切分版本一致才复用，不随每日阶段缓存清理
    ├─ 故障处理：分类超时、有限重试、可接受的降级与关键阻塞
    ├─ 实时日志：前端流式展示事件，完整技术日志持久化
    └─ Token / 费用：记录模型、调用、输入/输出、服务商缓存等信息
```

## 二、关键执行规则

### 1. 时间、采集与快照

- **每日 00:00、04:00、08:00、12:00、16:00、20:00 进行增量采集**（北京时间）；其中 **08:00 是六个既定采集时点之一**，承担最终采集，不额外发起第七次。完成必要索引后冻结快照，再启动 Agent。晨报窗口固定为前一天 08:00—当天 08:00。
- 新闻源个别超时或无法取得全文时，使用符合要求的已采集信息，**显式标明数据缺失**；证据不足的内容不能作深度结论。
- **必要向量索引严格阻塞**：本期新增/更新的 AI 技术资讯必须完成索引；历史晨报必要索引须保持可检索、一致。失败时停止进入 Agent 主工作流，按故障规则重试，不跳过。
- 仅增量更新必要索引，不对历史资料每日全量重建。新闻源缺失的容忍与索引缺失的阻塞是两种不同规则。
- 下午手动重新生成仍使用当天固定截止窗口；08:00 后才发布的新闻不进入本期，允许对既定窗口内漏采内容进行补齐与重算。不得静默把不同快照混为一次执行。

### 2. 固定三个 Subagent 与历史检索

- **技术研究、目标分析每天都调用且并行；建议 Subagent 必须在两者完成或已有明确终态后再运行。** 主 Agent 不负责选择是否启动它们。
- **三个 Subagent 全部使用统一 RAG Tool，并都可按需使用 Query 改写与 Rerank**：默认基础 Dense/BM25 混合检索，复杂问题或证据不足时增强，不强制每次调用完整增强链路；Query 改写和 Rerank 故障时可降级至基础检索并记日志，但**必要索引失败仍阻塞 Agent 分析**。应检查重要历史关联，**不强制每条 AI 资讯都展示历史对比**。
- 旧资料不因时间久而自动失去检索价值；观点冲突时优先考虑新认识，客观事实仍须回溯证据核实。历史晨报是辅助发现线索，不是事实的最终证明。
- 目标冲突：现有标红长期计划优先于对话补充目标，不自动修改原计划；必要时在晨报中提醒。

### 3. 数据存储分工

| 存储 | 职责 |
| --- | --- |
| 现有个人助手 SQLite（只读） | 每日计划、长期计划及可核实的历史活动等 |
| 晨报独立 SQLite（读写） | 国内/国际新闻原文，正式晨报/版本，Memory，阶段缓存，执行与实时日志，Token/费用，质量评价 |
| Qdrant：技术资讯 Collection | AI 技术资讯标题、全文、来源、时间、其他元数据与 Dense/BM25 检索 |
| Qdrant：历史晨报 Collection | 晨报语义片段、关联版本 ID、原始出处线索与历史检索 |

- 不要求为国内/国际新闻建立向量索引；需要时仍可通过 SQLite 获取和筛选。
- Qdrant 中的 AI 资讯正文属于应备份的持久数据，不只是可随意清空的索引。正式晨报的完整权威版本在 SQLite。
- 对检索片段保留稳定的文章/事件/晨报版本关联，保证可追溯；索引失败不能悄悄变成成功。

### 4. 阶段缓存、Checkpoint 与重新生成

- **阶段缓存**：普通 LLM 节点、三个 Subagent 等成功阶段完成后保存结果。仅在输入、相关资料版本、Memory、模型与配置等关键依赖一致时复用。
- **每日清理**：08:00 发起新一轮自动生成时清理前一轮阶段缓存；缓存最长有效期 12 小时。此操作不删除新闻、向量库、Memory、历史报告及正式日志。
- **部分变化**：只重算受影响阶段和下游依赖；最终整合与事实校验应重新执行。无法确认缓存安全性时完整重算。
- **用户纠错**：如指出缓存中存在错误，应能使相应阶段缓存失效；保留必要时完整重算的能力，不让错误无限复现。
- **区分多种缓存**：阶段结果缓存用于跨执行复用（最多 12h，08:00 清理）；**Embedding 复用缓存**按文本/分块内容哈希、Embedding 模型及版本、预处理/切分版本判断是否有效，不随阶段缓存清理；LLM 服务商前缀 Token 缓存用于重复输入优化。LangGraph Checkpoint 用于执行恢复，不等于上述缓存。
- **Prompt 组织**：固定系统规则尽量放前面，动态资料追加在后面；不因节约 Token 强行压缩有价值资料；遵守模型实际上下文窗口并预留输出；历史内容按相关性检索，不整库塞入 Prompt。
- **重新生成与版本**：页面只需一个主要“重新生成”入口；**若自动生成失败且当日尚无主报告，首次手动成功结果确立为当日唯一主报告**；之后同日手动成功结果作为附加版本存档，不覆盖原主报告；显示当前查看的版本。

### 5. 故障处理与发布门槛

| 故障场景 | 处理规则 |
| --- | --- |
| 个别资讯源不可访问 / 全文抓取失败 | 记录缺失，允许基于可信的已取得资料继续；不得伪造全文 |
| 本期必要 Qdrant 索引或必要历史索引异常 | **阻塞进入 Agent 分析**；重试修复，失败则本轮生成失败 |
| 部分非关键分析节点失败 | 保留成功阶段结果，视内容可信度允许降级，写明缺失 |
| 技术研究 / 目标分析 Subagent 失败 | 保留有效分析并显示降级；后续建议只能依据实际成功结果，不得假称完整分析 |
| 建议 Subagent 失败 | 可不展示建议，但必须记录“分析失败”，不能冒充“无新增建议” |
| 主 Agent 整合失败 | 不发布不完整晨报 |
| 严重事实 / 引用校验未通过 | 阻止发布错误内容 |
| 质量评价 API 超时或失败 | 记录“未评价/评价失败”，不阻塞已通过事实校验的晨报 |

- 自动生成失败有限重试，**最多 3 次**；手动重新生成不限总次数但防止并发重复运行。已成功阶段可按有效缓存复用。
- 模型超时、拒绝、限流或其他 API 故障必须记录具体状态，不能静默切换到未经许可的模型。
- 降级生成与阻塞规则同时存在：**资讯源的局部缺失可能降级；必要索引失败、主编失败、严重事实错误必须阻塞。**

### 6. 模型使用与质量评价

- 每日正式自动生成：指定 DeepSeek 模型（产品目标 `DeepSeek-V4.1-Flash-1017`；实际 API ID 与低峰时段需 Kimi Code 验证）；**每次调用前检查允许时段**，不可用则失败，不静默切换模型。
- 开发和手动重新生成：已接入的 DashScope 免费模型。质量评价也使用独立 LLM API 调用，具体模型在实施时验证。
- **质量评价仅输入最终晨报正文**：它能评价表达、结构、技术分析呈现及内部逻辑，**不能凭正文可靠核验新闻真伪和是否漏掉重大资讯**；后者仍由独立事实校验和新闻覆盖检查负责。
- 五维评分 + 综合分 + 一段自然语言**「评价」**；不拆“主要问题”“改进建议”。综合分采用稳定、统一、可解释且版本化的规则，具体权重/公式在 T18 验证前**仍是实施待定参数**。评分不作为自动重生成的触发条件，也不设置硬性合格线。
- 每份晨报版本与其评价结果绑定；评价 API 失败时保留未评价状态。

### 7. 日志、统计与前端呈现

- 每个主要步骤产生实时业务日志，例如“08:00 采集完成”“向量索引验证通过”“技术研究开始”“报告校验完成”“质量评价失败”。
- 技术详情可以展开查看模型、Tool 调用、耗时、Token、阶段/Embedding 缓存、Query 改写与 Rerank 是否启用、错误摘要；**日志持久化**，可按晨报运行/版本查阅。
- 记录总耗时、主要阶段耗时、模型调用次数、输入与输出 Token、供应商缓存命中/未命中、费用；另记录 Embedding 复用次数、RAG 增强调用及耗时；未由服务商提供的数据标记未知，不臆造。
- 页面以阅读为中心，顶部二级导航：**晨报正文 / 质量评价 / 历史晨报**。质量评价跟随当前选中的晨报版本。
- 正文页采用宽敞的 PC 阅读布局，右栏以晨报助手对话框为主、实时日志为辅；质量评价独立展示，不侵入正文。
- 生成中展示阶段与日志；失败展示原因与重新生成入口；展示旧晨报时必须标注原日期，不能伪装成当天报告。
- 晨报正文不做重度字段卡片化：**速览是重要资讯的总体总结；国内/国际标题+摘要；AI 标题+摘要+评价；“我的昨日”自然叙述；今日建议简洁且可执行。**

## 三、与 V1.2 相比的变化

1. 增加 **08:00 最终采集 → 必要 Qdrant 索引更新成功 → 冻结数据快照** 的严格前置门槛。
2. 明确存储选型为 **Qdrant（AI 技术全文/历史晨报语义索引）+ 独立 SQLite（社会新闻、晨报业务及日志）**，原个人助手数据库只读。
3. 固定保留 V1.2 的 **双分析节点并行、技术研究/目标分析并行、建议 Subagent 后置**，不改变三个 Subagent 的调用原则。
4. 将原先统一的“报告生成”明确拆分为 **主 Agent 编辑 → 事实校验 → 独立质量评价 → 发布/保存**，质量评价失败不影响合格报告发布。
5. 补充阶段结果缓存（12 小时、每日清理、按依赖局部重算）、Checkpoint 区别与缓存错误纠正规则。
6. 增加模型超时、拒绝、Tool 故障、索引失败、部分 Subagent 失败等**分级兜底**；关键前置条件与事实错误仍阻塞。
7. 用**实时且持久化的运行日志**代替单纯的 Agent 信息摘要窗口，并记录 Token、缓存、费用与主要阶段耗时。
8. 明确自然语言的**晨报内容结构与 PC 阅读型 UI**，并增加绑定历史版本的“质量评价”二级页面。
9. **同步产品 V0.5**：更正为每天六个固定采集时点，增加分层去重与新进展保护、三个 Subagent 共享的按需 Query 改写/Rerank，以及独立于 12 小时阶段缓存的 Embedding 复用；明确无主报告时首次手动成功结果的身份。
