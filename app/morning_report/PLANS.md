# PLANS.md — 今日晨报 Agent 开发计划

## 1. 项目定位与总体目标

本项目以今日晨报系统为实践载体，结合 OpenAI 公开的工程实践，通过真实开发验证五阶段 Agent 开发流程，并最终形成可复用的 Agent 开发 SOP/SDD。

### 1.1 两项硬性约束

1. **五阶段开发流程**：遵循「项目分析 → 目标与规格 → 架构与计划 → 实施 → 验收」的开发流程。
2. **OpenAI 工程实践**：参考 OpenAI 官方公开的工程原则、开发规范及实践案例，并通过实际开发验证其适用性。

需要明确区分 OpenAI 官方建议、官方实践案例与本项目的自主设计，不将项目适配方案表述为 OpenAI 官方标准。

### 1.2 通用开发理念

本项目最终希望形成的开发方法论，应适用于一般 Agent 业务开发，而不仅限于工程化改造项目。

其核心关系为：

- **业务需求**：决定项目为什么开发、需要交付什么价值。
- **五阶段流程**：组织从项目分析到最终验收的完整开发过程。
- **五大工程能力**：为 Agent 系统提供设计、实现、运行和质量保障方面的工程支持。
- **测试与验收**：验证业务目标、工程要求及开发过程是否达到预期。

一般项目应由业务需求驱动，根据实际需要设计和应用五大工程能力，而不是为满足工程清单而增加不必要的技术实现。

### 1.3 今日晨报的特殊定位

今日晨报 V3 及后续迭代是一次以工程能力建设为主要目标的专项实践。

本轮开发将五大 Agent 工程能力及其具体任务全部纳入固定范围，通过对真实晨报系统的开发和验证：

- 建设和验证五大 Agent 工程能力。
- 保证今日晨报核心业务流程能够正常运行，并满足本轮确定的业务规格。
- 检验五阶段流程是否完整、有效、可执行。
- 验证 OpenAI 工程实践在真实项目中的适用性。
- 最终形成可复用的 Agent 开发 SOP/SDD。

技术栈迁移、代码重构和框架选型属于实现手段，不作为独立的工程能力目标。

## 2. 固定任务清单

本轮实践的工程建设范围包含五大工程能力、14 项二级任务。

以下任务均需在本轮或后续迭代中完成实践与验证。具体实现方案和版本归属由后续阶段决定。

### 2.1 Orchestration（Agent 编排）

#### 2.1.1 Agent 驱动架构
- 将今日晨报整体改为 Agent 驱动。
- 明确 Agent 与确定性程序的职责边界。

#### 2.1.2 Workflow 重新编排
- 重新设计晨报生成流程。
- 明确任务步骤、执行顺序与编排逻辑。

#### 2.1.3 Agent 职责调整
- 合并目标分析 Agent 与建议 Agent。
- 简化 Agent 分工。

### 2.2 Context & Tools（上下文与工具）

#### 2.2.1 Prompt 与上下文管理
- 梳理 System Prompt、任务上下文及其组织和加载方式。

#### 2.2.2 Skills 渐进式披露
- 使用 Skills 实践任务指令的按需发现与加载。
- 保留核心 System Prompt，不直接用 Skills 替代。

#### 2.2.3 Tool Definitions 渐进式披露
- 组织工具定义。
- 实现工具能力的按需发现与加载。
- 明确工具调用方式。

### 2.3 Contracts & Guardrails（契约与护栏）

#### 2.3.1 数据与接口契约
- 定义数据模型。
- 定义 JSON Schema。
- 定义 API 契约。
- 定义工具输入输出契约。
- 定义任务状态契约。
- 实践类型检查与运行时数据校验。

#### 2.3.2 四类 Guardrails
- Agent Input Guardrails。
- Agent Output Guardrails。
- Tool Input Guardrails。
- Tool Output Guardrails。
- 定义检查失败时的处理行为。

### 2.4 Runtime & Observability（运行时与可观测性）

#### 2.4.1 执行与状态管理
- 管理任务执行状态。
- 管理 Agent 执行过程。
- 实现必要的状态持久化。

#### 2.4.2 异常处理与恢复
- 异常分类与处理。
- 超时控制。
- 重试机制。
- 任务取消。
- 失败恢复。
- 幂等性保障。

#### 2.4.3 可观测性
- 结构化日志。
- Agent Tracing。
- 告警机制。

### 2.5 Testing & Evals（测试与评估）

#### 2.5.1 自动化测试
- 单元测试（Unit Testing）。
- 集成测试（Integration Testing）。
- 端到端测试（End-to-End Testing）。

#### 2.5.2 属性测试
- Round-trip Encoding。
- Invariants。
- Idempotency。
- Equivalence。

#### 2.5.3 Agent Evals
- 建立评估数据集。
- 定义质量评估指标。
- 实现评估用例与评价机制。
- 建立回归评估机制。

## 3. 五阶段开发流程

五阶段是统一开发流程，业务需求与工程能力是贯穿各阶段的两个关注维度。

| 阶段 | 业务开发 | 工程能力 | 主要产出 |
|---|---|---|---|
| **阶段一：项目分析** | 理解业务现状、系统行为及已有问题 | 分析现有架构、工程机制和质量基线 | AGENTS.md、ARCHITECTURE.md、PLANS.md |
| **阶段二：目标与规格** | 定义业务目标、功能行为、范围与成功条件 | 定义工程要求、约束及质量目标 | GOALS.md、Product Specs |
| **阶段三：架构与计划** | 设计业务流程、模块交互和系统架构 | 设计适用的工程能力、技术方案及验证策略 | Design Docs、必要的执行计划 |
| **阶段四：实施** | 实现业务功能并完成集成 | 落实工程设计，持续测试、评估与修正 | 代码、配置、测试及评估实现 |
| **阶段五：验收** | 验证业务功能及交付价值 | 验证工程约束、可靠性及 Agent 质量 | 测试结果、Evals 结果、验收结论 |

阶段零为文档体系初始化，不计入正式五阶段流程。

### 3.1 统一原则

- 五阶段是开发过程，不与某项具体工程能力绑定。
- 业务开发和工程能力建设都应遵循五阶段流程。
- 工程能力在各阶段的工作内容与投入程度由项目目标和风险决定。
- 测试与 Evals 应在前期明确目标与方案，在实施阶段持续执行，在阶段五完成正式验收。
- 各阶段允许根据验证结果返回前序阶段修订，形成闭环。

### 3.2 阶段边界

- **阶段一**：理解现状和制定高层计划，不提前开展详细设计。
- **阶段二**：明确目标、范围、约束和成功条件，不提前绑定具体实现方案。
- **阶段三**：完成关键架构决策、接口契约、工程设计及验证方案。
- **阶段四**：依据规格与设计实施，持续测试和评估，及时反馈问题。
- **阶段五**：依据预先确定的成功条件进行验收，不以代码完成或测试运行作为唯一成功依据。

## 4. 开发安排与版本策略

### 4.1 总体原则

- 五大工程能力及 14 项任务构成本轮专项实践的固定范围。
- 版本划分仅用于安排工作量、控制变更风险和组织交付。
- 不提前限定必须开发 V3、V4 或 V5。
- 如果工作量允许，可以在 V3 完成全部任务。
- 如果工作量较大，可以划分为 V3、V4 或后续版本。
- 每个正式交付版本均应完整经历五阶段流程。
- 版本调整不得遗漏固定任务；如果确需改变总体范围，应明确记录原因与决策。

### 4.2 初步实施依赖

优先考虑以下依赖关系：

1. 建立业务与工程现状基线，明确已有能力、问题及风险。
2. 明确本轮业务目标、工程约束、数据与接口契约。
3. 设计并实现核心 Agent Orchestration。
4. 逐步建设 Context & Tools、Contracts & Guardrails、Runtime & Observability。
5. 持续开展自动化测试、属性测试和 Agent Evals。
6. 完成业务与工程验收，并根据结果改进开发方法。

以上为逻辑依赖，不代表所有工作必须严格串行。

### 4.3 版本规划

**V3：首次完整实践**

优先保证本轮交付能够完整执行五阶段流程，并实现可运行、可测试、可评估的业务与工程闭环。

具体范围在阶段二确定，依据阶段三的设计和工作量评估作必要调整。

**V4 及后续版本：按需开展**

用于完成尚未交付的固定任务，并继续检验和完善五阶段方法论。

如果 V3 已完成全部任务且验收充分，不强制增加后续版本。

## 5. 工程与文档原则

### 5.1 业务驱动、工程保障

一般 Agent 开发以业务目标为起点，工程能力服务于业务交付。

本轮今日晨报实践虽以工程能力建设为主要目标，仍必须保证业务行为的正确性和实际可用性。

### 5.2 遵循 OpenAI 工程实践

优先参考 OpenAI 官方公开的工程原则，并结合实际项目进行验证。

不将本项目的五阶段流程、五大工程能力分类或具体技术选择描述为 OpenAI 官方规定的标准。

### 5.3 渐进式披露与单一事实来源

项目文档通过清晰的导航结构按需访问。

Agent 指令、Skills 和 Tool Definitions 根据实际机制实现按需加载。

避免重复维护同一信息，优先通过引用关联已有文档。

### 5.4 明确工程职责边界

- Orchestration 负责 Agent 职责与执行流程的组织。
- Context & Tools 负责指令、上下文和工具能力的提供。
- Contracts & Guardrails 负责数据契约及 Agent 交互边界约束。
- Runtime & Observability 负责可靠执行、状态管理及运行观测。
- Testing & Evals 负责正确性、可靠性和 Agent 质量验证。

五大工程能力是项目管理和设计的关注领域，不要求代码必须严格划分为五个对应模块。

### 5.5 保持适当的工程复杂度

根据业务需求、风险和可验证的收益选择实现方案。

不为了增加技术组件而增加不必要的系统复杂度。

### 5.6 保持规格与实现可追溯

重要业务需求和工程要求应具备明确的验收依据。

设计、实现、测试和评估应能够追溯到对应的目标与规格。

## 7. SOP/SDD 验证与沉淀

### 7.1 最终目标

通过今日晨报开发实践，形成一套能够复用于其他 Agent 业务项目的五阶段 SOP/SDD。

该方法论应以业务开发为主线，将适用的工程能力融入各阶段，而不是要求所有项目都实现相同的技术组件。

### 7.2 验证重点

重点检验：

- **完整性**：五阶段是否覆盖从需求到验收的完整开发过程。
- **有效性**：各阶段活动和产出是否真正支持后续开发。
- **工程覆盖**：五大工程能力是否得到适当分析、设计和验证。
- **可追溯性**：业务目标、工程约束、设计、实现及验收能否形成对应关系。
- **可复用性**：流程能否应用于其他 Agent 项目，而不依赖今日晨报的特定架构。
- **可维护性**：文档与开发流程是否清晰、简洁，避免重复与过度工程化。

### 7.3 方法论沉淀

在开发过程中记录重要决策、问题及改进依据。

每轮验收后，依据实际结果修订开发流程。

最终 SOP/SDD 应明确：

- 五阶段的输入与产出。
- 各阶段的主要活动、职责和完成条件。
- 业务开发与工程能力的协作方式。
- 五大工程能力的设计检查项。
- 测试、Evals 与验收要求。
- 阶段之间的反馈和修订机制。
