# 今日晨报项目目标

阶段二目标与成功条件，与截至 Q90 的产品规格定稿候选同步。

## 1. 项目目的

今日晨报帮助个人助手用户按需了解国内、国际和 AI 资讯，并结合个人记录判断今天值得采取的行动。用户可以回看已发布报告，也可以收藏值得跟进的新闻。

现行系统已经支持定时生成、重新生成、重新组装、历史报告和新闻收藏。V3 采用手动生成，保留历史报告与新闻收藏，并改善个人分析的依据透明度、来源缺失时的可用性，以及生成异常时的可诊断性。晨报同时包含外部资讯、只读个人数据、模型推理、确定性组装和后台发布，适合在真实业务中检验 Agent 工程实践。[现行业务规则](../../Docs/PRD.md) · [模块现状](ARCHITECTURE.md)

## 2. 预期成果

| 类型 | 预期成果 |
| --- | --- |
| 业务 · 快速掌握资讯 | 用户从当期报告快速浏览资讯及可用来源。个别来源不可用时，用户仍可阅读已取得的内容，并能看出缺口。 |
| 业务 · 回顾与行动 | 用户可获得最多三条建议，每条标明去向，并可展开查看依据和评估结果。没有建议时能了解原因。 |
| 业务 · 控制与回看 | 用户能了解任务进度、停止执行，按需要生成当日晨报，并能继续查阅历史报告和收藏。 |
| 工程 · Orchestration | 晨报的 Agent 驱动编排可运行，Agent 的判断职责与程序负责的确定性处理边界清晰。 |
| 工程 · Context & Tools | Agent 可按任务取得必要的上下文、指令和工具，使用范围可核查。 |
| 工程 · Contracts & Guardrails | 数据、API、工具和运行状态的契约可验证，越界、非法输入或输出有明确处理结果。 |
| 工程 · Runtime & Observability | 运行状态可追踪，取消、失败和中断有明确结果，诊断信息足以定位问题。 |
| 工程 · Testing & Evals | 功能、关键不变量和 Agent 输出质量具备可重复的验证证据，支持后续回归比较。 |

## 3. 成功条件

**业务验收沿用现行 PRD，除非后续规格明确批准改动。**

- **资讯可读。** 在隔离场景中验证用户手动发起的当期生成。报告按 V3 收录规则展示资讯及可用链接。模拟单一来源失败时，进度和已发布报告说明缺口，是否发布按资讯和候选建议的可用性判断。V3 的触发规则见[生成规格](docs/product-specs/report-generation.md)。
- **建议有证据。** 用含完成、未完成和缺失记录的测试数据验证。今日建议最多三条，展开区可查看本轮依据及评估结果。无建议时保留小节，说明是依据不足、读取缺口还是分析失败。
- **结果可管理。** 验证手动生成与历史查看的行为。失败或取消的任务不会覆盖成功版本，历史列表仍可按日查看最新已发布版本，收藏、备注和重点状态读回一致。[报告操作回归](../../tests/test_morning_report_actions.py) · [个人决策回归](../../tests/test_morning_decision_workflow.py)

**工程验收按各版本获准的交付范围提供证据。**

| 能力 | 可观察的验收证据 |
| --- | --- |
| Orchestration | 正常与异常场景均能验证从触发到发布或终止的路径，并说明各环节由 Agent 还是程序负责。 |
| Context & Tools | 用例能确认需要的指令和工具可按需获得，个人分析仅使用授权上下文，越界请求得不到额外数据。 |
| Contracts & Guardrails | 有效和无效案例覆盖 Agent 与工具输入输出边界。非法数据或不支持 JSON mode 的响应触发预期的错误或降级结果。 |
| Runtime & Observability | 取消、超时、失败和中断场景有可观察的状态与非敏感诊断信息。重复提交或按约定恢复时，可检查历史成功结果是否受到保护。 |
| Testing & Evals | 为交付项提供可重复的自动化测试、适用的属性测试与 Agent 评估结果，并能对应到规格和验收条件。评估门槛待确认。 |

## 4. 项目范围

- **业务范围。** 今日晨报的资讯采集、个人行动建议、报告生成、版本与收藏、任务进度及相关页面和接口。
- **工程范围。** Orchestration、Context & Tools、Contracts & Guardrails、Runtime & Observability、Testing & Evals 共五类能力、14 项固定任务。明细和总体版本安排见[晨报专项计划](PLANS.md)。
- **宿主边界。** 范围覆盖晨报与宿主的装配、页面入口、API 和必要的个人数据只读接入。微信、GitHub、阅读与计划管理等独立业务的改造不属于晨报专项。确需改动共享核心接口时，按仓库规则先说明影响并获得授权。[宿主架构](../../ARCHITECTURE.md) · [仓库开发规范](../../AGENTS.md)
- **版本策略。** V3 为当前主要开发版本，优先完成可运行、可测试、可验收的今日晨报闭环。五大工程能力及 14 项任务构成整体固定建设范围，具体实施顺序在架构与计划阶段确定，仅在实际需要时划分后续版本。

## 5. 非目标

- 技术栈迁移、框架替换和代码重构按交付需要决定，不单设为成果。五阶段流程的合理性证明、完整 SOP/SDD 及其跨项目可复用性证明不作为本轮成功条件。可将实践记录用于长期积累。

## 6. 技术与运行约束

- 现有部署面向单用户 Windows PC，晨报作为 FastAPI + React 宿主中的模块运行。前端通过 `/api/*` 访问后端，生成等长任务走后台状态管理。遵守仓库关于依赖、外部调用和模型 JSON mode 的规则。[仓库开发规范](../../AGENTS.md) · [晨报开发规范](AGENTS.md)
- 保留既有报告、版本和收藏数据的可用性及历史兼容。代码合并不隐式迁移或覆盖个人数据库。涉及共享 API、配置或数据结构时先核对兼容性。具体契约变更以批准的规格为准。
- 遵循「项目分析 → 目标与规格 → 架构与计划 → 实施 → 验收」，并按授权推进。五阶段和五类工程能力是项目自主安排。结合 OpenAI 公开建议及实践案例，记录所采纳做法在晨报中的适用性。[Codex Cookbook](https://developers.openai.com/cookbook/examples/codex/iterating-development-workflows-with-codex) · [Harness Engineering](https://openai.com/index/harness-engineering/)
- DashScope 模型由配置选择，须支持原生 JSON mode 和工具调用。能力及切换约束见[晨报开发规范](AGENTS.md)。
- 现行编排使用 LangGraph，分析代理由 LangChain 实现。Runtime、框架及具体实现方式留待架构与计划阶段决定。

## 7. 安全、可靠性与恢复要求

- 只读访问已配置的个人数据源。读取失败时说明缺口，避免把无法取得数据当成没有进展。晨报运行数据写入独立数据库，禁止写入现有个人库、微信两库和 Chroma。
- 测试、调试与迁移验证用隔离数据，默认模拟模型和外部服务。真实模型或真实采集验证单独标记 LIVE。密钥和私人数据不得进入 Git 或文件日志，诊断只记录必要的非敏感信息。
- 来源故障、模型异常、任务取消与进程中断均应留下可见状态或明确的降级结果。按进度规格处理重启和手动重试，核查旧版本保留以及同次提交不重复生成。
- 保留已发布的成功报告和历史数据，禁止自动删除。异常处理中保护任务状态与用户收藏，禁止静默切换模型、去掉 JSON mode 或把非法输出当作正常结果。[晨报开发规范](AGENTS.md)
